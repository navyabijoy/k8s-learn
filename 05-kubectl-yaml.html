kubectl basics and reading YAML

How to talk to the cluster and read what it says back

Section 05

kubectl is how you talk to a cluster, and YAML is what you say. Both look strange for a day and then stop being strange. This chapter gives you the grammar of one and the shape of the other, so you can read any manifest you are handed.

The problem

The cluster's brain, the API server, speaks HTTP. You could talk to it with curl. You would need the right URL for every object type, the right credentials, and a JSON body for every change. Nobody wants that.

You also need a way to write down "what I want" in a file you can keep in git, read, and review. Shell commands do not do that well. A document does.

Key idea

kubectl is a command-line HTTP client for the API server. It turns kubectl get pods into a request, and your YAML files into the objects the cluster stores.

The grammar of kubectl

Nearly every command has the same shape: verb, resource, name, flags.


kubectl get pods web -n dev -o wide
│       │   │    │   │      │
│       │   │    │   │      └─ output format: wide
│       │   │    │   └──────── which namespace: dev
│       │   │    └──────────── which one (optional): web
│       │   └───────────────── what kind of thing: pods
│       └───────────────────── what to do: get
└───────────────────────────── the program

Leave out the name and you get all of them in that namespace. Verbs you will use all the time:

VerbDoesLinux cousin
getList objects, one line eachls
describeShow one object in detail, with eventsls -l plus journalctl
applyMake the cluster match a filecopy a config file into place
deleteRemove an objectrm
logsPrint a container's outputtail
execRun a command inside a containerssh in, but into a container
explainShow the documentation for a fieldman

Three ways to look at the same Pod


kubectl get pod web
kubectl get pod web -o wide
kubectl get pod web -o yaml
  • Plain get is the summary line.
  • -o wide adds the node and the Pod IP.
  • -o yaml prints the whole object, the way the API server stores it. It includes a status: block you did not write. When someone says "look at the YAML", this is what they mean.

Picking out one value


kubectl get pod web -o jsonpath='{.status.podIP}'
kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
kubectl get pods -o name
  • jsonpath walks into the object and prints one field. Good in scripts.
  • custom-columns builds your own table from fields.
  • -o name prints only pod/web. Good for piping into other commands.

Finding things


kubectl get pods -A
kubectl get pods -l app=web
kubectl get pods --watch
  • -A (--all-namespaces) looks everywhere, not only your current namespace.
  • -l filters by label (chapter 8).
  • --watch (-w) keeps the command open and prints a line whenever something changes. Press Ctrl+C to stop. Like tail -f.

Which cluster am I talking to?

This is the question that saves jobs. kubectl does not know about clusters by magic. It reads a file called a kubeconfig, by default ~/.kube/config. It holds three lists:

Clusters

Where each API server lives (address and its certificate authority).

Users

How you prove who you are to each cluster (certificate, token, or a login helper).

Contexts

A saved combination: this cluster, with this user, in this namespace.

Current context

The one kubectl uses right now, if you do not say otherwise.


kubectl config current-context
kubectl config get-contexts
kubectl config use-context kind-handbook
kubectl config set-context --current --namespace=dev
  • current-context prints the one you are on. Run it before anything destructive.
  • get-contexts lists them all. The current one has a *.
  • use-context switches.
  • set-context --current --namespace=dev changes the default namespace of the current context, so you can stop typing -n dev.

Linux link: this is the same idea as ~/.ssh/config, with a list of hosts and the keys to use for each. And just like PATH, the KUBECONFIG environment variable can point kubectl at a different file, or at several files joined with :.

This can break things

You are only ever one use-context away from running kubectl delete on production. Check kubectl config current-context first. Many teams put the context name in their shell prompt for this reason.

Reading YAML

YAML is a way to write nested settings as plain text. Three rules cover most of it:

  • Indentation is structure. Use spaces. Never tabs. Two spaces per level is the habit.
  • key: value is a setting. A key with nothing after it holds a nested block.
  • A line starting with - is one item in a list.

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80

Read it as a tree. Indentation gives the parent:


Pod
├── apiVersion: v1
├── kind: Pod
├── metadata
│   ├── name: web
│   └── labels
│       └── app: web
└── spec
    └── containers            ← a list
        └── (item 1)
            ├── name: nginx
            ├── image: nginx:1.27
            └── ports         ← another list
                └── (item 1)
                    └── containerPort: 80

The four top-level fields

FieldAnswersWho writes it
apiVersionWhich version of the API describes this?you
kindWhat type of object?you
metadataWhat is it called, and what labels does it carry?you (plus a few fields the cluster adds)
specWhat do I want?you
statusWhat is actually true right now?the cluster. You never write it.

apiVersion looks odd the first time. v1 means the original "core" group: Pods, Services, ConfigMaps. Other things live in named groups: Deployments are apps/v1, Ingress is networking.k8s.io/v1. The part before the slash is the group, the part after is the version.

YAML gotchas that bite


# a number
replicas: 3

# a string that looks like a number: quote it
version: "1.27"

# YAML turns these into booleans if you do not quote them
enabled: "true"
country: "NO"

# two objects in one file, separated by ---
apiVersion: v1
kind: Namespace
metadata:
  name: dev
---
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: dev
  • Env var values and annotation values must be strings. Quote numbers and booleans there.
  • --- splits one file into several objects. kubectl apply -f reads them all.

You do not need to memorise fields

This is the chapter's best trick. The cluster documents itself:


kubectl explain pod
kubectl explain pod.spec.containers
kubectl explain pod.spec.containers.resources --recursive
kubectl api-resources
  • explain pod describes the Pod object and lists its top-level fields.
  • Add dots to go deeper: pod.spec.containers lists what a container may contain.
  • --recursive prints the whole subtree as one outline.
  • api-resources lists every kind the cluster knows, its short name (like po, svc, deploy), its group, and whether it lives in a namespace. It is also how you find the right apiVersion.

In an interview, "I'd run kubectl explain" is a better answer than a half-remembered field name.

apply vs create


kubectl create -f nginx-pod.yaml
kubectl apply -f nginx-pod.yaml
kubectl apply -f ./manifests/
kubectl diff -f nginx-pod.yaml
  • create says "make this new". It fails if the object already exists.
  • apply says "make the cluster look like this file". It creates if missing and updates if it differs. Run it ten times and nothing breaks.
  • Give apply a folder and it applies every file in it.
  • diff shows what apply would change without changing anything. Use it before every apply on a real cluster.

A good bridge: let kubectl write the file for you, then edit and apply it.


kubectl create deployment web --image=nginx:1.27 --replicas=2 --dry-run=client -o yaml > web-deploy.yaml
kubectl apply -f web-deploy.yaml

--dry-run=client builds the object locally and prints it. --dry-run=server sends it to the API server, which validates it fully but stores nothing. The server version catches more mistakes.

Linux you already know

  • kubectl get pods is a GET request. You can watch kubectl make it: add -v=6 and it prints the HTTP calls. At -v=8 you see the request and response bodies.
  • You can talk to the API with curl. kubectl proxy opens localhost:8001 with your credentials already attached. Then curl localhost:8001/api/v1/namespaces/default/pods returns the same data as kubectl get pods -o json.
  • kubectl get --raw /api/v1/namespaces/default/pods does the same without a proxy.
  • Shell tricks you already know still work: kubectl get pods -o name | grep web, alias k=kubectl, and tab-completion with source <(kubectl completion bash) (or zsh).

Common mistakes

Common mistake

Tabs in YAML. They are not allowed. You get error converting YAML to JSON or a message about a found character that cannot start a token. Set your editor to insert spaces.

Common mistake

Wrong indentation that is still valid YAML. A ports: block indented one level too far or too little will often parse fine and then be rejected, or silently put the field somewhere else. When the cluster says unknown field, count the spaces.

Common mistake

"kubectl get all shows everything." It does not. It shows a fixed handful of kinds (Pods, Services, Deployments and a few more) in one namespace. ConfigMaps, Secrets, Ingresses, PVCs and custom resources are not included. Use kubectl api-resources and ask for the kind by name.

Common mistake

Editing live objects with kubectl edit, then applying the old file. The live object and your file drift apart, and the next apply quietly overwrites your edit. Treat the file as the truth. Edit the file, then apply.

Common mistake

Reusing -o yaml output as a manifest. It includes status, uid, resourceVersion and more. Some of that will make an apply fail or behave oddly. Start from --dry-run=client -o yaml instead.

Common mistake

Forgetting the -- in exec. kubectl exec web -- ls -l is right. Without --, kubectl tries to read -l as its own flag.

This can break things

kubectl delete -f file.yaml deletes everything defined in that file. kubectl delete -f ./manifests/ deletes everything in the folder. Run kubectl diff or kubectl get -f ./manifests/ first to see what will be touched.

Try it

Try it

Use the kind cluster from chapter 4 (context kind-handbook). Everything below is safe: it all lives in a namespace you delete at the end.


# 1. know where you are
kubectl config current-context
kubectl config get-contexts

# 2. a scratch namespace, and make it your default
kubectl create namespace dev
kubectl config set-context --current --namespace=dev

# 3. save the Pod from this chapter as nginx-pod.yaml, then preview and apply it
kubectl diff -f nginx-pod.yaml
kubectl apply -f nginx-pod.yaml
kubectl apply -f nginx-pod.yaml        # again: nothing should change

# 4. try create on something that exists
kubectl create -f nginx-pod.yaml       # should fail with AlreadyExists

# 5. read it three ways
kubectl get pod web -o wide
kubectl get pod web -o yaml
kubectl get pod web -o jsonpath='{.status.podIP}'

# 6. let the cluster document itself
kubectl explain pod.spec.containers.ports
kubectl api-resources | head -20

# 7. watch kubectl talk HTTP
kubectl get pod web -v=6

# 8. clean up, and put your default namespace back
kubectl config set-context --current --namespace=default
kubectl delete namespace dev

What to look for:

  • Step 3, second apply: it reports the Pod as unchanged. That is "declarative" in one line.
  • Step 4: AlreadyExists. That is the difference between create and apply.
  • Step 5, the YAML output: find the status: block, and fields you never wrote (uid, nodeName).
  • Step 7: lines starting with GET https://…/api/v1/namespaces/dev/pods/web. That is all kubectl is doing.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between kubectl apply and kubectl create?

create is imperative. It makes a new object and fails if it already exists. apply is declarative. I give it the state I want, and it creates the object if it's missing or updates it if it differs, so I can run it repeatedly. For anything real I use apply, with the file in git, and I run kubectl diff first to see what will change.

How does kubectl know which cluster to talk to?

From the kubeconfig, normally ~/.kube/config, or whatever KUBECONFIG points to. It holds clusters, users and contexts. A context ties one cluster to one user and a default namespace. The current context decides where commands go. I check it with kubectl config current-context before anything destructive.

What are the main top-level fields of a Kubernetes manifest?

apiVersion and kind say what type of object it is. metadata holds the name, namespace and labels. spec is what I want. And there's status, which the cluster fills in and I never write. A few kinds, like ConfigMap and Secret, have data instead of spec.

What's the difference between spec and status?

spec is desired state, written by me. status is observed state, written by the cluster. Controllers keep comparing them and acting on the gap. If I ask for three replicas and status says two are ready, a controller has work to do. That comparison loop is how Kubernetes works.

You don't remember a field name. How do you find it without a browser?

kubectl explain. For example kubectl explain pod.spec.containers lists the fields, with descriptions. Adding --recursive gives the whole tree. And kubectl api-resources tells me the kind, its group and whether it's namespaced, which gives me the apiVersion. It's the cluster's own built-in documentation, and it matches the exact version I'm running.

Habits worth keeping

Habits

Check the context before you change anything. Generate YAML with --dry-run=client -o yaml. Preview with kubectl diff. Keep the file as the truth and apply it, instead of editing live objects. Ask the cluster with kubectl explain before you search the web. And when kubectl confuses you, add -v=6 and watch the request it makes.
