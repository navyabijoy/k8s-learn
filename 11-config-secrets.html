ConfigMaps and Secrets

Keeping settings out of the image

Section 11

The same image should run in dev, staging and production. What changes between them is configuration: a log level, a database address, a password. Kubernetes keeps that outside the image, in two objects: ConfigMaps for ordinary settings and Secrets for sensitive ones. The most important thing in this chapter is what a Secret is not.

The problem

You build an image with the database address written into the code. To move from dev to production you rebuild the image. Now the thing you tested is not the thing you ship.

You fix that with environment variables, as in the Linux handbook. But now the production database password sits in a YAML file, and that YAML file is in git, and everyone with the repository can read it.

You need two things: a way to hand settings to a Pod without changing its image, and a separate way to hand over the sensitive ones with more care.

Key idea

A ConfigMap holds plain settings. A Secret holds sensitive ones. Both are objects in the cluster that a Pod can read as environment variables or as files. The image never changes.

ConfigMap

Key-value pairs or whole files: log level, feature flags, an nginx.conf. Not secret. Anyone who can read the namespace can read it.

Secret

The same shape, for passwords, tokens and keys. Handled a little more carefully, but not encrypted by default.

As env vars

Simple, but fixed at Pod start. Changing the ConfigMap does not change a running Pod's environment.

As files

Each key becomes a file in a directory. Updates arrive in the running Pod, after a delay.

ConfigMaps


apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  FEATURE_X: "true"
  app.properties: |
    colour=blue
    retries=3


data:                          a ConfigMap has data:, not spec:
  LOG_LEVEL: "info"            a simple key and value. Values are always strings: quote them.
  app.properties: |            a key whose value is a whole file. The | keeps line breaks.
    colour=blue
    retries=3

You can also create one without writing YAML:


kubectl create configmap app-config --from-literal=LOG_LEVEL=info --from-literal=FEATURE_X=true
kubectl create configmap app-files --from-file=app.properties
kubectl create configmap app-dir --from-file=./conf/
  • --from-literal makes a key from a value you type.
  • --from-file uses the file name as the key and the file contents as the value.
  • Pointing --from-file at a folder makes one key per file in it.

Both ConfigMaps and Secrets are limited to 1 MiB each. This is for settings, not for data.

Getting it into a Pod


apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "env | grep -E 'LOG_LEVEL|DB_PASSWORD'; ls -lL /etc/app /etc/creds; sleep 3600"]
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db
              key: password
      volumeMounts:
        - name: config
          mountPath: /etc/app
        - name: creds
          mountPath: /etc/creds
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: app-config
    - name: creds
      secret:
        secretName: db
        defaultMode: 0400

Three ways to use a ConfigMap, in order of how often you meet them:


# 1. one key as one environment variable
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL

# 2. every key as an environment variable
envFrom:
  - configMapRef:
      name: app-config

# 3. every key as a file in a folder
volumes:
  - name: config
    configMap:
      name: app-config
  • The first picks one key and lets you rename it. The most explicit, and the one to prefer.
  • envFrom pulls in everything. Short, but it hides what the app really depends on, and keys that are not valid variable names are skipped.
  • As a volume, each key becomes a file named after the key, containing its value. app.properties becomes the file /etc/app/app.properties. This is how you give nginx a real config file.

When the ConfigMap changes

How it is usedDoes a running Pod see the change?
environment variableNo. The environment is set once, when the container starts. Restart the Pod.
mounted as a volumeYes, eventually. The kubelet refreshes the files after a delay (up to about a minute or so), and the app must re-read them.
volume mounted with subPathNo. A subPath mount never updates.
immutable: true ConfigMapIt cannot change at all. You create a new one with a new name.

Even when files update, most programs read their config once at start. So the usual answer to "how do I apply a config change?" is to restart the Pods gently: kubectl rollout restart deployment/web (chapter 7). Helm users add a checksum of the ConfigMap to the Pod template, so a config change becomes a template change and triggers a rollout on its own.

Secrets

A Secret looks almost the same, and that is the first lesson: it is not magic. It is a ConfigMap with a different label, a few extra protections, and some different handling by tools.


kubectl create secret generic db --from-literal=password='s3cr3t-pw'
kubectl get secret db
kubectl get secret db -o jsonpath='{.data.password}'
kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
  • create secret generic makes a normal Secret (type Opaque).
  • get secret shows its name, type and number of keys, not the values.
  • The third command prints the stored value: a string of letters like czNjcjN0LXB3. That is the password, base64-encoded.
  • The fourth decodes it. Anyone who can run the third command can run the fourth.
This is the most important thing in the chapter

base64 is an encoding, not encryption. It exists so binary data fits in YAML. A Secret is not secret from anyone who can read it through the API, and by default it is stored unencrypted in etcd. The protection comes from who is allowed to read it (RBAC, chapter 16) and from optionally encrypting etcd at rest. Without those, a Secret is a ConfigMap with a misleading name.

Writing a Secret in YAML


apiVersion: v1
kind: Secret
metadata:
  name: db
type: Opaque
stringData:
  username: app
  password: s3cr3t-pw
  • stringData lets you write plain text. Kubernetes encodes it for you when it stores the object.
  • data is the stored form, where you must give base64 yourself. When you encode by hand, use echo -n 'value' | base64. Without -n, a newline is encoded into your password and logins fail in confusing ways.

Never commit this file. Anyone who can read the repository can read the password.

Environment variable or file?

Both work. For secrets, prefer files:

  • An environment variable is copied into every child process and shows up in crash dumps, debug pages and careless logging. The Linux handbook already said it: environment variables "are not automatically a secure secret store".
  • A file can have its permissions set. In the example above, defaultMode: 0400 makes each file readable only by its owner, the same chmod 400 you know.
  • Secret volumes are held in memory (tmpfs) on the node, not written to the node's disk.
  • Mounted Secrets also refresh when the Secret changes. Environment variables do not.

Doing better than the default

Linux you already know

  • A ConfigMap mounted as a volume is /etc for your app. You give the program a config file at a path, like /etc/nginx/nginx.conf, without baking it into the image.
  • Environment variables in a Pod are exactly the ones from the Linux handbook: export, printenv, inherited by child processes, gone when the process ends. kubectl exec app -- printenv shows them.
  • File permissions carry over: defaultMode is the chmod number. A Secret file readable by everyone is the chmod 777 mistake in new clothes.
  • echo -n matters here for the same reason it matters in scripts: a trailing newline is part of the data.
  • Passwords in /etc/shadow are stored hashed and readable only by root. A Kubernetes Secret is stored recoverably and readable by anyone with API access. That is a weaker default than the one Linux has had for decades, so you add the protections yourself.

Common mistakes

Common mistake

"Secrets are encrypted." They are base64-encoded. Decode them with one command. Real protection is RBAC, encryption at rest and an external store.

Common mistake

Committing a Secret manifest to git. Rotating the password does not remove it from history. Use Sealed Secrets, SOPS or an external store, and keep plain Secret YAML out of the repository.

Common mistake

"I changed the ConfigMap but the app still uses the old value." Environment variables do not update, and apps rarely re-read files. Restart the Pods: kubectl rollout restart.

Common mistake

Using subPath and expecting updates. A file mounted with subPath is copied once and never updated. It is handy for dropping one file into an existing folder, but not for live config.

Common mistake

The ConfigMap is in a different namespace. A Pod can only use ConfigMaps and Secrets from its own namespace. Create it where the Pod lives.

Common mistake

A missing ConfigMap, Secret or key. The Pod stays in CreateContainerConfigError and describe says which reference could not be found. The fix is in chapter 20: read the Events.

Common mistake

Encoding with echo instead of echo -n. The stored value ends in a newline, and "wrong password" errors follow.

This can break things

kubectl get secret NAME -o yaml prints the encoded values to your terminal, your shell scrollback and any screen share. kubectl describe secret is safer: it shows key names and sizes, not values. Be as careful with the first as with cat /etc/shadow.

Try it

Try it

On the kind cluster, in a scratch namespace. Use made-up passwords only.


# 1. a ConfigMap and a Secret
kubectl create namespace dev
kubectl create configmap app-config -n dev --from-literal=LOG_LEVEL=info
kubectl create secret generic db -n dev --from-literal=password='s3cr3t-pw'

# 2. see what is stored, and decode it
kubectl describe secret db -n dev
kubectl get secret db -n dev -o jsonpath='{.data.password}'
kubectl get secret db -n dev -o jsonpath='{.data.password}' | base64 -d

# 3. use both in a Pod (save the Pod from this chapter as app-pod.yaml)
kubectl apply -n dev -f app-pod.yaml
kubectl wait -n dev --for=condition=Ready pod/app --timeout=60s
kubectl logs -n dev app
kubectl exec -n dev app -- printenv LOG_LEVEL
kubectl exec -n dev app -- cat /etc/creds/password

# 4. change the ConfigMap, and watch what updates
kubectl patch configmap app-config -n dev -p '{"data":{"LOG_LEVEL":"debug"}}'
kubectl exec -n dev app -- printenv LOG_LEVEL          # still info: env vars do not change
kubectl exec -n dev app -- ls /etc/app                  # the file is there; its content updates after a delay

# 5. break it on purpose: ask for a key that does not exist
kubectl run broken -n dev --image=busybox:1.37 --overrides='{"spec":{"containers":[{"name":"broken","image":"busybox:1.37","command":["sleep","60"],"env":[{"name":"X","valueFrom":{"configMapKeyRef":{"name":"app-config","key":"NOPE"}}}]}]}}'
kubectl get pod broken -n dev
kubectl describe pod broken -n dev | tail -8

# 6. clean up
kubectl delete namespace dev

What to look for:

  • Step 2: describe hides the value. The jsonpath version shows it encoded. base64 -d reveals it. That demonstrates the point of the chapter.
  • Step 3: the log shows LOG_LEVEL and DB_PASSWORD from the environment, and the files under /etc/app and /etc/creds. ls -lL shows the Secret file's mode as -r--------.
  • Step 4: the environment variable stays info.
  • Step 5: the Pod sits in CreateContainerConfigError, and the Events name the missing key.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between a ConfigMap and a Secret?

Both hold key-value data that Pods read as environment variables or mounted files, with the same 1 MiB limit. A ConfigMap is for ordinary configuration. A Secret is for sensitive data. Kubernetes handles it a bit more carefully: it isn't shown by describe, and mounted Secrets use in-memory storage. But by default a Secret is only base64-encoded and stored unencrypted in etcd, so the real protection is RBAC, encryption at rest, or an external secret store.

Are Kubernetes Secrets secure?

Not on their own. base64 is encoding, not encryption, so anyone who can read the Secret through the API can decode it, and by default it sits unencrypted in etcd. To make them reasonably safe I restrict RBAC so few identities can read Secrets, turn on encryption at rest for etcd, avoid committing them to git, and for serious setups use an external manager like Vault through the External Secrets Operator or a CSI driver, which also gives me rotation and audit.

Environment variables or mounted files: which would you use, and why?

For non-sensitive config either is fine, and env vars are simpler. For secrets I prefer files. Env vars are inherited by child processes and can leak into logs and crash dumps, and they can't be updated without a restart. A mounted file can have restrictive permissions, lives in memory, and is refreshed when the Secret changes. The trade-off is the app has to read a file.

I updated a ConfigMap. How do I get my Pods to use it?

It depends how it's consumed. Environment variables never update in a running Pod, so I need to restart it. Mounted files do refresh after a delay, unless I used subPath, but most apps only read config at startup anyway. So I normally run kubectl rollout restart on the Deployment. A cleaner approach is to put a hash of the ConfigMap in the Pod template, which Helm can do, so any config change is a template change and rolls out automatically.

How would you handle secrets in a GitOps workflow?

I wouldn't commit plain Secret manifests. Either I commit encrypted ones, using Sealed Secrets or SOPS, so only the cluster or my key can decrypt them, or I commit a reference and let an operator like External Secrets pull the real value from Vault or a cloud secret manager into a Kubernetes Secret at runtime. The second keeps the secret out of git entirely and makes rotation easier.

Habits worth keeping

Habits

Keep config out of the image. Say "base64 is not encryption" before anyone else does. Mount secrets as files with tight permissions. Limit who can read Secrets. Never commit plain Secret YAML. Restart Pods after a config change. And use describe, not get -o yaml, when you only want to look.
