Storage: volumes, PV, PVC

What happens to data when a Pod dies

Section 12

A container's filesystem disappears when the container does. That is fine for a web server and fatal for a database. Kubernetes solves it with a small chain of objects: volumes, PersistentVolumes, claims and StorageClasses. The names are awkward the first time. The idea behind them is simple: ask for storage, do not build it.

The problem

Three situations, in order of how bad they get:

  • Your app writes a file into its own filesystem. The container restarts, and the file is gone.
  • You want two containers in one Pod to share a folder. That needs a volume.
  • You run a database. The Pod is deleted and recreated on another node. The data must follow, and the database should not need to know which disk or which cloud it is on.

The last one is the hard one. Developers want to say "I need 10 GB that survives". An administrator knows how to provide that on this particular cluster. Kubernetes puts a request form between them.

Key idea

A PersistentVolumeClaim (PVC) is an app's request for storage. A PersistentVolume (PV) is a piece of real storage. A StorageClass says how to create one on demand. The app asks with a claim, the cluster supplies a volume, and the data outlives the Pod.

Think of it as

Parking. The PV is a real space. The PVC is a permit request: "one space, big enough for a van". The StorageClass is the garage operator who builds a space when asked.

PV

A real disk or directory, registered with the cluster. It belongs to the cluster, not to a namespace.

PVC

A claim made by an app, in its namespace: size, access mode, class. Kubernetes binds it to a matching PV.

StorageClass

A recipe for creating PVs automatically (dynamic provisioning), usually via a CSI driver for your cloud or storage system.

Pod→ uses →PVC (request)→ bound to →PV (real storage)← made by ←StorageClass

Persistent storage

1. The claim


apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi


spec:
  accessModes:
    - ReadWriteOnce      who may mount it, and how (see the table below)
  resources:
    requests:
      storage: 1Gi       at least this much
  (storageClassName:)    which StorageClass to ask. Leave out for the cluster's default.

That is all an app team writes. No disk type, no cloud name, no device path.

2. Using it in a Pod


apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "date >> /data/log.txt; cat /data/log.txt; sleep 3600"]
      volumeMounts:
        - name: storage
          mountPath: /data
  volumes:
    - name: storage
      persistentVolumeClaim:
        claimName: data

The Pod refers to the claim by name. The container sees an ordinary folder at /data.

3. What happens behind the scenes

  1. You create the PVC. Kubernetes looks for a PV that fits, or asks the StorageClass's provisioner to make one. That is dynamic provisioning.
  2. The PV is created and bound to your claim. One claim, one volume.
  3. You start a Pod that uses the claim. The scheduler places it, and the kubelet attaches and mounts the volume on that node.
  4. The Pod dies. The claim, the volume and the data stay. A new Pod that mentions the same claim gets the same data.

kubectl get storageclass
kubectl get pvc
kubectl get pv
kubectl describe pvc data
  • get storageclass lists the classes. One is marked (default).
  • get pvc shows STATUS: Pending (waiting) or Bound (has a volume).
  • get pv shows the volumes, who they are bound to, and the reclaim policy. Note it has no namespace.
  • describe pvc has the events when a claim is stuck.
Key idea

Many StorageClasses use volumeBindingMode: WaitForFirstConsumer. The claim stays Pending on purpose until a Pod uses it, because the volume should be created where the Pod will run. A Pending PVC with no Pod yet is normal, not a fault. kind's default class behaves this way.

The StorageClass


apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true


provisioner: ...                who creates the storage: a CSI driver (here, an AWS example)
parameters: type: gp3           options only that driver understands
reclaimPolicy: Delete           what happens to the data when the claim is deleted
volumeBindingMode:              Immediate = create at once; WaitForFirstConsumer = wait for a Pod
allowVolumeExpansion: true      the claim may be made bigger later

The provisioner line above is an example for one cloud. Yours depends on your platform: a cloud's CSI driver, Ceph, OpenEBS, or a local-path provisioner on a laptop. CSI (Container Storage Interface) is the standard plug-in layer. The old built-in cloud volume types have been removed from Kubernetes in favour of CSI drivers.

What happens to the data afterwards: reclaim policy

PolicyWhen the PVC is deleted
Deletethe PV and the real disk are deleted. This is the default for dynamically created volumes.
Retainthe PV is kept, in a Released state, with the data intact, for an administrator to deal with.

Growing a volume

If the StorageClass allows expansion, edit the claim and raise the number. You can only grow, never shrink.


kubectl patch pvc data -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
kubectl get pvc data

Linux you already know

  • A mounted volume is a mount point, the same idea as /mnt or /media in the Linux filesystem chapter. Inside a Pod, df -h /data shows a separate filesystem mounted there, and mount | grep /data shows the details.
  • lsblk and df -h from the handbook's "what the kernel manages" section work on a node to see real disks.
  • Think of a PV as a disk you would add to /etc/fstab, and a PVC as the entry that says "mount me one of those at this path", with Kubernetes doing the mount for you.
  • Permissions still apply. If the app runs as a non-root user and the volume is owned by root, writes fail with Permission denied. securityContext.fsGroup makes Kubernetes set the volume's group ownership so the app's group can write. It is chgrp and chmod g+w, done at mount time.
  • A disk is not a backup. The Linux handbook's advice about backups and snapshots before upgrades applies unchanged. A PV is one copy of the data.

Common mistakes

Common mistake

"My data is safe in an emptyDir." It survives a container restart but not the Pod being deleted or moved. For anything you need tomorrow, use a PVC.

Common mistake

"My PVC is Pending, so storage is broken." If the class uses WaitForFirstConsumer, it stays Pending until a Pod uses it. Create the Pod first. If a Pod uses it and it is still Pending, describe pvc usually shows no default StorageClass or no provisioner.

Common mistake

A Deployment with several replicas sharing one RWO claim. The Pods land on different nodes, but an RWO disk attaches to one node. Some Pods hang in ContainerCreating with a multi-attach error. For one volume per replica, use a StatefulSet (chapter 14). For one volume shared by many, you need an RWX-capable class.

Common mistake

hostPath for real data. It works until the Pod moves to another node and finds an empty folder. It also gives the Pod access to the node's filesystem.

Common mistake

Mixing up PV and PVC. An app only ever writes a PVC. A PV is the cluster's side. Also, a PVC is namespaced, a PV is not.

Common mistake

"Permission denied" on the mounted folder. A non-root app on a root-owned volume. Set fsGroup, or fix ownership with an init container.

Common mistake

Trying to shrink a claim. Only growing is supported, and only if allowVolumeExpansion is true.

This can break things

With the default reclaimPolicy: Delete, deleting a PVC deletes the underlying disk and its data. So does deleting the namespace that holds it. For anything valuable, use a class with Retain, and take backups or snapshots. Check kubectl get pv for the policy before you delete a claim.

Try it

Try it

On the kind cluster, which ships with a default StorageClass called standard. Save the PVC as data-pvc.yaml and the Pod as writer-pod.yaml.


# 1. what classes exist? which is the default?
kubectl create namespace dev
kubectl get storageclass

# 2. create the claim, and look at it BEFORE any Pod uses it
kubectl apply -n dev -f data-pvc.yaml
kubectl get pvc -n dev
kubectl describe pvc data -n dev | tail -5

# 3. start a Pod that uses it
kubectl apply -n dev -f writer-pod.yaml
kubectl wait -n dev --for=condition=Ready pod/writer --timeout=90s
kubectl get pvc,pv -n dev
kubectl logs -n dev writer

# 4. the data outlives the Pod
kubectl delete pod writer -n dev
kubectl apply -n dev -f writer-pod.yaml
kubectl wait -n dev --for=condition=Ready pod/writer --timeout=90s
kubectl logs -n dev writer                 # two lines now: the old and the new

# 5. look at the mount like a Linux admin
kubectl exec -n dev writer -- df -h /data
kubectl exec -n dev writer -- ls -l /data

# 6. the dangerous bit: delete the claim, then look at the volume
kubectl delete pod writer -n dev
kubectl get pv
kubectl delete pvc data -n dev
kubectl get pv                             # gone, because the reclaim policy is Delete

# 7. clean up
kubectl delete namespace dev

What to look for:

  • Step 2: the claim is Pending, with an event saying it waits for a first consumer. That is normal for this class.
  • Step 3: now Bound, and a PV has appeared that you never created.
  • Step 4: the log has two timestamps. A new Pod, the same data.
  • Step 5: df shows /data as its own mount, not part of the container's root filesystem.
  • Step 6: the PV disappears with the claim. That is Delete in action.

Interview questions

Interview

Click a question, answer out loud first, then check.

Explain PV, PVC and StorageClass.

A PersistentVolume is a piece of real storage in the cluster, and it isn't namespaced. A PersistentVolumeClaim is an app's request for storage in its namespace: a size, an access mode and optionally a class. Kubernetes binds a claim to a matching PV. A StorageClass defines how to create PVs on demand, through a provisioner, usually a CSI driver. So developers just write a claim, and the platform provides the actual disk. That separation is the point.

What is dynamic provisioning?

When I create a PVC that names a StorageClass, or uses the default one, the class's provisioner creates the underlying disk and the PV automatically and binds it to the claim. Without it, an administrator would have to pre-create PVs by hand and hope they match. With WaitForFirstConsumer, creation is delayed until a Pod is scheduled, so the volume is made in the right zone or node.

What are the access modes, and why does it matter?

ReadWriteOnce means one node can mount it read-write, ReadWriteOncePod restricts it to a single Pod, ReadOnlyMany lets many nodes read, and ReadWriteMany lets many nodes write. It matters because most cloud block disks are RWO. So a Deployment with several replicas on different nodes can't share one such claim. Some Pods hang trying to attach the disk. For per-replica disks I use a StatefulSet, and for shared writable storage I need a class that supports RWX, like NFS or CephFS.

What happens to the data when I delete a PVC?

It depends on the reclaim policy. With Delete, which is the default for dynamically provisioned volumes, the PV and the underlying disk are deleted along with the data. With Retain, the PV stays in a Released state with the data intact until an admin deals with it. For important data I use a class with Retain and also take snapshots or backups, because deleting the namespace deletes the claim too.

What's the difference between an emptyDir and a PVC?

An emptyDir is created when the Pod starts and deleted when the Pod goes away. It survives container restarts but not a replaced Pod, so it's for scratch data, caches, or sharing files between containers. A PVC is backed by a PersistentVolume that exists independently of any Pod, so the data survives Pod deletion and rescheduling. I use emptyDir for temporary data and PVCs for anything I need to keep.

Habits worth keeping

Habits

Ask for storage with a claim, never by disk name. Know your StorageClass: its reclaim policy, binding mode and access modes. Remember that most block storage is RWO. Use StatefulSets for databases. Check kubectl get pv before deleting a claim. Back up, because a volume is not a backup. And say it: "emptyDir is scratch, a PVC is a promise."
