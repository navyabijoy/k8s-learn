Conclusion

What you can explain now

Section 23

You started with a question people argue about, "why does Kubernetes exist?", and ended with a cluster you can run apps on, secure, watch and repair. The commands did not change as the chapters went on. get lists, describe explains, apply declares. Controllers compare what you want with what exists, and close the gap. This last chapter puts it together, and gives you a way to say all of it out loud.

What you can explain now

  • Why Kubernetes exists: containers solve packaging, and something must decide where they run and keep them running (chapter 1).
  • Say what a container is: a Linux process with namespaces and cgroups, started from an image (2).
  • Name the parts of a cluster: API server, etcd, scheduler, controllers, kubelet, runtime. And walk through what happens on kubectl apply (3).
  • Build a local cluster and know why a laptop cluster is not production (4).
  • Use kubectl, read YAML, tell apply from create, and know which cluster you are talking to (5).
  • Explain a Pod: containers that share a network and storage, and are mortal (6).
  • Run Deployments, roll them out, and roll them back (7).
  • Find things with labels, and separate them with namespaces (8).
  • Give Pods a stable address with Services and DNS, and debug an empty one (9).
  • Route outside traffic with Ingress or Gateway API, and say why one is frozen and ingress-nginx is retired (10).
  • Keep config out of images with ConfigMaps and treat Secrets honestly: base64 is not encryption (11).
  • Keep data with PVs, PVCs and StorageClasses (12).
  • Set probes, requests and limits, and explain self-healing as kubelet plus controllers (13).
  • Pick between StatefulSets, DaemonSets, Jobs and CronJobs (14).
  • Steer Pods with taints, tolerations and affinity, and drain a node safely (15).
  • Grant exactly the right access with RBAC and ServiceAccounts (16).
  • Describe the Pod network, CNI, and NetworkPolicy, including the policy that does nothing (17).
  • Package and upgrade with Helm (18).
  • Explain CRDs, operators and the reconcile loop (19).
  • Debug with describe, logs, events in a fixed order (20).
  • Collect logs and metrics, and say what Prometheus does (21).
  • Say how MicroK8s, Canonical Kubernetes, Charmed Kubernetes and Juju relate (22).

Say it in one sentence

In an interview you get seconds, not paragraphs. Each of these should come out in one breath. Cover the right column and test yourself.

AskOne sentence
What is Kubernetes?Software that runs containers across many machines, keeping what is running equal to what you declared.
What is a Pod?One or more containers that share a network and storage and are scheduled together.
Deployment vs ReplicaSet?A Deployment manages rollouts by creating a ReplicaSet per version, and each ReplicaSet keeps N Pods running.
What does a Service do?Gives a set of Pods one stable address and name, finding them by label and only using the ready ones.
Ingress vs Service?A Service exposes Pods, an Ingress routes HTTP by host and path to Services, and needs a controller to do anything.
ConfigMap vs Secret?Same shape; a Secret is only base64-encoded, so its safety comes from RBAC, encryption at rest, or an external store.
PV, PVC, StorageClass?A PV is real storage, a PVC is a request for it, and a StorageClass says how to make it on demand.
Liveness vs readiness?Liveness failing restarts the container; readiness failing only removes the Pod from Services.
Request vs limit?Requests are what the scheduler reserves; limits are what the kernel enforces: CPU is throttled, memory is killed.
Taint vs affinity?Taints on nodes push Pods away; affinity on Pods pulls them toward nodes; a toleration only permits.
Role vs ClusterRole?A Role is permissions in one namespace, a ClusterRole is cluster-wide, and bindings attach either to subjects.
What is CNI?The standard the runtime uses to ask a plugin to give each Pod an IP and connect it to the network.
NetworkPolicy catch?It is only enforced if your network plugin supports it, so you test that a deny actually denies.
Helm vs operator?Helm installs software from templates; an operator keeps running it, with application-specific knowledge.
What is the reconcile loop?Compare desired state to actual state, close the gap, repeat, so the system heals itself.
Pod stuck Pending?Run describe and read the scheduler's event: usually resources, taints, selectors or an unbound claim.
CrashLoopBackOff?The container keeps exiting; read logs --previous and the exit code.
Control plane down?Running Pods keep running, but nothing changes: no scheduling, scaling, or new self-healing.
Canonical's Kubernetes?Three distributions: MicroK8s as a snap, Canonical Kubernetes as a snap or charm, and Charmed Kubernetes through Juju.

How to answer out loud

Every chapter followed the same shape. It is also a good shape for a spoken answer. Use it when you are asked "explain X":

  1. The problem. "Pod IPs change, so how does one app find another?"
  2. The idea, in one sentence. "A Service is a stable virtual IP and name that selects Pods by label."
  3. One small example. "A Service called web with selector: app=web and port 80."
  4. The common mistake. "People forget the selector must match the Pod labels, so it has no endpoints."
  5. The Linux you know. "It is like a reverse proxy, built from kernel rules, rebuilt from labels."

That is about forty seconds. It shows you understand why, not only what. And if you do not know something, say the path you would take: "I'd check kubectl explain", "I'd read the events first". Knowing how to find out is a real skill.

Key idea

No single object is clever. The skill is knowing which small object solves which small problem, and that they connect through labels, names and the same API.

Habits worth keeping

Habits

Check the context before you change anything. Pin image tags and chart versions. Declare with apply, keep files in git, and diff before you apply. Give every app a readiness probe and honest requests. Use Deployments, not bare Pods. Start closed with RBAC and NetworkPolicy, and test that a deny denies. Never commit Secrets, and say "base64 is not encryption". Go describe, logs, events, in that order. Back up etcd and your volumes. And when you do not know, say how you would find out.

The next time something breaks, you already have a path: get the state, describe for why, logs for what the app said, then events and exec. The next time someone asks "what is Kubernetes?", you already have a sentence.

Kubernetes will keep feeling large. That is normal. The loop still runs: look at what you want, look at what you have, close the gap. The API server is still the only front door. The kubelet is still a Linux service on a Linux machine. Everything in this handbook is a way of looking at that same system, clearly enough to change it on purpose.

Try it

Try it

Apply the capstone to your kind cluster, prove each part works, then break one thing at a time and fix it with the chapter 20 path. Save the YAML above as capstone.yaml.


kubectl config current-context
kubectl apply -f capstone.yaml
kubectl rollout status deployment/web -n shop
kubectl get all,pdb,networkpolicy,configmap,secret -n shop

# who is where, and how are they spread?
kubectl get pods -n shop -o wide

# does the Service work for an allowed client?
kubectl run client -n shop --image=curlimages/curl --labels=role=client -- sleep 3600
kubectl wait -n shop --for=condition=Ready pod/client --timeout=60s
kubectl exec -n shop client -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web

# and for a stranger? (blocked only if your CNI enforces NetworkPolicy)
kubectl run stranger -n shop --image=curlimages/curl -- sleep 3600
kubectl wait -n shop --for=condition=Ready pod/stranger --timeout=60s
kubectl exec -n shop stranger -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web

# is the secret really a file, readable only by the app's group (0440)?
kubectl exec -n shop deploy/web -- ls -lL /etc/web-secret
kubectl exec -n shop deploy/web -- id

# break and fix: a bad image
kubectl set image deployment/web web=nginxinc/nginx-unprivileged:does-not-exist -n shop
kubectl rollout status deployment/web -n shop --timeout=30s
kubectl get pods -n shop
kubectl describe pod -n shop -l app=web | tail -20
kubectl rollout undo deployment/web -n shop

# try to drain a node and watch the PDB protect you
kubectl drain handbook-worker --ignore-daemonsets --delete-emptydir-data
kubectl uncordon handbook-worker

# clean up
kubectl delete namespace shop

What to look for:

  • The Pods spread over different nodes, and run as a non-root user (id prints a UID that is not 0).
  • client gets 200. stranger gets 000 if your plugin enforces policy, 200 if it does not. Either way you now know something true about your cluster.
  • The Secret file has mode -r--r-----: readable by its owner and group, not by everyone. id shows group 101 among the app's groups, which is what fsGroup added.
  • The bad image leaves the old Pods serving while the new one fails. You found the cause with describe, and rollout undo fixed it.
  • The drain evicts Pods one at a time, never dropping below the budget.

Interview questions

Interview

The big, joined-up ones. Click, answer out loud first, then check.

Walk me through what happens from a user typing a URL to a Pod answering.

DNS resolves the name to the entry point, usually a cloud load balancer. That sends the request to the Ingress or Gateway controller, which is a proxy running in Pods inside the cluster. It terminates TLS and matches the host and path against its rules to pick a Service. The Service has a virtual IP, and kube-proxy rules, or the CNI, on that node rewrite the destination to one ready Pod from its EndpointSlice. The Pod network, built by the CNI, carries the packet to that Pod, possibly across nodes, and the container answers. NetworkPolicies may allow or block it at the Pod.

How would you deploy a stateless web app so it's reliable and secure?

A Deployment with at least three replicas, spread across nodes with topology spread constraints, and a rolling update strategy with maxUnavailable zero. Startup, readiness and liveness probes, and memory and CPU requests with a memory limit. A Service in front, and an Ingress or Gateway for outside traffic with TLS. Config in a ConfigMap and secrets from a proper store. A PodDisruptionBudget so drains can't take it down, and an HPA if load varies. Security: its own ServiceAccount with no extra rights, non-root, no privilege escalation, dropped capabilities, and a default-deny NetworkPolicy with only the needed allows.

How would you explain Kubernetes to someone who isn't technical?

Imagine you run lots of small programs on lots of computers. Kubernetes is the manager that decides which computer runs which program, restarts the ones that crash, adds more copies when it gets busy, and updates them without stopping the service. You tell it what you want, three copies of this program, always, and it keeps checking and fixing until reality matches.

What are the most important things to secure in a cluster?

Access to the API: strong authentication and least-privilege RBAC, with very few cluster-admins. Secrets: restrict who can read them, encrypt etcd at rest, and keep them out of git. The workloads: non-root, no privilege escalation, Pod Security Admission enforced per namespace. The network: default-deny NetworkPolicies on a CNI that actually enforces them. And the supply chain: pinned, scanned images from trusted registries. Plus keeping Kubernetes and nodes patched, and audit logging so I can see what happened.

What would you do in your first week joining a team that runs Kubernetes?

Learn the shape of the platform before changing it: which distribution and version, how clusters are created and upgraded, which CNI, ingress and storage, and how deploys happen, whether GitOps or pipelines. I'd read the runbooks and recent incidents, check how monitoring and alerting work, and find out how access is granted. Then I'd pick up a small change in a non-production cluster and follow it all the way through to production, asking questions as I go.
