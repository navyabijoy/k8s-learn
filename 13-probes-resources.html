Probes, requests, limits, self-healing

How Kubernetes decides a Pod is alive, ready and big enough

Section 13

"Running" does not mean "working". And one greedy app can starve its neighbours. This chapter covers the three tools Kubernetes gives you for both problems: probes, requests and limits. Then it puts them together and explains what self-healing really is, because it is not magic.

The problem

Three real situations:

  • Your app starts, opens its port, and then deadlocks. The process is alive. Every request hangs. Kubernetes sees a running container and is happy.
  • Your app takes 40 seconds to warm up. For those 40 seconds the Service sends it traffic and users get errors.
  • Another team's app eats all the memory on a node. Yours gets killed for no fault of its own.

In each case Kubernetes needs to be told something about your app that it cannot guess.

Key idea

Probes tell Kubernetes whether your app is alive and ready. Requests tell it how much room to reserve. Limits tell it the most your app may take.

Liveness

"Is it stuck?" If this fails, the kubelet kills the container and restarts it.

Readiness

"Can it take traffic right now?" If this fails, the Pod is taken out of its Services. It is not restarted.

Startup

"Has it finished starting?" Switches off the other two until it passes, so slow starters are not killed.

Requests and limits

Requests are for the scheduler: reserve this much. Limits are for the kernel: never more than this.

Probes

Think of a doctor's checks. A startup probe asks "are you out of bed yet?". A readiness probe asks "are you fit to see patients?". A liveness probe asks "do you still have a pulse?". Different questions, different consequences.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          startupProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 10
            failureThreshold: 3
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              memory: 128Mi

Break one probe apart


livenessProbe:
  httpGet:                 how to check: ask over HTTP
    path: /                which URL
    port: 80               which port
  periodSeconds: 10        check every 10 seconds
  failureThreshold: 3      3 failures in a row = failed
  (timeoutSeconds: 1)      a check that takes longer than this counts as a failure
  (initialDelaySeconds: 0) wait this long before the first check
  (successThreshold: 1)    successes in a row to count as healthy again

The ones in brackets are defaults. With these numbers, a stuck app is declared dead after about 30 seconds (3 failures, 10 seconds apart).

Four ways to ask


httpGet:                    # success = any status from 200 to 399
  path: /healthz
  port: 8080

tcpSocket:                  # success = the port accepts a connection
  port: 5432

exec:                       # success = the command exits with 0
  command: ["cat", "/tmp/healthy"]

grpc:                       # success = the gRPC health service says SERVING
  port: 9090
  • httpGet is the usual choice for web apps.
  • tcpSocket is for things that are not HTTP, like a database. It only proves the port is open.
  • exec runs a command inside the container, like kubectl exec, and checks the exit code. Exit 0 is success, as it is everywhere in Linux.
  • grpc uses the standard gRPC health-check protocol.

What each failure does

ProbeWhen it failsEffect on traffic
Startuppast failureThresholdcontainer killed and restarted. Until it succeeds, liveness and readiness do not run.
Livenesspast failureThresholdcontainer killed and restarted (the Pod stays, the container restarts).
ReadinessimmediatelyPod removed from Service endpoints. Container keeps running. It returns when the probe passes again.

The startup probe, in numbers

The startup probe above allows up to 5 seconds × 30 = 150 seconds for the app to come up. Only then, or as soon as it succeeds, do the other two start. Without it, you would have to guess an initialDelaySeconds that is long enough for the slowest start and still lets the liveness probe catch real problems later.

This can break things

Never let a liveness probe check something outside the container: a database, a cache, another service. If that dependency has an outage, every Pod fails liveness, every Pod restarts, and a small outage becomes a big one. Put dependency checks in readiness, where the worst outcome is "take me out of rotation". Liveness should only answer "is this process itself stuck?"

Requests and limits


resources:
  requests:
    cpu: 250m
    memory: 128Mi
  limits:
    cpu: "1"
    memory: 256Mi

Key idea

CPU is compressible: if you want too much, you wait. Memory is not: if you want too much, you die. That one fact explains most resource surprises.

How the scheduler uses requests

Each node has an allocatable amount of CPU and memory (what is left after the OS and Kubernetes itself). The scheduler adds up the requests of the Pods already on a node and only places a new Pod if its requests fit in what remains. It looks at requests, not at what Pods actually use right now.


kubectl describe node <node-name>

Look for the Allocated resources section. It shows the sum of requests and limits against the node's capacity. When a Pod sits in Pending with an event like 0/3 nodes are available: 3 Insufficient cpu, this is where the sum ran out.

QoS classes: who is evicted first

From your requests and limits, Kubernetes gives every Pod a Quality of Service class. When a node runs low on memory, it decides whom to evict by class.

ClassHow you get itEvicted
Guaranteedevery container has CPU and memory requests and limits, and requests equal limitslast
Burstableat least one request or limit set, but not Guaranteedin the middle
BestEffortno requests or limits at allfirst
 

kubectl get pod web-xyz -o jsonpath='{.status.qosClass}'

Every Pod you ran without a resources block, including the chapter 6 Pod, is BestEffort. That is fine for a lab and a bad idea for production.

How self-healing actually works

"Kubernetes is self-healing" is true, but there is no healer. There are several small loops, each watching for one kind of failure. Know which loop handles which.

What failsWho noticesWhat happens
A container crashesthe kubelet, on that nodeRestarts it in place, with growing delays. Repeated crashes show as CrashLoopBackOff.
A container hangs (liveness fails)the kubeletKills and restarts that container.
A Pod is not ready (readiness fails)the kubelet reports it, the endpoints controller reactsPod removed from Service endpoints. No restart.
A Pod is deleted or evictedthe ReplicaSet controllerCreates a new Pod. The scheduler picks a node.
A node stops reportingthe node lifecycle controllerMarks the node NotReady and taints it. Pods on it are evicted after a grace period (300 seconds by default), then replaced elsewhere.
Load growsthe HorizontalPodAutoscaler (if you made one)Changes the Deployment's replica count. It needs CPU requests set to work with CPU percentages.
container problem→kubelet fixes it on the node·Pod or node problem→controllers replace Pods elsewhere

Notice the split. The kubelet handles anything inside a Pod on its own node. The controllers handle anything that needs a Pod to appear somewhere else. A bare Pod gets the first kind of healing only.

Shutting down politely

When a Pod is deleted, two things start at about the same time: the Pod is removed from Service endpoints, and its containers get SIGTERM. Both take a moment to spread. For a short time, traffic can still arrive at a Pod that is already shutting down.


spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: nginx
      image: nginx:1.27
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "5"]
  • terminationGracePeriodSeconds is how long the Pod gets between SIGTERM and SIGKILL. Default 30. Same as kill then kill -9 from the Linux handbook.
  • preStop runs before SIGTERM. A short sleep gives the endpoint removal time to spread, so the app is not asked to stop while traffic is still arriving. Your app must also handle SIGTERM and finish its current requests.

Linux you already know

  • Limits are cgroups. The memory limit becomes a file the kernel reads. Inside a container with cgroup v2 you can see it: cat /sys/fs/cgroup/memory.max and cat /sys/fs/cgroup/cpu.max.
  • OOM kill is the Linux kernel's own out-of-memory killer. The container exits with code 137, which is 128 plus signal 9 (SIGKILL). It is kill -9 from the kernel, with no warning to your app.
  • CPU throttling is the kernel's CFS scheduler handing your cgroup a time quota. When you use it up, your processes wait for the next period. That is why throttled apps get slow rather than die.
  • Liveness is what you would do with systemctl is-active in a loop. exec probes use the exit-code rule from shell scripts: 0 is success.
  • Evicting under memory pressure is the same trade-off as choosing which process to sacrifice when a Linux box runs out of RAM. QoS classes make that choice predictable.

Common mistakes

Common mistake

A liveness probe that is too eager on a slow-starting app. It fails during boot, the container is killed, it starts again, fails again. Forever. Add a startupProbe instead of just raising initialDelaySeconds.

Common mistake

No readiness probe. Rolling updates (chapter 7) and Services (chapter 9) treat a Pod as ready the moment its container starts. Traffic then reaches an app that is still loading.

Common mistake

The same endpoint for liveness and readiness. They answer different questions. A busy app can be "not ready right now" while very much alive. If both probes fail on the same check, a busy spell causes restarts.

Common mistake

No requests at all. Pods are BestEffort, so the scheduler packs them onto whichever node and they are the first to be evicted. Also, CPU-based autoscaling cannot compute a percentage of a request that is not there.

Common mistake

A CPU limit that is too low. The app does not crash, it just gets slow, and you chase latency for hours. If you set a CPU limit, set it generously and watch for throttling. Many teams set CPU requests but no CPU limit.

Common mistake

A memory limit below what the runtime needs. A Java app whose heap is bigger than the container's memory limit is OOMKilled again and again. Leave headroom above the heap for the rest of the process.

Common mistake

"RESTARTS 12 means my app crashes." It means the container was restarted 12 times. The reason can be a crash, an OOM kill, or a failing liveness probe. kubectl describe pod shows Last State and the reason.

Common mistake

M versus Mi. 128M is 128,000,000 bytes. 128Mi is 134,217,728. Use Mi and Gi.

Try it

Try it

Three small experiments on the kind cluster. Do them in a scratch namespace.

Experiment 1: readiness controls traffic


apiVersion: v1
kind: Pod
metadata:
  name: ready-demo
  labels:
    app: ready-demo
spec:
  containers:
    - name: app
      image: busybox:1.37
      command: ["sh", "-c", "sleep 3600"]
      readinessProbe:
        exec:
          command: ["cat", "/tmp/ready"]
        periodSeconds: 3


kubectl create namespace dev
kubectl apply -n dev -f ready-demo.yaml
kubectl get pod ready-demo -n dev            # READY 0/1: the file does not exist yet
kubectl exec -n dev ready-demo -- touch /tmp/ready
kubectl get pod ready-demo -n dev --watch    # within a few seconds: READY 1/1
kubectl exec -n dev ready-demo -- rm /tmp/ready
kubectl get pod ready-demo -n dev            # back to 0/1, and it was never restarted

Experiment 2: liveness restarts the container


apiVersion: v1
kind: Pod
metadata:
  name: live-demo
spec:
  containers:
    - name: app
      image: busybox:1.37
      args:
        - /bin/sh
        - -c
        - touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600
      livenessProbe:
        exec:
          command: ["cat", "/tmp/healthy"]
        initialDelaySeconds: 5
        periodSeconds: 5


kubectl apply -n dev -f live-demo.yaml
kubectl get pod live-demo -n dev --watch     # after about 40 seconds, RESTARTS goes to 1
kubectl describe pod live-demo -n dev        # Events: "Liveness probe failed ... Killing"

Experiment 3: the memory limit kills


apiVersion: v1
kind: Pod
metadata:
  name: oom-demo
spec:
  containers:
    - name: stress
      image: polinux/stress
      command: ["stress"]
      args: ["--vm", "1", "--vm-bytes", "250M", "--vm-hang", "1"]
      resources:
        requests:
          memory: 50Mi
        limits:
          memory: 100Mi


kubectl apply -n dev -f oom-demo.yaml
kubectl get pod oom-demo -n dev --watch      # STATUS flips to OOMKilled, then CrashLoopBackOff
kubectl describe pod oom-demo -n dev         # Last State: Terminated, Reason: OOMKilled, Exit Code: 137
kubectl get pod oom-demo -n dev -o jsonpath='{.status.qosClass}'   # Burstable

kubectl delete namespace dev

What to look for: in experiment 1 the Pod was never restarted, just made unready. In experiment 2 the restart count rose. In experiment 3, Exit Code: 137 is the kernel's SIGKILL, and the class is Burstable because requests and limits are set but not equal.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between liveness, readiness and startup probes?

Liveness asks "is this container stuck?". If it fails, the kubelet restarts the container. Readiness asks "can it take traffic now?". If it fails, the Pod is taken out of Service endpoints but not restarted. Startup asks "has it finished booting?". Until it passes, the other two are disabled, so slow-starting apps don't get killed. They answer different questions, so they usually check different things.

Why shouldn't a liveness probe check the database?

Because when the database has a problem, every Pod would fail liveness at once, and the kubelet would restart all of them. Restarting doesn't fix a database. It just adds load and turns a partial outage into a total one. Dependency checks belong in readiness, where the effect is only that the Pod stops getting traffic. Liveness should only check the process itself.

What's the difference between a request and a limit?

A request is what the scheduler reserves when it picks a node. It adds up requests on each node and only places the Pod if they fit. A limit is the maximum the container may use, enforced by the kernel through cgroups. Over the CPU limit, the container is throttled. Over the memory limit, it's OOM-killed. So CPU is compressible and memory isn't.

Explain the QoS classes.

Kubernetes derives them from requests and limits. Guaranteed means every container has CPU and memory requests equal to limits. Burstable means some requests or limits are set but not that. BestEffort means none are set. When a node is short of memory, it evicts BestEffort Pods first, then Burstable ones over their requests, and Guaranteed last. So for important workloads I set requests, and often make them equal to limits for memory.

A node dies. How long until its Pods run elsewhere, and who does it?

The kubelet stops reporting, and after a grace period the node lifecycle controller marks the node NotReady and taints it. Pods get a default toleration for that taint of 300 seconds, so after about five minutes they are evicted. The ReplicaSet controller sees fewer Pods than it wants and creates new ones, and the scheduler places them on healthy nodes. If I need it faster I can lower the toleration seconds on the Pods, at the risk of reacting to brief network blips.

Habits worth keeping

Habits

Give every app a readiness probe, and a startup probe if it boots slowly. Keep liveness simple and local. Set memory requests and limits, and CPU requests. Remember that CPU slows you down and memory kills you. Read Last State in describe before blaming the app. And explain self-healing as what it is: the kubelet for the container, controllers for the Pod and node.
