Containers in five minutes

Image vs container, and what Linux is doing underneath

Section 02

You know Docker basics, so this chapter is a fast check, with the Linux underneath shown plainly. The one sentence to leave with: a container is a Linux process in a fenced-off room, started from a read-only image. If you can say what that means, you understand everything Kubernetes asks of a container.

The problem

You write an app. It needs Python 3.12, a certain library version, and a config file at a specific path. It works on your laptop. On the server, Python is 3.9, the library is different, and it breaks.

On a real Linux server you also run several apps, and they fight over the same libraries, the same ports and the same files. Virtual machines solve that, but each one carries a whole operating system: gigabytes of disk and a minute to boot.

You want each app packaged with everything it needs, isolated from the others, and starting in a second.

Key idea

An image is a packaged filesystem plus a default command. A container is a running instance of an image. The image is the recipe. The container is the dish.

You met the same pair in the Linux handbook: a program is code stored on disk, a process is that program running. An image is the program. A container is the process.


docker pull nginx:1.27
docker images
docker run -d --name web -p 8080:80 nginx:1.27
docker ps
  • pull downloads an image from a registry.
  • images lists the images you have. They are not running.
  • run -d --name web -p 8080:80 creates and starts a container from the image: -d in the background, --name a name, -p 8080:80 sends port 8080 on your machine to port 80 in the container.
  • ps lists running containers. Ten docker run commands give ten containers from the same one image.

Layers

An image is built in layers, one per step of a build file. Layers are shared between images, so a second image built on the same base downloads only what is new.


FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]


FROM python:3.12-slim          base layer: a small Linux userland with Python
WORKDIR /app                   sets the working directory
COPY requirements.txt .        a layer containing just that file
RUN pip install -r ...         a layer with the installed libraries
COPY . .                       a layer with your code
CMD ["python", "app.py"]       the default command (not a layer; it is metadata)

Order matters. Docker reuses a cached layer if nothing above it changed. Copying requirements.txt and installing before copying your code means a code change does not reinstall every library.

Registries, names and tags


registry.example.com / team / web : 1.4.2
│                      │      │     │
│                      │      │     └─ tag: a label for a version
│                      │      └─────── repository name
│                      └────────────── namespace or organisation
└───────────────────────────────────── registry (leave out for Docker Hub)

A registry is a server that stores images. Docker Hub is the default one, so nginx:1.27 really means docker.io/library/nginx:1.27.

A tag is a movable label. nginx:1.27 can point to a different image next month. For an exact, unchanging reference, use the digest:


docker pull nginx:1.27
docker pull nginx@sha256:<64-hex-characters>
  • The first form follows the tag.
  • The second pins one exact image, forever. It is what you use when you must prove what was running.

A container is a process

This is the part that makes Kubernetes make sense. A container is not a small virtual machine. There is no second kernel. It is a normal Linux process, with two kernel features applied to it:

Namespaces

Control what the process can see. Its own process list (it thinks it is PID 1), its own network, its own mounts, its own hostname.

cgroups

Control how much the process can use: CPU, memory, and number of processes. This is where Kubernetes limits come from (chapter 13).

Union filesystem

Stacks the image layers read-only and adds one writable layer on top, so the container sees one ordinary filesystem.

Shared kernel

All containers on a node share its Linux kernel. That is why they start in a second, and why a container cannot run a different kernel than its host.

You can see it for yourself on a Linux machine with Docker:


docker run -d --name sleeper alpine sleep 600
docker exec sleeper ps
ps aux | grep "sleep 600"
docker top sleeper
  • Inside the container, ps shows sleep 600 as PID 1.
  • On the host, the same program shows up in ps aux with an ordinary, different PID.
  • It is one process, seen through two namespaces. On a Mac you only see the host side from inside Docker Desktop's Linux VM, but the idea is the same.

PID 1 and signals

Whatever the container's command is becomes PID 1 inside it. When Kubernetes stops a container, it sends SIGTERM to PID 1 and, after a grace period, SIGKILL. This is the kill and kill -9 pair from the Linux handbook. A program that ignores SIGTERM, or a shell script wrapper that does not pass it on, will take the full grace period to stop. Exec form (CMD ["python", "app.py"]) hands the signal straight to your app. Shell form (CMD python app.py) puts a shell in between.

Runtimes: who actually starts it

When you type docker run, a chain of programs does the work. Kubernetes uses the lower part of that chain, without Docker's command line.

docker CLI→Docker daemon→containerd→runc→Linux kernel
  • containerd is a container runtime: it pulls images and manages containers. Kubernetes nodes talk to it (or to CRI-O) through the Container Runtime Interface, CRI.
  • runc is the small program that actually creates the namespaces and cgroups and starts the process.
  • Images follow an open standard, OCI (Open Container Initiative), so an image built with Docker runs on containerd, CRI-O or Podman.

That is why "Kubernetes dropped Docker" was a headline that mostly meant nothing for you: your Docker-built images still run, because they are standard OCI images. What changed is that nodes talk to containerd directly instead of through the Docker daemon.

The rules containers live by

  • One main process per container. Not a web server, a database and an SSH daemon in one. One job per container, and the Pod (chapter 6) groups the ones that belong together.
  • The writable layer is temporary. Anything written inside is gone when the container is replaced. Keep data on a volume (chapter 12).
  • Log to stdout and stderr. The runtime captures those. kubectl logs reads them. A log file inside the container is invisible.
  • Configuration comes in from outside: environment variables and mounted files (chapter 11), so one image runs in dev and prod.
  • Containers are cattle, not pets. Expect them to be replaced at any time.

How this shows up in Kubernetes


containers:
  - name: web
    image: registry.example.com/team/web:1.4.2
    imagePullPolicy: IfNotPresent
    command: ["python"]
    args: ["app.py"]


image: ...:1.4.2          what to run (registry / repo : tag)
imagePullPolicy:          when the node should download it
command: ["python"]       replaces the image's ENTRYPOINT
args: ["app.py"]          replaces the image's CMD

Two details trip people up:

  • imagePullPolicy. If you leave it out, Kubernetes uses IfNotPresent for a specific tag, but Always if the tag is :latest or there is no tag. Always means a registry check every time a Pod starts.
  • command and args are the Kubernetes names for Docker's ENTRYPOINT and CMD. command replaces the entrypoint. args replaces the command. People set command thinking it is args, and wipe out the image's entrypoint.

Linux you already know

  • ps aux, top, kill work on containers because containers are processes. A runaway container shows up in the host's top.
  • The filesystem tree (/, /etc, /var, /tmp) inside a container is the image's. Your host's / is separate unless you mount something into it.
  • Permissions still apply. A process in a container runs as a user. The default in many images is root, which is why good images set a non-root user (chapter 16 and your security habits).
  • /proc is still the kernel's window. Inside a container, cat /proc/1/cgroup and ls -l /proc/1/ns show the cgroup and namespaces the kernel put it in.
  • Packages. apt install inside a Dockerfile RUN line is exactly the Linux handbook's package chapter, baked into a layer.

Common mistakes

Common mistake

"A container is a lightweight VM." It has no kernel of its own. It is a process with limited view and limited resources. That is why a Linux container cannot run on a Windows kernel without a Linux VM underneath.

Common mistake

"I'll save my data inside the container." The writable layer vanishes when the container is removed. Anything you need after a restart goes on a volume.

Common mistake

"nginx:1.27 always means the same image." Tags move. For a build you must be able to reproduce, use a version tag you control, or a digest.

Common mistake

"Docker is required for Kubernetes." Not on the nodes. Modern clusters use containerd or CRI-O. You may still use Docker on your laptop to build images.

Common mistake

Running as root with :latest and no resource limits. It works on day one and causes three separate incidents later. Pin the tag, set a user, set limits.

This can break things

docker run --privileged, or a Kubernetes container with privileged: true, removes most of the isolation. The container can then do almost anything the host can. Never use it for something you do not fully trust.

Try it

Try it

You need Docker. These commands are safe. Everything is removed at the end. On a Mac, Docker runs in a Linux VM, so the ps aux on the host side will not find the process. Use a Linux machine for that step, or skip it.


# 1. one image, two containers
docker pull nginx:1.27
docker run -d --name web1 -p 8081:80 nginx:1.27
docker run -d --name web2 -p 8082:80 nginx:1.27
docker ps
curl -I localhost:8081
curl -I localhost:8082

# 2. a container is a process (on Linux)
docker run -d --name sleeper alpine sleep 600
docker exec sleeper ps
ps aux | grep "sleep 600"

# 3. the filesystem is temporary
docker exec web1 sh -c 'echo hello > /tmp/note.txt; cat /tmp/note.txt'
docker rm -f web1
docker run -d --name web1 -p 8081:80 nginx:1.27
docker exec web1 cat /tmp/note.txt      # No such file: a new container, a fresh layer

# 4. limits are cgroups
docker run -d --name limited --memory=64m --cpus=0.5 nginx:1.27
docker exec limited cat /sys/fs/cgroup/memory.max
docker exec limited cat /sys/fs/cgroup/cpu.max

# 5. clean up
docker rm -f web1 web2 sleeper limited

What to look for:

  • Step 1: two containers from one image, on two ports.
  • Step 2: sleep 600 is PID 1 inside, and an ordinary process on the host.
  • Step 3: the note is gone. The data lived in a layer that no longer exists.
  • Step 4: the memory limit appears as a number of bytes in a file, and the CPU limit as a quota and a period. That is exactly what Kubernetes limits turn into. (The file names assume cgroup v2, which current Docker Desktop and recent Linux use.)

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between an image and a container?

An image is a read-only, layered package: a filesystem plus metadata like the default command. A container is a running instance of it, with a thin writable layer on top, which disappears when the container is removed. One image can have many containers. It's the same relationship as a program on disk and a process running it.

What is a container, technically?

A normal Linux process with two kernel features applied. Namespaces limit what it can see: its own process list, network, mounts and hostname. cgroups limit how much it can use: CPU, memory, process count. It shares the host's kernel, which is why it starts in about a second, and why it's less isolated than a VM.

How are containers different from VMs?

A VM runs a whole operating system with its own kernel on a hypervisor. A container shares the host kernel and is just an isolated process. So containers are much smaller and start much faster, but the isolation is weaker because they depend on the kernel's own boundaries. Both have uses. A Linux container can't run a different kernel from its host.

Kubernetes "dropped Docker". What does that mean for me?

Nodes no longer use the Docker daemon as the runtime. They talk to containerd or CRI-O through the Container Runtime Interface. It doesn't affect my images, because Docker builds standard OCI images, and those run on any OCI runtime. I can still build with Docker on my laptop. What I can't do is assume the Docker command exists on a node.

What are command and args in a Pod spec?

command overrides the image's ENTRYPOINT, and args overrides its CMD. If I set only args, the image's entrypoint still runs with my arguments. If I set command, I replace the entrypoint entirely. The common mistake is setting command when I meant to pass arguments, which silently removes the entrypoint the image relied on.

Habits worth keeping

Habits

Think "process in a fenced room", not "tiny VM". Pin image tags. Log to stdout. Keep data on volumes and config outside the image. Run as a non-root user. Use exec form for CMD so signals reach your app. And when a container misbehaves, remember you can use the Linux tools you already know.
