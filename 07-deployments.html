Deployments, ReplicaSets, rollouts

How a Pod gets replaced, scaled and rolled back

Section 07

A bare Pod dies and stays dead. A Deployment is the answer to "keep three copies running, and let me change the version without anyone noticing". It is the object you will write most often. By the end of this chapter you can explain how a rolling update works, one Pod at a time.

The problem

You ran web as a Pod. Now three things go wrong, one after another:

  • The node dies. Your Pod is gone. Nobody replaces it.
  • Traffic grows. You want five copies, not one.
  • You ship version 2. You do not want to delete the old Pod and wait while the new one starts. Users would see an outage.

You need something that holds a number and a template, and keeps reality equal to them. That is a Deployment.

Key idea

A Deployment says "I want N copies of this Pod template, always". It creates a ReplicaSet to hold the copies, and when you change the template it moves from the old ReplicaSet to a new one, a few Pods at a time.

Deployment (the plan)→ReplicaSet (counts heads)→Pod·Pod·Pod
Deployment

Holds the replica count and the Pod template. Handles updates and rollbacks. You write this one.

ReplicaSet

Keeps exactly N Pods matching its template running. The Deployment creates it. You rarely touch it.

Pod

The thing that actually runs. Created and replaced by the ReplicaSet.

Why two layers?

Each version of your template gets its own ReplicaSet. That is what makes rollbacks possible: the old one is still there.

Your first Deployment


apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80

Break it into the two halves that matter:


spec:
  replicas: 3              how many copies
  selector:                how the Deployment finds ITS Pods
    matchLabels:
      app: web             ──┐ these two must match
  template:                  │
    metadata:                │
      labels:                │
        app: web           ──┘
    spec:                    everything below here is just a Pod spec,
      containers: ...        the same one you wrote in chapter 6

Everything under template is a Pod, minus apiVersion and kind. The Deployment stamps out Pods from it.

The selector is how the Deployment knows which Pods are its own: any Pod carrying the label app: web. So the labels in the template must match the selector. If they do not, the API server refuses the Deployment.


kubectl apply -f web-deploy.yaml
kubectl get deployment web
kubectl get replicaset
kubectl get pods -l app=web
  • get deployment shows READY 3/3 once all copies are up. UP-TO-DATE counts Pods already on the newest template. AVAILABLE counts Pods ready for traffic.
  • get replicaset shows one ReplicaSet named web- plus a hash, like web-6d4cf56db6. The hash comes from the Pod template. Change the template, get a new hash, get a new ReplicaSet.
  • get pods -l app=web shows three Pods named web-<hash>-<random>. The name tells you which ReplicaSet made it.

Self-healing, in one command


kubectl delete pod web-6d4cf56db6-abcde
kubectl get pods -l app=web

Use a real Pod name from your own output. Almost at once there are three Pods again, one of them brand new. The ReplicaSet saw two where it wanted three, and made another. In chapter 6 the same delete was permanent. The difference is that something owns the Pod now.

Scaling


kubectl scale deployment web --replicas=5
kubectl scale deployment web --replicas=2
kubectl apply -f web-deploy.yaml
  • The first two change the replica count straight away. Quick, but they leave your file saying 3.
  • The third is the clean way: edit replicas in the file and apply it. The file stays the truth.

Scaling does not create a new ReplicaSet and does not count as a rollout. Only a change to the Pod template does.

Rolling updates

Change the image and apply. Or do it in one line:


kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web
kubectl get replicaset
  • set image deployment/web nginx=nginx:1.28 reads as: in the Deployment web, the container named nginx gets image nginx:1.28. The part before = is the container name, not the image.
  • rollout status waits and prints progress until the rollout finishes or fails. Handy in scripts: its exit code tells you if it worked.
  • get replicaset now shows two. The new one has the Pods. The old one is kept at zero Pods, ready for rollback.

What the Deployment actually does

It never kills everything and starts again. It moves Pods across, a few at a time. Two numbers control the pace:

SettingMeansDefault
maxSurgeHow many extra Pods above the desired count are allowed during the update.25%, rounded up
maxUnavailableHow many Pods may be unavailable at the same time.25%, rounded down
 

spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

With 3 replicas, maxSurge: 1 and maxUnavailable: 0, the update goes like this. "Ready" is the key word: a new Pod only counts once it is ready for traffic.

StepOld ReplicaSetNew ReplicaSetWhat happened
030Start
131One extra Pod starts (the surge). Total is 4. Nothing old has been touched.
221The new Pod is ready, so one old Pod is removed.
322Another new Pod starts.
412It becomes ready, another old Pod goes.
513Last new Pod starts.
603Ready. The old ReplicaSet is left at 0.

At no point are fewer than three Pods ready. That is a zero-downtime update. With the defaults on 3 replicas (surge 25% rounds up to 1, unavailable 25% rounds down to 0) you get exactly this behaviour.

Key idea

"Ready" is decided by a readiness probe (chapter 13). If you have none, a Pod counts as ready the moment its container starts. The rollout then races ahead and can send traffic to an app that is still booting, and your zero-downtime update has downtime in it.

The other strategy


spec:
  strategy:
    type: Recreate

Recreate kills every old Pod, then starts the new ones. There is an outage. Use it only when two versions cannot run side by side, for example an app that locks a database schema.

Rollbacks


kubectl rollout history deployment/web
kubectl rollout undo deployment/web
kubectl rollout undo deployment/web --to-revision=1
kubectl rollout restart deployment/web
  • history lists revisions. Each template change is one revision.
  • undo goes back one revision. It does it as a normal rolling update, so users do not see a break.
  • --to-revision=1 goes back to a specific one.
  • restart triggers a fresh rolling update with no template change. Use it to pick up a changed ConfigMap or to cycle Pods gently.

Undo works because the old ReplicaSet is still there, scaled to zero. Kubernetes keeps the last revisionHistoryLimit of them, 10 by default. Set it to 0 and you give up rollbacks.

History shows revision numbers but not why. Add the reason yourself:


kubectl annotate deployment/web kubernetes.io/change-cause="bump nginx to 1.28"

The text then appears in the CHANGE-CAUSE column of rollout history.

When a rollout gets stuck

Say you push an image tag that does not exist. The new Pod sits in ImagePullBackOff. The Deployment keeps the old Pods running, because maxUnavailable: 0 forbids removing them until the new one is ready. Your users keep being served by the old version. The rollout simply waits.

After progressDeadlineSeconds (600 by default, ten minutes) the Deployment marks itself Progressing=False with reason ProgressDeadlineExceeded. That is a label, not an action. It does not roll back. You do that.

Linux you already know

  • A Deployment is Restart=always in a systemd unit, grown up. systemd keeps one process of one service alive on one machine. A Deployment keeps N copies alive across many machines, and picks a new machine when one fails.
  • kubectl rollout restart is systemctl restart done gently: one copy at a time, behind a load balancer, so the service never goes fully down. It is closer to systemctl reload in spirit than restart.
  • kubectl rollout undo is the "have a rollback plan before you upgrade" advice from the package-management chapter, built in. The old version is not deleted, only set aside.

Common mistakes

Common mistake

Labels in the template do not match the selector. The API server rejects it with an error saying the selector does not match the template labels. They must agree. Copy the same app: web into both.

Common mistake

Trying to change spec.selector on a live Deployment. It is immutable in apps/v1. You get field is immutable. Decide your selector before the first apply. To change it you must delete and recreate the Deployment.

Common mistake

"I pushed a new image to myapp:latest, so my Deployment will update." It will not. The template did not change, so there is no rollout. Use a unique tag per build (a version or a git SHA), then change the tag in the template. Or run kubectl rollout restart, and know that the pull policy for :latest will pull again.

Common mistake

Editing a Pod or a ReplicaSet by hand. The controller above it will change it back, or recreate it. Change the Deployment. That is the only place your edit survives.

Common mistake

"A failed rollout rolls back by itself." It does not. The Deployment stops making progress and reports it. If you want automatic rollback, that is the job of your CI/CD tool or something like Argo Rollouts or Flagger.

Common mistake

"rollout undo restores my replica count." It restores the Pod template of an older revision. The replica count stays whatever it is now.

This can break things

kubectl delete deployment web deletes the Deployment, its ReplicaSets and every Pod. For a service people are using, that is an outage. Scale to zero first only if you mean it, and prefer rollout undo to deleting.

Try it

Try it

Use the kind cluster from chapter 4. Work in a scratch namespace so cleanup is one command. Open a second terminal and run kubectl get pods -n dev --watch to see every step as it happens.


# 1. set up
kubectl create namespace dev
kubectl apply -n dev -f web-deploy.yaml
kubectl rollout status deployment/web -n dev
kubectl get deployment,replicaset,pods -n dev

# 2. self-healing: delete one Pod (use a real name)
kubectl get pods -n dev
kubectl delete pod -n dev <one-of-the-web-pods>

# 3. scale
kubectl scale deployment web -n dev --replicas=5
kubectl get pods -n dev

# 4. a good rolling update
kubectl set image deployment/web nginx=nginx:1.28 -n dev
kubectl rollout status deployment/web -n dev
kubectl get replicaset -n dev
kubectl rollout history deployment/web -n dev

# 5. a bad one: an image tag that does not exist
kubectl set image deployment/web nginx=nginx:does-not-exist -n dev
kubectl rollout status deployment/web -n dev --timeout=30s
kubectl get pods -n dev
kubectl describe deployment web -n dev | tail -20

# 6. roll back
kubectl rollout undo deployment/web -n dev
kubectl rollout status deployment/web -n dev

# 7. clean up
kubectl delete namespace dev

What to look for:

  • Step 2: a new Pod appears within seconds, and its age is small.
  • Step 4: get replicaset lists two ReplicaSets. The old one shows 0 desired. Your --watch window shows new Pods starting before old ones terminate.
  • Step 5: the new Pod is stuck on ErrImagePull / ImagePullBackOff, but most old Pods are still Running. With 5 replicas and the default 25% maxUnavailable, the Deployment may take away one old Pod, no more. rollout status times out. Service carries on.
  • Step 6: the stuck Pod goes away and the Deployment is healthy again.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the relationship between a Deployment, a ReplicaSet and a Pod?

A Deployment owns ReplicaSets, and a ReplicaSet owns Pods. The Deployment holds the desired replica count and the Pod template and handles updates and rollbacks. Each version of the template gets its own ReplicaSet, whose only job is to keep the right number of Pods running. In practice I only write the Deployment. Each layer is a controller doing a reconcile loop on the layer below it.

How does a rolling update work?

When I change the Pod template, the Deployment creates a new ReplicaSet and gradually shifts Pods from old to new. Two settings control the pace. maxSurge is how many extra Pods are allowed above the desired count. maxUnavailable is how many can be unavailable at once. It starts a new Pod, waits for it to be ready, removes an old one, and repeats. That's why readiness probes matter. Without one, Kubernetes treats a Pod as ready the moment its container starts.

What triggers a rollout, and what doesn't?

Any change to spec.template: the image, environment variables, labels, resource requests. That creates a new ReplicaSet. Scaling changes replicas, not the template, so it doesn't trigger a rollout. Pushing a new image under the same tag doesn't either, because the template text is unchanged. That's why I use unique tags.

A rollout is stuck with new Pods failing. What happens, and how do you recover?

The old Pods keep serving, as long as maxUnavailable doesn't let the Deployment remove them first, so there's usually no outage. After the progress deadline, ten minutes by default, the Deployment reports ProgressDeadlineExceeded, but it doesn't roll back by itself. I'd run kubectl rollout undo to go back, then look at describe and the logs of the failing Pod to find out why it failed.

What does kubectl rollout undo actually restore?

It restores the Pod template from an earlier revision, by scaling the old ReplicaSet back up and the current one down, using the normal rolling update. It works because the Deployment keeps old ReplicaSets, up to revisionHistoryLimit, which defaults to 10. It doesn't change the replica count, and it can't help if I've set the history limit to zero.

Habits worth keeping

Habits

Use a Deployment, not a bare Pod, for anything that should stay up. Tag every image with something unique. Add a readiness probe so a rolling update waits for real readiness. Run rollout status after every apply in a pipeline. Keep the file in git and change the file, not the live object. And know your way out: rollout history, then rollout undo.
