Logs, metrics and Prometheus

Seeing what the cluster is doing

Section 21

Chapter 20 gave you the path for when something is already broken. This chapter is about knowing before it breaks, and about having evidence when it did. It covers three things: logs (what the app said), metrics (how it is doing, as numbers over time) and the standard tool for metrics, Prometheus.

The problem

kubectl logs and kubectl describe are good when you are sitting at a terminal and the Pod still exists. They fail you in three ways:

  • The Pod crashed last night and was replaced. Its logs went with it.
  • The node died. Its files, including every log on it, are gone.
  • Nothing is broken, but the app is slowly getting worse. Memory creeps up. Latency doubles. By the time a user complains, you have no history.

You need two things that outlive Pods: logs stored somewhere central, and metrics recorded over time so you can graph them and set alarms.

Key idea

Logs say what happened: one line per event, for reading. Metrics say how it is going: numbers sampled over time, for graphing and alerting. You need both, and neither lives inside the Pod.

Logs

Text your app prints to stdout and stderr. Good for "why did this request fail?". Large and noisy.

Metrics

Numbers with a timestamp: requests per second, memory used, errors. Small, cheap, and easy to alert on.

Events

Cluster-level notes ("scheduled", "pulled", "killed"). Short-lived: about an hour (chapter 20).

Traces

The path of one request across many services. A third pillar, usually built with OpenTelemetry. Mentioned here, not covered.

Logs

Where they go

A container should write its logs to stdout and stderr. The container runtime captures that output and writes it to files on the node. kubectl logs asks the kubelet to read those files.

app prints to stdout→runtime writes a file on the node→kubelet serves it→kubectl logs

On a node the files live under /var/log/pods/, with convenient links under /var/log/containers/. The kubelet rotates them by size, so old lines disappear. By default each container keeps up to five files of 10 MiB each.


kubectl logs web
kubectl logs web --tail=20 --timestamps
kubectl logs web --since=10m
kubectl logs web -f
kubectl logs web --previous
kubectl logs -l app=web --all-containers --prefix
  • --tail=20 shows the last 20 lines. --timestamps adds the time to each.
  • --since=10m shows only the last ten minutes.
  • -f follows, like tail -f.
  • --previous reads the run before the last restart (chapter 20).
  • -l app=web --all-containers --prefix reads from every matching Pod, every container, and prefixes each line with its source so you can tell them apart.

Why kubectl logs is not enough

  • The files live on the node. If the Pod is deleted, or the node goes, the logs go.
  • Rotation drops old lines.
  • You cannot search across fifty Pods and three days with kubectl.

So real clusters ship logs off the node. A small agent runs on every node, which is a job for a DaemonSet (chapter 14). It tails the log files and forwards them to a central store you can search.

Pods write logs→agent on each node (DaemonSet)→central store→search and dashboards
RoleCommon choices
Agent on each nodeFluent Bit, Vector, Promtail, Grafana Alloy, Filebeat
Store and searchLoki, Elasticsearch, OpenSearch, or a cloud logging service
Look at itGrafana, Kibana, OpenSearch Dashboards

Make logs easy to use: print one JSON object per line (structured logging) with fields like level, request ID and user, so the store can filter on them. Never log passwords or tokens (chapter 11).

metrics-server and kubectl top


kubectl top nodes
kubectl top pods -A
kubectl top pod web --containers

top shows what each node and Pod is using right now, the Kubernetes version of the Linux top you know. If it answers Metrics API not available, metrics-server is not installed. It does not come with every cluster. (Canonical Kubernetes bundles one: chapter 22.)

The same data feeds the HorizontalPodAutoscaler that chapter 13 mentioned:


apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

Read it as: "keep average CPU at about 50 percent of what each Pod requested, between 2 and 10 replicas". It needs CPU requests on the Pods (chapter 13) and a metrics source. Percent of nothing is not a number.

Prometheus

Prometheus is the standard metrics system for Kubernetes. Four ideas explain it:

  1. It pulls. Apps do not send metrics. They expose a plain-text page, usually /metrics, and Prometheus scrapes it every few seconds.
  2. It stores time series. Each metric has a name and labels (the sticky notes again), and a value for every scrape: http_requests_total{pod="web-1", status="500"}.
  3. You query it with PromQL. A small language for turning samples into answers.
  4. It alerts. Rules are evaluated constantly, and firing alerts go to Alertmanager, which deduplicates and sends the page or message. Grafana draws the graphs.
app exposes /metrics←Prometheus scrapes→time-series database→PromQL: Grafana graphs, alert rules→Alertmanager

The metric types

TypeGoes…Example
counteronly up (resets on restart)total requests served. You almost always want its rate.
gaugeup and downmemory in use, queue length
histogrambuckets of observationshow many requests took under 100 ms, under 500 ms… so you can compute percentiles

A few PromQL queries


rate(http_requests_total[5m])
sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="dev"}[5m]))
container_memory_working_set_bytes{namespace="dev", pod=~"web-.*"}
kube_pod_container_status_restarts_total
sum(kube_deployment_status_replicas_available) by (deployment)
  • rate(...[5m]) turns a counter into "per second, averaged over the last five minutes". This is the most used function.
  • sum by (pod) (...) adds series up, keeping one value per pod label.
  • container_cpu_usage_seconds_total and container_memory_working_set_bytes come from the kubelet's cAdvisor and describe each container. The working set is the number the OOM killer cares about (chapter 13).
  • kube_pod_container_status_restarts_total and kube_deployment_status_replicas_available come from kube-state-metrics, a small service that turns the state of Kubernetes objects into metrics.

Prometheus on Kubernetes: the operator

You rarely install Prometheus by hand. The kube-prometheus-stack Helm chart installs the Prometheus Operator (chapter 19), Prometheus, Alertmanager, Grafana, node-exporter (node-level metrics) and kube-state-metrics together, with dashboards ready. The operator gives you new kinds of object, so "monitor this app" is a manifest:


apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: web
  labels:
    release: monitoring
spec:
  selector:
    matchLabels:
      app: web
  endpoints:
    - port: http
      path: /metrics
      interval: 30s


kind: ServiceMonitor        a CRD from the Prometheus Operator
labels: release: monitoring the label Prometheus uses to find this ServiceMonitor (must match your Helm release name!)
selector: app=web           which Services to scrape (chapter 8's labels again)
endpoints: port http        the NAMED port on the Service
  path: /metrics            where the metrics page is
  interval: 30s             how often

An alert is a manifest too:


apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: web-alerts
  labels:
    release: monitoring
spec:
  groups:
    - name: web
      rules:
        - alert: WebPodRestarting
          expr: increase(kube_pod_container_status_restarts_total{namespace="dev"}[15m]) > 3
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "{{ $labels.pod }} restarted more than 3 times in 15 minutes"

for: 5m means the condition must hold for five minutes before the alert fires. It stops one blip from paging someone.

What to watch

You cannot alert on everything. A short list that works for most services is the four golden signals:

SignalQuestionExample
LatencyHow long do requests take?95th percentile response time
TrafficHow much demand is there?requests per second
ErrorsHow many requests fail?share of 5xx responses
SaturationHow full is it?CPU against requests, memory against limit, disk fullness

Alert on what users feel (errors, latency) rather than on every internal number. An alert should mean "a human needs to act now".

Linux you already know

  • kubectl logs -f is tail -f and journalctl -u … -f. The log files on the node under /var/log are the same /var/log from the filesystem chapter: "if something goes wrong with a server, /var/log is often one of the first places you look".
  • Log rotation is logrotate's job on a normal server. The kubelet does it for container logs, and that is why old lines vanish.
  • kubectl top is top. Same question, "what is eating my CPU or RAM right now?", for the whole cluster. htop on a node shows the same processes.
  • Prometheus node-exporter reads /proc. The handbook said /proc is "a window the kernel provides so user programs can read live system state". Almost every system metric (CPU, memory, disk, network) comes from there or from cgroup files.
  • A log-shipping agent on every node is a DaemonSet, the "install on every server" idea from chapter 14.
  • An alert is a cron job that never sleeps: evaluate a rule every few seconds and tell someone if it is true.

Common mistakes

Common mistake

Relying on kubectl logs for history. Pod gone, logs gone. Ship them off the node.

Common mistake

Logging to a file inside the container. Nothing collects it, and it grows the container's layer. Log to stdout.

Common mistake

"kubectl top says Metrics API not available, so the cluster is broken." metrics-server is not installed. It is a separate add-on.

Common mistake

Using metrics-server as a monitoring system. It keeps no history and cannot alert. It is for top and autoscaling.

Common mistake

A ServiceMonitor that Prometheus ignores. The usual causes: the release label does not match the Helm release name, the selector does not match the Service's labels, or port names a number instead of the Service port's name. Check the Prometheus UI under Targets.

Common mistake

Graphing a raw counter. It only goes up and resets on restart. Take its rate().

Common mistake

Alerting on everything. If people ignore alerts, they ignore the real one. Alert on symptoms users feel, and keep a short list.

Common mistake

High-cardinality labels. A label such as user ID or full URL creates a new series for every value and can overload Prometheus. Keep label values to small, bounded sets.

This can break things

Never log secrets, tokens or personal data. Logs are copied to central stores that more people can read than the Secret itself. Also, kube-prometheus-stack is large: it can need several gigabytes of memory, and a small laptop cluster may be unable to schedule it.

Try it

Part A: logs and events


kubectl create namespace dev
kubectl run chatty -n dev --image=busybox:1.37 -- sh -c 'i=0; while true; do echo "line $i"; i=$((i+1)); sleep 1; done'
kubectl wait -n dev --for=condition=Ready pod/chatty --timeout=60s

kubectl logs -n dev chatty -f                 # Ctrl+C to stop

# where the file really is: find the node, then look inside it
kubectl get pod chatty -n dev -o wide
docker exec handbook-worker ls /var/log/pods            # use the node name from the line above
docker exec handbook-worker ls /var/log/containers | grep chatty

kubectl delete pod chatty -n dev
kubectl logs -n dev chatty                              # gone: the logs went with the Pod

Part B: metrics-server and kubectl top


kubectl top nodes                              # probably: Metrics API not available

What to look for:

  • Part A: the node's /var/log/pods holds a folder per Pod, and /var/log/containers has a link named after your Pod. After the Pod is deleted, kubectl logs has nothing. That is the reason to ship logs.
  • Part B: top first complains, then shows CPU and memory per node and Pod. It is the same idea as Linux top.
  • Part C: in the Prometheus UI, up lists every target with a value of 1 (alive) or 0. Try rate(container_cpu_usage_seconds_total[5m]). In Grafana, open a dashboard called something like "Kubernetes / Compute Resources / Namespace (Pods)".

Interview questions

Interview

Click a question, answer out loud first, then check.

Where do container logs go, and why isn't kubectl logs enough?

The app writes to stdout and stderr, the runtime captures that into files on the node under /var/log/pods, and kubectl logs reads them through the kubelet. They're rotated by size, and they disappear when the Pod is deleted or the node is lost. So for real use I run a log agent on every node, a DaemonSet like Fluent Bit or Vector, that ships logs to a central store such as Loki or Elasticsearch, where I can search across Pods and over time.

What's the difference between metrics-server and Prometheus?

metrics-server serves only the current CPU and memory for Pods and nodes, with no history. It powers kubectl top and the HorizontalPodAutoscaler. Prometheus is a full monitoring system: it scrapes any metrics, stores them as time series, and supports queries with PromQL, dashboards and alerting. I'd install both: metrics-server for autoscaling and quick checks, Prometheus for monitoring and investigation.

How does Prometheus find what to monitor in Kubernetes?

It pulls. Apps expose a metrics endpoint, and Prometheus scrapes it. In Kubernetes it discovers targets through the API, and with the Prometheus Operator I describe targets as objects: a ServiceMonitor selects Services by label and names the port and path to scrape. The operator turns those into Prometheus's configuration. When a target is missing, I check that the ServiceMonitor's labels match what Prometheus selects, and that the selector and port name match the Service.

What would you monitor and alert on for a web service?

The four golden signals: latency, traffic, errors and saturation. I'd alert on what users feel, such as error rate and high latency percentiles, and on saturation that predicts trouble, like memory near its limit or a disk filling. I'd add Kubernetes-level signals such as frequent restarts and unavailable replicas. Alerts should be few and actionable, with a duration so a blip doesn't page anyone.

Why do you use rate() on counters?

A counter only ever increases and resets to zero when the process restarts, so the raw value is not useful on a graph. rate() over a window like five minutes gives the per-second increase, and it handles resets properly. So "requests per second" is rate(http_requests_total[5m]), and an error ratio is the rate of errors divided by the rate of all requests.

Habits worth keeping

Habits

Log to stdout, in JSON, with no secrets. Ship logs off the node. Install metrics-server for top and autoscaling, Prometheus for history. Take the rate() of counters. Watch latency, traffic, errors and saturation. Alert on what users feel, and keep the list short. And remember that events fade after an hour: write down what you learn.
