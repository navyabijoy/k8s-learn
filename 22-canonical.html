Kubernetes at Canonical

MicroK8s, Canonical Kubernetes, Charmed Kubernetes, Juju

Section 22

You are preparing for a team at Canonical, so this is the chapter that is about them. Canonical ships Kubernetes in more than one form, and the names are easy to mix up. By the end you can say what each one is, how they relate, what Juju has to do with it, and which questions to ask the interviewer.

Everything below was read from Canonical's own pages in October 2026 (sources are listed at the end), and where a page did not say something, this chapter says so instead of guessing. The problem

Upstream Kubernetes is a set of programs and a lot of choices. Which network plugin? Which DNS? How do you install it, upgrade it, patch it, and who do you call at 3 a.m.? Most companies do not want to make all of those choices themselves.

You already know this pattern from the Linux handbook. The Linux kernel is not something you install on its own. You install a distribution like Ubuntu: the kernel plus a chosen set of tools, defaults and a package manager. Kubernetes has distributions for the same reason.

Key idea

Upstream Kubernetes is to a Kubernetes distribution what the Linux kernel is to Ubuntu. A distribution adds the choices, the packaging, the upgrades and the support. Canonical, the company behind Ubuntu, sells three of them.

Snaps in two minutes

Two of the three products are installed as snaps. In the Linux handbook you installed software with apt, which pulls many small packages and shares libraries. A snap is one self-contained package with its own dependencies, managed by a service called snapd. Installs go through a store, and by default snaps update themselves in the background.


snap info k8s
snap list
snap services k8s
sudo snap refresh k8s
  • snap info k8s shows the available channels: which versions, and how stable. Canonical's channel names look like <version>-classic/<risk>, for example 1.36-classic/stable. Read this output instead of trusting a blog post for what exists today.
  • snap list shows what is installed and which channel you follow.
  • snap services k8s lists the background services the snap runs. They are ordinary systemd services under the hood.
  • snap refresh updates to the latest revision of the channel you follow.

The --classic flag on the install commands means the snap is installed with classic confinement: it is not sandboxed. A Kubernetes node needs to touch the whole machine (networking, mounts, containers), so it cannot be fenced in.

MicroK8s

What Canonical says

"Low-ops, minimal production Kubernetes", for developer workstations up to high-availability production clusters. Built by the Kubernetes team at Canonical.

Shape

One snap. Upstream Kubernetes. Updates over the air. Optional add-ons switched on with one command.

Good for

Learning, local development, CI, small edge sites, and small clusters that need to stay up.

Status

Actively released: its release notes list 1.34, 1.35 and 1.36. Canonical has not announced it going away.


sudo snap install microk8s --classic
microk8s status --wait-ready
microk8s kubectl get nodes
microk8s enable dns
  • The install is a normal snap install.
  • status --wait-ready blocks until the cluster is up. It is the first command to run after installing.
  • microk8s kubectl is the bundled kubectl. You can alias it to kubectl.
  • microk8s enable <addon> turns on an add-on. The add-on list changes between releases, so use microk8s status to see what exists on yours. For example, with 1.36 Canonical removed its dashboard add-on, after upstream deprecated the Kubernetes Dashboard.

On macOS, Canonical documents brew install ubuntu/microk8s/microk8s followed by microk8s install. That is Canonical's route for macOS.

Clustering and high availability


# on the first node
microk8s add-node

# on the node that is joining (paste the command add-node printed)
microk8s join 192.168.1.230:25000/<token>
microk8s join 192.168.1.230:25000/<token> --worker

# leaving
microk8s leave
microk8s remove-node 10.22.254.79
  • add-node prints a one-time join command with a token. You run that on the new machine.
  • --worker joins a node that only runs workloads, not control-plane components.
  • leave is run on the node that is going away. remove-node is then run from a remaining node.

Per Canonical's docs, high availability has been on by default since MicroK8s 1.19. With three or more nodes the datastore is replicated, so the cluster survives one node failing. Worker-only nodes do not count toward that. The datastore is dqlite, not etcd.

Canonical Kubernetes

This is Canonical's newer distribution. Canonical describes it as "a performant, lightweight, secure and opinionated distribution of Kubernetes". It builds on upstream and adds the extra services a cluster needs, so you do not have to choose them. The same distribution can be deployed three ways: as a snap, as a Juju charm, or through Cluster API.

What is in the box

Canonical's launch post listed what it bundles: networking, DNS, a metrics server, local storage, ingress, a gateway and a load balancer, "powered by Cilium, CoreDNS, OpenEBS, and Metrics Server". Network, DNS and the metrics server run straight after bootstrap, and the rest you switch on. Confirm the current list on your own cluster with sudo k8s status, because features are added over time.

You know these from earlier chapters: DNS (chapter 9), ingress (chapter 10), storage (chapter 12), the network plugin (chapter 17), metrics (chapter 21). Canonical Kubernetes is a cluster where those choices were made for you.

Install on a Linux machine


snap info k8s
sudo snap install k8s --classic --channel=1.36-classic/stable
sudo k8s bootstrap
sudo k8s status --wait-ready
sudo k8s kubectl get nodes
sudo k8s kubectl get pods -n kube-system
  • snap info k8s first, to see which channels exist today. Canonical's own docs use 1.37-classic/stable as an example while their release notes list up to 1.36 LTS. Pick a channel that snap info really shows.
  • sudo k8s bootstrap creates a new cluster on this node. You run it once.
  • sudo k8s status --wait-ready waits for the cluster, then shows which features are enabled.
  • sudo k8s kubectl ... is the bundled kubectl. Running it with sudo is how Canonical's tutorial does it.

Turn features on and off


sudo k8s enable local-storage
sudo k8s disable local-storage
sudo k8s status

enable and disable switch core cluster features. local-storage is the one Canonical's tutorial uses as its example.

Add a worker node


# on the existing control-plane node
sudo k8s get-join-token --worker

# on the new machine: install the same channel, then join
sudo snap install k8s --classic --channel=1.36-classic/stable
sudo k8s join-cluster <JOIN-TOKEN>
  • get-join-token --worker makes a token for a worker-only node.
  • The new machine needs the snap, on the same channel as the cluster. Then join-cluster with that token.
  • For a control-plane node, Canonical's pages I read did not show the exact form. Run sudo k8s get-join-token --help and use what it prints.

Requirements and a warning

  • Ubuntu 22.04 or later, or another OS that supports snaps. Root or sudo. Internet access.
  • Canonical recommends at least 20 GB of disk and 8 GB of memory for workloads.
  • Use a clean machine. The docs warn that the snap may conflict with Docker or containerd already on the host. If you use LXD, use virtual machines rather than containers.

Support and lifecycle

In February 2025 Canonical announced a 12-year security maintenance and support commitment starting with Kubernetes 1.32, delivered as Canonical Kubernetes 1.32 LTS. Its release notes label both 1.32 and 1.36 as LTS. Canonical's MicroK8s page ties paid enterprise support to Ubuntu Pro.

Charmed Kubernetes and Juju

To understand Charmed Kubernetes, you first need Juju, because Charmed Kubernetes is a Kubernetes you get through Juju.

Juju in plain words

Canonical describes Juju as "an open source orchestration engine for software operators". Chapter 19 explained operators: programs that hold the knowledge of how to run a piece of software. Juju is the same idea, applied to machines and clouds. A charm is that packaged knowledge for one application: how to install it, configure it, connect it to others, scale it and upgrade it.

Juju wordPlain meaningKubernetes cousin
controllerthe Juju server that manages deployments on one or more cloudsthe control plane
modela workspace holding a set of deployed applicationsa namespace
charmpackaged code and metadata that knows how to run an applicationan operator, or a Helm chart with brains
applicationa deployed charm, with a namea Deployment
unitone running instance of an application, on one machinea Pod
integrationa link between two applications that exchange dataa Service plus config wiring
bundlea set of charms and integrations deployed togethera Helm release of many things

The table is my plain-words summary. Juju's own docs have the precise definitions. Canonical's CLI reference lists the commands that matter, and the names below are all taken from it:


juju bootstrap
juju add-model dev
juju deploy <charm-or-bundle>
juju integrate <app-a> <app-b>
juju status
juju config <app>
juju add-unit <app>
juju scale-application <app> <n>
  • bootstrap creates a controller on a cloud.
  • add-model makes a workspace.
  • deploy puts a charm or bundle in it.
  • integrate connects two applications. Older guides call this relate. Today's command list has integrate, not relate.
  • status is the one you will run most.
  • config reads and sets application settings. add-unit and scale-application change how many units run.

Charmed Kubernetes

Canonical describes it as wrapping "upstream K8s with software operators". It is Kubernetes deployed and run by charms: a control-plane charm, a worker charm, etcd and a certificate authority charm (easyrsa), all connected with Juju integrations. Because Juju can drive many clouds and bare metal, it is aimed at multi-cloud and larger deployments.


juju add-model k8s
juju deploy charmed-kubernetes
juju status
  • The bundle is called charmed-kubernetes. Canonical's install guide says it has "significantly higher resource requirements (10+ machines)".
  • A smaller bundle called kubernetes-core puts one control-plane unit with etcd and a certificate authority on one machine and one worker on another. Canonical's install guide for existing machines uses it and needs Juju 3.1 or later and Ubuntu 22.04 or equivalent.
  • You scale the parts separately with Juju, for instance juju add-unit kubernetes-worker.
  • The control-plane application was called kubernetes-master in old guides. Today it is kubernetes-control-plane.

The Canonical Kubernetes charm

Canonical Kubernetes can also be deployed with Juju. Its docs describe a charm named k8s that installs and configures the k8s snap on machines Juju manages, on any cloud Juju supports. So the same distribution has two doors: install the snap by hand on a machine, or let Juju do it across many. For the exact charm commands and channels, use the "k8s charm" install guide in Canonical's docs. I did not copy them here because I could not verify them.

The relationship, carefully

In Feb 2025 Canonical wrote that "future releases of MicroK8s and Charmed Kubernetes will build on Canonical Kubernetes and also gain the 12 year LTS", and at the beta launch called Canonical Kubernetes "an excellent foundation" for them. That is a statement about direction, in 2024 and 2025 posts. MicroK8s and Charmed Kubernetes are still shipping and documented in 2026. Say it that way: three distributions, with Canonical Kubernetes as the foundation Canonical is building the others on. And ask the interviewer where each stands today. That is a good question to ask.

Linux you already know

  • Distribution versus kernel is the very first table of the Linux handbook, reused. Say "Kubernetes is the kernel, Canonical Kubernetes is the distribution" and you have explained it.
  • snap versus apt is a packaging choice. apt pulls shared libraries from an archive. A snap carries what it needs and updates itself. snap info, snap list and snap refresh are the counterparts of apt show, apt list --installed and apt upgrade.
  • LTS is the same word as in "Ubuntu LTS". It means "supported for a long time, with security fixes", and the handbook told you to prefer it.
  • The services the snap runs are systemd services. snap services k8s, systemctl and journalctl are how you see them, exactly as for nginx.
  • A node is a Linux machine. k8s get-join-token and microk8s add-node are ways to say "this machine is now part of the cluster".

Common mistakes

Common mistake

"Canonical Kubernetes, MicroK8s and Charmed Kubernetes are the same thing." They are three distributions with different packaging and audiences. Name the install method for each: snap, snap and charm, Juju bundle.

Common mistake

"Canonical Kubernetes replaces MicroK8s." Not as far as Canonical has said. It is described as a foundation for future MicroK8s and Charmed Kubernetes releases, and MicroK8s still ships. Do not claim a deprecation that nobody announced.

Common mistake

"A charm is a Helm chart." A Helm chart templates YAML and stops. A charm contains code that keeps running: it reacts when units join, configuration changes or an integration is made. That is closer to an operator.

Common mistake

Installing on a machine that already runs Docker or containerd. The docs warn of conflicts. Use a clean VM.

Common mistake

Using a channel from a blog post. Channels and versions move. snap info k8s shows what exists now.

Common mistake

Older Juju commands. juju relate became juju integrate, and kubernetes-master became kubernetes-control-plane. Old guides use the old names.

Try it

Try it

You need a clean Ubuntu 22.04 or later machine with root access: a cloud VPS (chapter 4 of the Linux handbook), a VirtualBox VM, or WSL on Windows with snap support. Give it 8 GB of memory and 20 GB of disk if you can. Do not run this on a machine that has Docker installed. This is a different cluster from your kind cluster, so skip it if you only have a Mac and no VM.


# 1. what does the store offer today?
snap info k8s

# 2. install and bootstrap (use a channel from step 1)
sudo snap install k8s --classic --channel=1.36-classic/stable
sudo k8s bootstrap
sudo k8s status --wait-ready

# 3. it is just Kubernetes
sudo k8s kubectl get nodes -o wide
sudo k8s kubectl get pods -n kube-system
sudo k8s kubectl create deployment hello --image=nginx:1.27 --replicas=2
sudo k8s kubectl get pods

# 4. the Linux side
snap services k8s
snap list
sudo k8s get --help

# 5. features
sudo k8s enable local-storage
sudo k8s status

# 6. clean up
sudo snap remove k8s --purge

Then, on a separate clean machine, compare with MicroK8s:


sudo snap install microk8s --classic
microk8s status --wait-ready
microk8s kubectl get nodes
microk8s kubectl get pods -A
sudo snap remove microk8s --purge

What to look for:

  • Step 3: the same kube-system Pods you saw in chapter 3, plus what Canonical bundled (a network plugin and DNS). Compare with a kind cluster and with MicroK8s.
  • Step 4: the snap runs services you can list. Same operating system, same systemd.
  • Step 5: k8s status changes. Features are switches, not separate installs.
  • Write down three differences you noticed between the two. That list is your interview answer to "how do they differ in practice?"

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between MicroK8s, Canonical Kubernetes and Charmed Kubernetes?

All three are Canonical distributions of upstream Kubernetes. MicroK8s is a single snap, described as low-ops and minimal production, good for workstations, edge and small HA clusters. Canonical Kubernetes is the newer, opinionated distribution. It's a snap called k8s, also a Juju charm, also usable through Cluster API, with Cilium, CoreDNS and other defaults bundled, and a 12-year LTS from 1.32. Charmed Kubernetes is deployed with Juju charms and bundles, aimed at multi-cloud and larger setups. Canonical has said it's building the other two on top of Canonical Kubernetes over time.

Why would a company use a distribution instead of plain upstream Kubernetes?

Upstream is components and decisions. A distribution makes the decisions: which network plugin, DNS, storage and ingress, how to install, how to upgrade and patch, and who supports it. It's the same reason people run Ubuntu and not a bare kernel. For Canonical specifically, you also get a long support commitment, a 12-year security maintenance commitment starting with 1.32, and enterprise support through Ubuntu Pro.

What is Juju, and what is a charm?

Juju is an orchestration engine for software operators. A charm is one of those operators: packaged code that knows how to install, configure, connect, scale and upgrade one application. A controller manages deployments, a model is a workspace, an application is a deployed charm, and units are the running instances. You connect applications with integrations. A charm is closer to a Kubernetes operator than to a Helm chart, because it keeps reacting to events rather than just templating files.

How would you add a worker node to a Canonical Kubernetes cluster? And to MicroK8s?

For Canonical Kubernetes I'd run sudo k8s get-join-token --worker on a control-plane node, install the same snap channel on the new machine, and run sudo k8s join-cluster with the token. For MicroK8s I'd run microk8s add-node on an existing node, which prints a join command, and run that on the new machine, with --worker if it should only run workloads. In both cases the shape is the same: a one-time token from the cluster, used by the new node.

Why does it matter that these are delivered as snaps?

A snap is a self-contained package with its own dependencies, installed from a store and tied to a channel, which combines a Kubernetes version and a stability level. That gives you one installable unit with a clear version, and it can refresh itself, which Canonical uses for automatic patch updates. The trade-off is that Kubernetes snaps use classic confinement, so they aren't sandboxed, and they can conflict with a container runtime already on the machine.
