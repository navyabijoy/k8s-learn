Labels, selectors and namespaces

How Kubernetes finds things and keeps them apart

Section 08

A real cluster holds hundreds of objects, and they have to find each other and stay out of each other's way. Kubernetes does both with two simple tools: labels that you stick on things and search by, and namespaces that split the cluster into separate rooms. You have already used both without naming them.

The problem

Two questions come up the moment the cluster has real workloads.

  • How does a Service know which Pods are its Pods? Pods are created and destroyed all the time. A fixed list of names cannot work.
  • How do two teams share one cluster without tripping over each other? Alice's web and Bob's web cannot both exist if names are global.

The Linux handbook solved a similar problem with groups ("put everyone in developers and give the group access") and directories (/home/alice/notes.txt and /home/bob/notes.txt can both exist). Kubernetes uses the same two ideas.

Key idea

A label is a key and value stuck on an object. A selector finds objects by their labels. A namespace is a named space that holds objects, so the same name can exist in two namespaces.

Label

A sticky note: app: web. Many objects can carry the same one, and one object can carry many.

Selector

A search over sticky notes: "everything with app: web". Services, Deployments and policies use it.

Namespace

A room. Names must be unique inside a room, not across the cluster. Policies and quotas attach to rooms.

Annotation

A note that is not searchable: build numbers, URLs, tool settings. Labels identify. Annotations describe.

Labels


metadata:
  name: web
  labels:
    app: web
    env: dev
    tier: frontend

Three labels on one Pod. Nothing special about app, env or tier. You choose them. What matters is that your team uses them the same way.

Look at them, add them, remove them


kubectl get pods --show-labels
kubectl get pods -L app,env
kubectl label pod web tier=frontend
kubectl label pod web tier=backend --overwrite
kubectl label pod web tier-
  • --show-labels adds a column with every label. -L app,env adds one column per label you name, which is easier to read.
  • label pod web tier=frontend adds a label to a live object.
  • --overwrite is needed to change one that already exists. Without it, kubectl refuses.
  • A trailing dash, tier-, removes the label.

Rules for labels

  • A key is a name, optionally with a prefix and a slash: app, app.kubernetes.io/name.
  • Names and values are at most 63 characters, start and end with a letter or digit, and may contain -, _ and . in between.
  • Values are strings. replicas: 3 as a label value needs quotes: "3".

Labels worth agreeing on

Kubernetes suggests a shared set so tools can understand each other. They all live under app.kubernetes.io/:

This handbook uses the short app: web to keep examples small. Real manifests usually use the longer set, and Helm (chapter 18) adds them for you.

Selectors

On the command line


kubectl get pods -l app=web
kubectl get pods -l 'env in (dev,staging)'
kubectl get pods -l app=web,env!=prod
kubectl get pods -l '!tier'
  • app=web: label equals value. A comma means AND.
  • env in (dev,staging): value is one of a set. Quote it, because the shell treats the brackets specially.
  • env!=prod: not equal. (It also matches objects that have no env label.)
  • '!tier': the label tier does not exist.

In YAML


selector:
  matchLabels:
    app: web
  matchExpressions:
    - key: env
      operator: In
      values: [dev, staging]
    - key: tier
      operator: Exists


matchLabels:                    exact matches (all must hold)
  app: web
matchExpressions:               richer tests (all must hold, and together with matchLabels)
  - key: env
    operator: In                In, NotIn, Exists, DoesNotExist
    values: [dev, staging]      required for In and NotIn

Deployments, ReplicaSets, Jobs and NetworkPolicies use this form. A Service is older and simpler: it takes a plain selector: map of equal labels, as in chapter 9.

Why this is powerful

Everything connects by label, not by name. The Service finds Pods by app: web. The Deployment finds its Pods by the same label. Change a label and the connections change, with no other edit.

Deployment selects app=web·Service selects app=web·both find the same Pods

The orphan trick

Here is something to do when a Pod is misbehaving and you want to study it without losing it. Remove the label the ReplicaSet uses:


kubectl label pod web-6d4cf56db6-abcde app-

The ReplicaSet no longer counts that Pod as its own. It sees too few and creates a replacement. The Service also stops sending traffic to the old Pod. Your sick Pod keeps running, alone, for you to inspect. Delete it when you are done.

Namespaces

A namespace is a named space inside the cluster. Almost every object you create lives in exactly one. A fresh cluster already has four:

NamespaceFor
defaultwhat you create when you do not choose
kube-systemthe cluster's own parts: DNS, the proxy, the network plugin
kube-publicreadable by everyone, rarely used
kube-node-leaseone small object per node, used to detect dead nodes
 

kubectl create namespace dev
kubectl get namespaces
kubectl get pods -n dev
kubectl get pods -A
kubectl config set-context --current --namespace=dev
  • create namespace makes one. get namespaces lists them (short form ns).
  • -n dev works in that namespace for one command. -A looks in all of them.
  • set-context --current --namespace=dev changes your default so you can drop -n. Check kubectl config view --minify | grep namespace if you forget which one you are in.

Or put the namespace in the file:


apiVersion: v1
kind: Namespace
metadata:
  name: dev
---
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: dev

Not everything lives in a namespace

Some objects belong to the whole cluster: Nodes, Namespaces themselves, PersistentVolumes, StorageClasses, ClusterRoles. Ask the cluster which is which:


kubectl api-resources --namespaced=true
kubectl api-resources --namespaced=false

What a namespace gives you, and what it does not

A namespace does give youA namespace does not give you
separate names: web in dev and in prodnetwork isolation. A Pod in dev can still call a Service in prod, by its full DNS name, unless a NetworkPolicy stops it (chapter 17).
a scope for RBAC: "alice may edit things in dev" (chapter 16)node isolation. Pods from every namespace share nodes unless you schedule otherwise (chapter 15).
a scope for quotas and default limitsa hard security wall by itself. It is one layer of several.
a handle for Pod Security rules, set by labels on the namespacea way to hide objects from cluster admins.

Quotas and default limits

Two objects turn a namespace into a managed budget:


apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    pods: "5"
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.memory: 4Gi
---
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-defaults
  namespace: dev
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 64Mi
      default:
        memory: 128Mi
  • A ResourceQuota caps the total a namespace may use or create: five Pods, two CPUs of requests, and so on. Beyond that, creation is refused.
  • A LimitRange sets defaults for containers that do not say. Here, a Pod with no resources block gets a 100m CPU request, 64Mi memory request and a 128Mi memory limit. It fixes the "no requests at all" mistake from chapter 13 for the whole namespace.
  • When a quota covers CPU or memory, every Pod in the namespace must declare those requests or limits, or be rejected. A LimitRange default makes that painless.

Linux you already know

  • Labels are like groups. In the Linux handbook, a user can be in many groups, and you grant access to a group. A Pod can have many labels, and a Service or policy targets a label.
  • Namespaces are like directories. /home/alice/notes.txt and /home/bob/notes.txt can both exist. web in dev and web in prod can too. And you can reach across: /home/bob/notes.txt from Alice's shell, web.prod from a Pod in dev.
  • kubectl get -l is grep for objects. kubectl get pods -o name | grep web works too, but a label is exact.
  • Do not confuse two uses of one word. Chapter 2 had Linux namespaces (kernel isolation for a process). A Kubernetes namespace is a name scope in the API. They are unrelated, and mixing them up is a classic interview slip.

Common mistakes

Common mistake

"Namespaces isolate my teams." They separate names and let you attach permissions and quotas. They do not stop network traffic, and they do not isolate nodes. For real isolation add NetworkPolicy, RBAC, quotas and Pod Security.

Common mistake

Forgetting -n. "My Pod disappeared!" It is in another namespace. Use kubectl get pods -A | grep web when you are not sure.

Common mistake

Typos in labels. app: wbe in a Service selector selects nothing, and the Service silently has no endpoints. Compare labels with --show-labels.

Common mistake

Using labels as a database. A label value is short and plain. Put a long description or a URL in an annotation.

Common mistake

Pod labels that two Deployments share. If two Deployments select app: web, they fight over the same Pods. Give each one a distinct label, such as app.kubernetes.io/instance.

Common mistake

"A quota is on, but my Pod was created without requests." It cannot be. With a CPU or memory quota in place, a Pod without requests is rejected. Add them or add a LimitRange.

This can break things

kubectl delete namespace dev deletes everything inside it: Deployments, Pods, Services, Secrets, PersistentVolumeClaims. It does not ask twice. Never run it on a namespace you did not create for yourself, and check your context first.

Try it

Try it

On the kind cluster. We make two rooms, dev and prod, put a web in each, and play with labels and a quota.


# 1. two namespaces, the same Deployment name in each
kubectl create namespace dev
kubectl create namespace prod
kubectl create deployment web --image=nginx:1.27 --replicas=2 -n dev
kubectl create deployment web --image=nginx:1.27 --replicas=3 -n prod
kubectl get deployments -A | grep web

# 2. labels
kubectl get pods -n dev --show-labels
kubectl label namespace dev env=dev
kubectl label pods -n dev -l app=web tier=frontend
kubectl get pods -A -l app=web -L tier

# 3. selectors
kubectl get pods -A -l 'app=web,tier'
kubectl get pods -A -l 'app=web,!tier'

# 4. the orphan trick
kubectl get pods -n dev
kubectl label pod -n dev <one-web-pod> app-
kubectl get pods -n dev --show-labels      # three Pods now: one without the app label

# 5. reach across namespaces
kubectl expose deployment web -n prod --port=80
kubectl run tmp -n dev --rm -it --restart=Never --image=curlimages/curl -- curl -s -m 3 http://web.prod

# 6. a quota
kubectl apply -n dev -f - <<'EOF'
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
spec:
  hard:
    pods: "3"
EOF
kubectl scale deployment web -n dev --replicas=6
kubectl get pods -n dev
kubectl describe replicaset -n dev | grep -i -A2 quota

# 7. clean up
kubectl delete namespace dev prod

What to look for:

  • Step 1: two Deployments with the same name, no conflict.
  • Step 4: after removing the label, the Pod stays Running but the Deployment starts a replacement, so there are now three Pods in dev.
  • Step 5: the nginx page from web.prod. A Pod in dev reached a Service in prod. Namespaces did not stop it.
  • Step 6: the Pod count stops at the quota. The ReplicaSet's events say the creation was forbidden because the quota was exceeded. (The orphaned Pod from step 4 counts too.)

Interview questions

Interview

Click a question, answer out loud first, then check.

How does a Service know which Pods to send traffic to?

By labels. The Service has a selector, like app: web. A controller watches Pods, and any Pod in the same namespace carrying those labels, and ready, goes into the Service's EndpointSlice. There's no list of names to maintain. If I change a Pod's label, it joins or leaves the Service automatically.

What's the difference between labels and annotations?

Labels identify objects and can be selected on. Services, Deployments and policies find objects by label. They're short, with limited characters. Annotations hold non-identifying information, like a build URL or settings for an ingress controller. They can be larger and can't be used in selectors.

Do namespaces isolate workloads from each other?

Only partly. They separate names, and give a scope for RBAC, quotas and Pod Security settings. They don't isolate the network: by default a Pod in one namespace can call a Service in another using its full DNS name. They don't isolate nodes either. For real isolation I add NetworkPolicies, RBAC, quotas, and sometimes dedicated nodes or even separate clusters.

Which resources are cluster-scoped rather than namespaced?

Nodes, Namespaces, PersistentVolumes, StorageClasses, ClusterRoles and ClusterRoleBindings, and CustomResourceDefinitions, for example. I can list them with kubectl api-resources --namespaced=false. Their names are unique across the whole cluster, since there's no namespace to separate them.

What's a ResourceQuota, and how is it different from a LimitRange?

A ResourceQuota caps the total a namespace can use or create: total CPU and memory requests, number of Pods, and so on. Past that, new objects are refused. A LimitRange works per container or Pod. It sets default requests and limits, and minimums and maximums, so a Pod that doesn't specify any gets sensible values. They're often used together, because once a quota covers CPU or memory, every Pod must declare it.

Habits worth keeping

Habits

Agree on a small set of labels and use them everywhere. Check --show-labels before you blame a Service. Use annotations for long or tool-specific notes. Remember that namespaces separate names, not traffic. Set quotas and default limits per namespace. And before delete namespace, read your context out loud.
