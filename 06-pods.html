Pods

The smallest thing Kubernetes runs

Section 06

With Docker you ran a container. In Kubernetes you never run a container directly. You run a Pod, and the Pod runs your containers. This chapter is about why that extra layer exists and how to read one.

The problem

Imagine you run nginx to serve a website. Next to it you want a tiny helper that rewrites index.html every few seconds. Two programs. They must:

  • start together and stop together,
  • talk to each other over localhost,
  • share one folder on disk.

On a plain Linux server that is easy. Two processes on one machine already share a network and a disk. Docker alone makes it awkward: every container gets its own network and its own filesystem.

Kubernetes needs a unit that means "these containers belong together". That unit is the Pod.

Key idea

A Pod is one or more containers that share a network address and storage, are placed on the same node, and live and die together.

Think of it as

A flat. The containers are flatmates. One street address (the IP), one shared kitchen (volumes), and they move in and out together.

Most of the time

A Pod holds exactly one container. Several containers in one Pod is for tightly coupled helpers, not for "my app and my database".

It does not

Heal itself, scale itself, or move itself to another node. Other objects do that. A Pod is the thing they manage.

Short-lived

Pods are disposable. When one is replaced, the new one is a different Pod with a different IP.

Your first Pod

Everything in Kubernetes is described in YAML (a plain-text format for nested settings). Here is the smallest useful Pod:


apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80

Read it top to bottom, the way you read an ls -l line:


apiVersion: v1          what version of the API describes this object
kind: Pod               what type of object it is
metadata:
  name: web             its name, unique among Pods in a namespace
  labels: app: web      a sticky note you can search by (chapter 8)
spec:                   what you WANT, not what exists
  containers:           a list: one entry per container
    - name: nginx       a name for this container inside the Pod
      image: nginx:1.27 which image to run (use a version tag)
      ports: 80         a note for humans and tools, see "Common mistakes"
Key idea

spec is what you ask for. Kubernetes keeps a second block, status, for what is actually happening. Most of the work in Kubernetes is making status match spec.

Create it: three ways


kubectl apply -f nginx-pod.yaml
kubectl run web --image=nginx:1.27 --port=80
kubectl run web --image=nginx:1.27 --port=80 --dry-run=client -o yaml
  • apply -f reads the file and makes the cluster match it. This is the way you will use most.
  • run creates a Pod straight from flags. Quick for experiments, nothing saved.
  • --dry-run=client -o yaml creates nothing. It prints the YAML that run would send. It is the fastest way to get a starting file.

The third command printed this on a real cluster. Notice what Kubernetes added for you: restartPolicy: Always and dnsPolicy: ClusterFirst are defaults.


apiVersion: v1
kind: Pod
metadata:
  labels:
    run: web
  name: web
spec:
  containers:
  - image: nginx:1.27
    name: web
    ports:
    - containerPort: 80
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}

Look at it

Three commands answer almost every question about a Pod.


kubectl get pod web
kubectl get pod web -o wide
kubectl describe pod web
  • get is the one-line summary.
  • -o wide adds the Pod IP and the node it landed on.
  • describe is the full story, with a list of Events at the bottom. When something is wrong, read the events first.

NAME   READY   STATUS    RESTARTS   AGE   IP             NODE       NOMINATED NODE   READINESS GATES
web    1/1     Running   0          1s    10.244.0.127   minikube   <none>           <none>

Column by column:

ColumnWhat it tells you
READYContainers that are ready, out of the containers in the Pod. 1/2 means one of two is ready.
STATUSA human-friendly reason: Running, ImagePullBackOff, CrashLoopBackOff…
RESTARTSHow many times the containers restarted. The Pod itself stays the same.
IPThe Pod's own address inside the cluster. It changes if the Pod is replaced.
NODEWhich machine the Pod was placed on.

The bottom of describe is a timeline of what happened to the Pod:


Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  1s    default-scheduler  Successfully assigned default/web to minikube
  Normal  Pulled     1s    kubelet            spec.containers{nginx}: Container image "nginx:1.27" already present on machine and can be accessed by the pod
  Normal  Created    1s    kubelet            spec.containers{nginx}: Container created
  Normal  Started    1s    kubelet            spec.containers{nginx}: Container started
Scheduled (scheduler picks a node)→Pulled (kubelet gets the image)→Created→Started

This run had the image cached already. On a node that has never seen the image, you also get a Pulling event first, and the wait can be many seconds.

Two different programs wrote those lines. The default-scheduler picked a node. Then the kubelet on that node did the work. Chapter 3 explains who they are. For now, remember that "who wrote this event" tells you which part of the cluster to look at.

Talk to it


kubectl logs web
kubectl exec -it web -- sh
kubectl port-forward pod/web 8080:80
  • logs prints what the container wrote to stdout and stderr. Add -f to follow, --previous to see the last crashed run.
  • exec -it web -- sh opens a shell inside the container. The -- separates kubectl's flags from the command you want to run in there.
  • port-forward makes localhost:8080 on your laptop reach port 80 in the Pod. Use it to test. It is not how real traffic arrives (chapters 9 and 10).

curl -I localhost:8080


HTTP/1.1 200 OK
Server: nginx/1.27.5

Two containers, one Pod

Back to the problem from the start. nginx serves a folder. A second container writes into it. They share a volume called shared.


apiVersion: v1
kind: Pod
metadata:
  name: web-with-helper
spec:
  volumes:
    - name: shared
      emptyDir: {}
  containers:
    - name: nginx
      image: nginx:1.27
      volumeMounts:
        - name: shared
          mountPath: /usr/share/nginx/html
    - name: writer
      image: busybox:1.37
      command: ["sh", "-c", "while true; do date > /data/index.html; sleep 5; done"]
      volumeMounts:
        - name: shared
          mountPath: /data

volumes is declared once, at the Pod level. Each container then mounts it where it wants, like mount on Linux. emptyDir starts empty and is deleted when the Pod goes away.

Because both containers share the Pod's network, the writer container can reach nginx on localhost:


kubectl exec web-with-helper -c writer -- wget -qO- localhost


Sun Oct 11 11:25:08 UTC 2026

The -c flag picks a container. You need it whenever a Pod has more than one.

Native sidecars

A "helper that lives next to the app" is called a sidecar. Since Kubernetes 1.33 there is a proper way to declare one: put it under initContainers and set restartPolicy: Always on that container. It then starts before the main container and keeps running next to it. The writer above is the older, still valid style: just a second entry in containers.

Linux you already know

A container is not a small virtual machine. It is a normal Linux process that the kernel has fenced in with namespaces (what it can see) and cgroups (how much it can use). You met both ideas in the Linux handbook: ps, /proc, and the kernel that decides who gets CPU and memory.

A Pod is the same trick applied to a group. Look at the namespaces of PID 1 in each container of web-with-helper (nginx uses GNU ls, busybox a smaller one, which is why the spacing differs):


kubectl exec web-with-helper -c nginx  -- ls -l /proc/1/ns/net /proc/1/ns/ipc /proc/1/ns/mnt /proc/1/ns/pid
kubectl exec web-with-helper -c writer -- ls -l /proc/1/ns/net /proc/1/ns/ipc /proc/1/ns/mnt /proc/1/ns/pid

The nginx container:


lrwxrwxrwx 1 root root 0 Oct 11 11:25 /proc/1/ns/ipc -> ipc:[4026536930]
lrwxrwxrwx 1 root root 0 Oct 11 11:25 /proc/1/ns/mnt -> mnt:[4026537332]
lrwxrwxrwx 1 root root 0 Oct 11 11:25 /proc/1/ns/net -> net:[4026536933]
lrwxrwxrwx 1 root root 0 Oct 11 11:25 /proc/1/ns/pid -> pid:[4026537334]

The writer container:


lrwxrwxrwx    1 root     root             0 Oct 11 11:25 /proc/1/ns/ipc -> ipc:[4026536930]
lrwxrwxrwx    1 root     root             0 Oct 11 11:25 /proc/1/ns/mnt -> mnt:[4026537336]
lrwxrwxrwx    1 root     root             0 Oct 11 11:25 /proc/1/ns/net -> net:[4026536933]

Compare the numbers in brackets. Same number means same namespace.

NamespaceSame number in both?What it means
netyesOne network stack. Same IP, same localhost, same port space.
ipcyesThey can use shared memory and semaphores.
mntnoEach container has its own root filesystem. They only share what you mount.
pidnoEach container sees only its own processes (by default).

Two more Linux links:

  • Deleting a Pod works like kill, not kill -9. Kubernetes sends SIGTERM, waits (30 seconds by default, set by terminationGracePeriodSeconds), then sends SIGKILL.
  • restartPolicy: Always is the Pod-sized version of Restart=always in a systemd unit. The kubelet restarts the container on the same node. The Pod is not recreated.

Pods are mortal

This is the sentence to take away from the chapter. Delete a Pod made with the YAML above and it is simply gone. Nothing brings it back.


kubectl delete pod web
kubectl get pod web


pod "web" deleted from default namespace
Error from server (NotFound): pods "web" not found

A Pod is also never moved. If its node dies, the Pod dies with it. Something else has to notice and create a new Pod, and that something is a controller. The next chapter introduces the most common one, the Deployment.

You create a Pod→It runs on one node→It dies→Nobody replaces it (unless a controller owns it)

Phases, and why STATUS says more

A Pod has a phase, a coarse summary of where it is in its life:

PhaseMeaning
PendingAccepted by the cluster, but not all containers are set up yet. Not placed on a node, or still pulling images.
RunningPlaced on a node, all containers created, at least one still running or starting.
SucceededEvery container finished successfully and will not restart.
FailedEvery container finished, and at least one failed.
UnknownThe state could not be obtained, usually because the node cannot be reached.

The STATUS column in kubectl get is friendlier and more detailed. It is not the same thing as the phase. Here is a Pod with a typo in the image tag:


kubectl run oops --image=nginx:1.27-typo
kubectl get pod oops


NAME   READY   STATUS             RESTARTS   AGE
oops   0/1     ImagePullBackOff   0          20s

The phase of that Pod is still Pending. ImagePullBackOff is a container reason, not a phase. Chapter 20 gives you a fixed path for these.

Common mistakes

Common mistake

"I'll just run my app as a bare Pod." That works on a laptop. In real use nothing recreates a bare Pod when it or its node dies. Use a Deployment (chapter 7) for anything you want to stay up.

Common mistake

"containerPort: 80 opens port 80." It does not. It is a note for humans and tools. The container listens on whatever port the program inside listens on, whether you list it or not.

Common mistake

"I'll edit the Pod to change a setting." Most of a Pod's spec cannot change after creation. You may update a container image, add tolerations, and a few time limits. For anything else, delete the Pod and create a new one, or change the controller above it.

Common mistake

"image: nginx is fine." With no tag, or with :latest, you get whatever is newest today, and Kubernetes pulls on every start. Pin a version like nginx:1.27 so a restart next month runs the same thing.

Common mistake

"RESTARTS 5 means five new Pods." It means the same Pod's container restarted five times. The Pod, its IP and its volumes stay.

This can break things

kubectl delete pod on a Pod with no controller is permanent. Nothing recreates it, and an emptyDir volume goes with it. Check kubectl get pod NAME -o yaml for ownerReferences if you are not sure whether something will bring it back.

Try it

Try it

You need any local cluster and kubectl pointed at it. The outputs in this chapter came from minikube on macOS (Docker driver). The commands are the same on kind or MicroK8s. Chapter 4 covers setup.


# 1. check kubectl is talking to your cluster
kubectl get nodes

# 2. save the YAML from this chapter as nginx-pod.yaml, then create it
kubectl apply -f nginx-pod.yaml

# 3. watch it start (Ctrl+C to stop watching)
kubectl get pod web --watch

# 4. read the events
kubectl describe pod web

# 5. reach it from your laptop
kubectl port-forward pod/web 8080:80
# in a second terminal:
curl -I localhost:8080

# 6. look inside
kubectl exec -it web -- sh
ls -l /proc/1/ns

# 7. break it on purpose, then read the events
kubectl run oops --image=nginx:1.27-typo
kubectl describe pod oops

# 8. clean up
kubectl delete pod web oops

Questions to answer yourself before moving on:

  • Which node did web land on, and which component put it there? (Hint: look at the first event.)
  • What does kubectl get pod web say after step 8? Why does nothing bring it back?
  • In step 7, which event line names the real problem?

Interview questions

Interview

Click a question, answer out loud first, then check.

What is a Pod, and why doesn't Kubernetes just run containers?

A Pod is the smallest thing Kubernetes schedules. It is one or more containers that share a network address and storage and always land on the same node together. Kubernetes needs that unit because some programs have to sit side by side: an app and a log shipper, for example. Putting them in one Pod means they share localhost and a volume, and they start and stop together. Most Pods hold one container.

What do containers in the same Pod share, and what don't they share?

They share the network: one IP, one localhost, one set of ports, so two containers cannot both listen on port 80. They share IPC, and any volumes you declare and mount. They do not share a root filesystem or, by default, a process tree. Under the hood it is Linux namespaces: the network and IPC namespaces are common, the mount and PID ones are separate.

I deleted a Pod and it didn't come back. Why?

Because nothing was responsible for it. A bare Pod is not watched by anything. If a Deployment, ReplicaSet or similar controller had owned it, that controller would have noticed the count was wrong and made a new Pod. I'd check ownerReferences on the Pod. In practice you almost never create bare Pods for real workloads.

RESTARTS shows 4. Did Kubernetes create four new Pods?

No. It is the same Pod. The kubelet on that node restarted the container four times because restartPolicy defaults to Always. The Pod name, IP and volumes are the same. A new Pod would have a new name and a new IP. If the restarts keep climbing, I'd look at kubectl logs --previous to see why the container keeps dying.

What is a sidecar, and how do you declare one?

A sidecar is a helper container that runs next to the main one for the whole life of the Pod: a log shipper, a proxy, a config reloader. The classic way is just a second entry in containers. Since 1.33 there is a native way: an entry in initContainers with restartPolicy: Always. That one starts before the app, keeps running, and is handled properly on shutdown, so it fits things like proxies that must be up first.

Habits worth keeping

Habits

Pin image tags. Read events before logs. Generate YAML with --dry-run=client -o yaml instead of typing it. Use -c when a Pod has more than one container. Don't run bare Pods for anything you want to survive. Say it out loud: "A Pod is a group of containers sharing network and storage, scheduled together, and disposable."
