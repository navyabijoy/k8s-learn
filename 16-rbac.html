RBAC and ServiceAccounts

Who is allowed to do what

Section 16

Every request to the API server comes from someone: a person with kubectl, a CI job, or a Pod. The cluster must decide, for each one, whether it is allowed. That decision is RBAC. It is the same question the Linux handbook opened its permissions chapter with: who is allowed to read, modify or execute what?

The problem

Imagine a cluster shared by three people. Harry runs it. Alice is a developer who deploys in dev. Bob is a developer who should only be able to look. Then add a Pod that needs to list other Pods, and a CI pipeline that deploys.

Without rules, everyone with a login can delete anything, read every Secret and shut the cluster down. You need to give each identity exactly the permissions its job needs, and nothing else.

Key idea

RBAC (Role-Based Access Control) is an allow-list. A Role lists permissions. A binding hands that Role to a person, group or ServiceAccount. If nothing allows it, it is denied. There are no "deny" rules.

Authentication

"Who are you?" Settled before RBAC: a certificate, a token, or a login through your identity provider.

Authorization

"What may you do?" This is RBAC. It looks at the identity, the verb, the resource and the namespace.

Role

A list of permissions, inside one namespace. Nothing happens until it is bound.

Binding

The link: "give this Role to alice". Without a binding, a Role is just a document.

Subject (alice, a group, a ServiceAccount)→ RoleBinding →Role (verbs on resources)→allowed in that namespace

The four objects

ObjectScopeMeaning
Roleone namespacea set of permissions in that namespace
RoleBindingone namespacegives a Role (or a ClusterRole) to subjects, in that namespace only
ClusterRolewhole clusterpermissions that may cover cluster-wide objects (Nodes, PersistentVolumes) or all namespaces
ClusterRoleBindingwhole clustergives a ClusterRole to subjects everywhere

A Role


apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]


rules:
  - apiGroups: [""]              which API group. "" is the core group: Pods, Services, ConfigMaps, Secrets.
                                 Deployments are "apps"; Ingress is "networking.k8s.io".
    resources: ["pods"]          which kinds of object (plural, lower case)
    verbs: [get, list, watch]    which actions

The verbs map straight onto HTTP: get (one), list (many), watch (stream changes), create, update, patch, delete. Find the group for any resource with kubectl api-resources (the APIVERSION column).

Two details people miss:

  • Sub-resources are separate. Reading logs is pods/log. Running kubectl exec is pods/exec (and is very powerful). Giving pods does not give those.
  • kubectl get pods needs list, not just get, and --watch needs watch.

A binding


apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-pod-reader
  namespace: dev
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io


subjects:                  WHO gets it. A list: User, Group or ServiceAccount.
  - kind: User, name: alice
roleRef:                   WHAT they get. One Role or ClusterRole. Cannot be changed later:
  kind: Role                 to change it, delete and recreate the binding.
  name: pod-reader

The result: alice can get, list and watch Pods in dev. Nothing else, and nothing in other namespaces.

The same thing, in one line each


kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding alice-pod-reader --role=pod-reader --user=alice -n dev
kubectl create clusterrolebinding ops-view --clusterrole=view --group=ops
  • The first two build the Role and binding above. Add --dry-run=client -o yaml to get the YAML.
  • The third gives the group ops the built-in view ClusterRole across the whole cluster.

A trick worth knowing: bind a ClusterRole in one namespace

A RoleBinding may point at a ClusterRole. The permissions are then limited to the binding's namespace. It lets you define a role once and hand it out per namespace:


kubectl create rolebinding bob-view --clusterrole=view --user=bob -n dev

Bob can now see most things in dev and nothing in prod. Kubernetes ships four ready-made ClusterRoles for this:

ClusterRoleGives
viewread most things in a namespace. Cannot read Secrets.
editread and write most things in a namespace, including Secrets. Cannot change roles.
admineverything in a namespace, including roles and bindings there.
cluster-admineverything, everywhere.

There is no "User" object

This surprises people. You will not find kubectl get users. Kubernetes does not store people. The identity alice comes from outside: a client certificate with CN=alice, or a token from your company's login system (OIDC). RBAC only ever sees a name and a list of groups, and the binding matches on those strings.

Pods are different. They get an identity that is an object: a ServiceAccount.

ServiceAccounts: identities for Pods

A ServiceAccount is the identity a Pod uses when it talks to the API server. Every namespace has one called default. A Pod that does not choose one runs as it.


kubectl create serviceaccount viewer -n dev
kubectl get serviceaccounts -n dev
kubectl create token viewer -n dev


spec:
  serviceAccountName: viewer
  automountServiceAccountToken: true
  containers:
    - name: app
      image: curlimages/curl
  • create token prints a short-lived token for that ServiceAccount, valid for a limited time. That is what scripts and CI should use.
  • Inside a Pod, the token appears as a file under /var/run/secrets/kubernetes.io/serviceaccount/, with the cluster's CA certificate and the namespace. It is a bound, time-limited token that the kubelet refreshes, not a permanent Secret. (Older clusters created long-lived token Secrets automatically. Modern ones do not.)
  • Set automountServiceAccountToken: false on Pods that never talk to the API. A Pod that cannot see a token cannot misuse it.

A ServiceAccount has no permissions until you bind a Role to it. The subject looks like this:


subjects:
  - kind: ServiceAccount
    name: viewer
    namespace: dev

Its full identity string is system:serviceaccount:dev:viewer, which you will use when testing.

Asking "can they?"


kubectl auth can-i list pods -n dev
kubectl auth can-i delete pods -n dev --as alice
kubectl auth can-i list pods -n dev --as system:serviceaccount:dev:viewer
kubectl auth can-i --list -n dev --as alice
kubectl auth whoami
  • can-i answers yes or no. It is the first thing to try when you see a Forbidden error.
  • --as asks as someone else (impersonation). It needs permission to impersonate, which an admin has.
  • --list prints everything the identity may do in that namespace.
  • auth whoami tells you the identity and groups the API server sees for you.

A denial looks like this, and it tells you exactly what to grant:


Error from server (Forbidden): pods is forbidden: User "alice" cannot list resource "pods" in API group "" in the namespace "dev"

Read it as a recipe: user alice, verb list, resource pods, group "", namespace dev.

Giving less than you could

  • One ServiceAccount per app, with only what that app needs. Never reuse default for something with permissions.
  • Avoid cluster-admin for anything except a very small group of humans. A tool that "needs cluster-admin" usually does not.
  • Avoid wildcards (verbs: ["*"], resources: ["*"]). They grow silently as new resources appear.
  • Be careful with Secrets, pods/exec and create pods. Reading Secrets is obvious. Being able to create a Pod, or exec into one, often means being able to reach more than you were granted.
  • Prefer namespaced bindings over cluster-wide ones.
  • You cannot grant what you do not have. The API server blocks privilege escalation: to create a Role with a permission, you must hold it yourself (or hold the special escalate verb).

The Pod side of the same idea

RBAC controls what an identity may ask the API. A Pod's securityContext controls what its process may do on the node. Keep the second one tight too:


spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: registry.example.com/team/web:1.4.2
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
  • runAsNonRoot refuses to start a container that would run as root.
  • allowPrivilegeEscalation: false stops a process gaining more rights than its parent.
  • readOnlyRootFilesystem makes the container's own filesystem read-only. Write only to mounted volumes.
  • capabilities: drop: ["ALL"] removes the special Linux powers a root process normally has.
  • Clusters can enforce such settings per namespace with Pod Security Admission, by labelling the namespace (for example pod-security.kubernetes.io/enforce: restricted). The three levels are privileged, baseline and restricted.

Linux you already know

  • It is the permissions chapter again. Users, groups and rwx become subjects, roles and verbs. "Give the group developers access" becomes "bind a Role to the group developers".
  • A RoleBinding is usermod -aG. It adds an identity to a set of permissions. And just like -aG, the point is that it adds and never takes away. RBAC has no deny.
  • A ServiceAccount is a system user for a program. Nginx runs as www-data, not as root, so a bug in Nginx cannot rewrite the whole system. A Pod runs as a ServiceAccount for the same reason.
  • cluster-admin is root. sudo did not mean "become root forever", and a ClusterRoleBinding should not either: give it briefly, to few people, with a reason.
  • kubectl auth can-i --as is sudo -u alice for permission checks: "what would alice be able to do?"
  • "Do not chmod 777 to fix a permission problem." The Kubernetes version is "do not bind cluster-admin to make an error go away". Read the Forbidden message, and grant that one thing.
  • runAsNonRoot is the container-sized version of "do not run it as root".

Common mistakes

Common mistake

Binding in the wrong namespace. A RoleBinding grants access only in its own namespace. A binding in default does nothing for dev.

Common mistake

"Role and ClusterRole are the same." A Role is one namespace. A ClusterRole can also cover cluster-wide objects like Nodes, and can be bound cluster-wide. Cluster-scoped resources can only be granted through a ClusterRole.

Common mistake

Granting get and expecting kubectl get pods to work. Listing needs list. Following needs watch.

Common mistake

Wrong apiGroups. Deployments are in apps, not "". A rule on deployments with group "" matches nothing.

Common mistake

"I'll deny Bob access to Secrets." There is no deny. You can only avoid granting it. Check that none of his roles, or his groups' roles, include it, and remember the edit and admin roles do.

Common mistake

Giving every app the default ServiceAccount with extra rights. Every other Pod in that namespace shares it. Create one ServiceAccount per app.

Common mistake

Leaving the token mounted in Pods that do not need it. If the app is compromised, so is whatever that token can do. Turn automountServiceAccountToken off.

This can break things

kubectl create clusterrolebinding … --clusterrole=cluster-admin hands over the whole cluster. And any identity in the group system:masters bypasses RBAC completely, with no way to take it back short of changing the credentials. Treat both like a root password.

Try it

Try it

On the kind cluster. You are cluster-admin on your own laptop cluster, so we use --as to pretend to be Alice, and a Pod that calls the API with its ServiceAccount token.


kubectl create namespace dev

# ---- 1. a person (impersonated) ----
kubectl auth can-i list pods -n dev --as alice            # no
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding alice-pod-reader --role=pod-reader --user=alice -n dev
kubectl auth can-i list pods -n dev --as alice            # yes
kubectl auth can-i delete pods -n dev --as alice          # no: reading is not deleting
kubectl auth can-i list pods -n prod --as alice           # no: the binding is only in dev
kubectl get pods -n dev --as alice
kubectl get secrets -n dev --as alice                     # Forbidden: read the error out loud
kubectl auth can-i --list -n dev --as alice

# ---- 2. a Pod ----
kubectl create serviceaccount viewer -n dev
kubectl apply -n dev -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: api-test
spec:
  serviceAccountName: viewer
  containers:
    - name: curl
      image: curlimages/curl
      command: ["sleep", "3600"]
EOF
kubectl wait -n dev --for=condition=Ready pod/api-test --timeout=90s
kubectl exec -n dev api-test -- ls /var/run/secrets/kubernetes.io/serviceaccount

# the Pod calls the API with its own token: first denied ...
kubectl exec -n dev api-test -- sh -c 'curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" https://kubernetes.default.svc/api/v1/namespaces/dev/pods | head -12'

# ... then allowed after a binding
kubectl create rolebinding viewer-pod-reader --role=pod-reader --serviceaccount=dev:viewer -n dev
kubectl exec -n dev api-test -- sh -c 'curl -s --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" https://kubernetes.default.svc/api/v1/namespaces/dev/pods | head -12'

# ---- clean up ----
kubectl delete namespace dev

What to look for:

  • Part 1: no, then yes after the binding, then no for delete and for another namespace. The Forbidden message names the user, verb, resource, group and namespace.
  • Part 2: the first curl returns a JSON error of kind Status with code 403 and a message naming system:serviceaccount:dev:viewer. After the binding, the same request returns a PodList. The Pod's identity is the ServiceAccount, and its rights come only from bindings.

Interview questions

Interview

Click a question, answer out loud first, then check.

Explain Role, ClusterRole, RoleBinding and ClusterRoleBinding.

A Role is a list of permissions, verbs on resources, inside one namespace. A ClusterRole is the same but cluster-wide, so it can cover cluster-scoped objects like Nodes or all namespaces. A binding attaches a role to subjects: users, groups or ServiceAccounts. A RoleBinding grants within its own namespace, and it may reference either a Role or a ClusterRole, which is a handy way to reuse a definition per namespace. A ClusterRoleBinding grants cluster-wide.

How do Kubernetes users work?

There's no User object. Kubernetes doesn't store people. Identity comes from outside: a client certificate where the common name is the user, or tokens from an OIDC identity provider. The API server authenticates the request and gets a username and groups, and RBAC matches bindings against those strings. ServiceAccounts are the exception: they're real objects, used by Pods and automation.

How would you check what a user or ServiceAccount can do?

kubectl auth can-i, with --as to impersonate, for example --as system:serviceaccount:dev:viewer. --list prints everything they can do in a namespace. When I see a Forbidden error, it names the user, verb, resource, API group and namespace, so I know exactly what's missing, and I grant that one permission and no more.

What is a ServiceAccount, and how has its token changed?

It's the identity a Pod uses to call the API. Each namespace has a default one, and I should create one per application. Its token is mounted into the Pod at /var/run/secrets/kubernetes.io/serviceaccount. Modern clusters use short-lived, bound tokens that the kubelet refreshes, instead of the old permanent token Secrets. If the Pod doesn't need the API, I set automountServiceAccountToken: false.

How do you apply least privilege in a cluster?

One ServiceAccount per app with a narrow Role. Namespaced bindings rather than cluster-wide ones. No wildcards, and no cluster-admin except for a few humans. Extra care with Secrets, pods/exec and the right to create Pods. On the Pod side, run as non-root with a read-only filesystem and dropped capabilities, enforced per namespace with Pod Security Admission. And RBAC has no deny rules, so I audit what's granted with can-i --list.

Habits worth keeping

Habits

Start from nothing and add. Read the Forbidden message and grant exactly that. One ServiceAccount per app. Prefer RoleBindings to ClusterRoleBindings. Test with kubectl auth can-i --as. Treat cluster-admin and system:masters like root. And remember: it is the permissions chapter of the Linux handbook, with new nouns.
