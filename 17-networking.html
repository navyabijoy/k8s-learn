Networking: the Pod network, CNI, NetworkPolicy

How every Pod can reach every Pod, and how to stop that

Section 17

Services (chapter 9) sit on top of something: a network where every Pod has its own address and can reach every other Pod. This chapter looks at that layer, who builds it (a CNI plugin), and the one tool Kubernetes gives you to stop everything talking to everything: NetworkPolicy. It also covers the trap that catches almost everyone: a policy that is accepted and does nothing.

The problem

Pods run on different machines. A Pod on node A at 10.244.1.5 wants to call a Pod on node B at 10.244.2.9. Those are not real addresses on your office network. Who makes the call arrive?

And once that works, you meet the opposite worry. If every Pod can reach every other Pod, then a compromised front-end can talk straight to your database. On a plain Linux network you would use a firewall. In a cluster, the Pods keep moving, so IP-based rules cannot keep up. You need rules written in terms of labels.

Key idea

Kubernetes defines what the network must do and leaves how to a plugin. Every Pod gets its own IP. Any Pod can reach any Pod without address translation. A NetworkPolicy then narrows that, if the plugin enforces it.

The network model

Kubernetes sets down three rules, and every network plugin has to satisfy them:

  1. Every Pod gets its own IP address. Not shared with the node, not shared with other Pods.
  2. Pods can talk to all other Pods, on any node, without NAT. Pod B sees the real source IP of Pod A.
  3. Agents on a node (the kubelet, for health checks) can reach all Pods on that node.

This is a deliberately simple promise. It means your app can use plain IPs and ports, with no port mapping, as on a flat network.

Who builds it: the CNI plugin

The Container Network Interface (CNI) is a small standard. When a Pod starts, the container runtime calls the CNI plugin installed on that node and says "wire up this Pod". The plugin does the work.

  1. The runtime creates the Pod's network namespace (the one from chapter 2), held open by a tiny "sandbox" container.
  2. The plugin gives the Pod an IP from that node's Pod range.
  3. It creates a virtual cable (a veth pair) from the Pod's namespace to the node, and sets up routes.
  4. For traffic to other nodes, it uses an overlay (packets wrapped inside packets, for example VXLAN), or routing (such as BGP), or eBPF programs in the kernel.

When a Pod is deleted, the runtime calls the plugin again to clean up. If the plugin is broken, new Pods hang in ContainerCreating with a message about a failed sandbox (chapter 20).

Look at it


kubectl get pods -A -o wide
kubectl get nodes -o wide
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.podCIDR}{"\n"}{end}'
kubectl exec web -- ip addr
kubectl exec web -- ip route
  • The IP column of Pods and the INTERNAL-IP of nodes are different ranges. That is the overlay at work.
  • The jsonpath line prints each node's podCIDR: the slice of Pod addresses it hands out. (Some plugins manage their own ranges and leave this empty.)
  • ip addr inside a Pod shows a network interface with the Pod's IP, usually named eth0. ip route shows its default route, out through that virtual cable.

Unlike a Service address, a Pod IP answers ping. You can kubectl exec into one Pod and ping another's IP. That is a simple test that the Pod network works.

NetworkPolicy

By default, every Pod can talk to every other Pod, in every namespace. A NetworkPolicy is a firewall rule written in terms of labels.

Read this twice

Kubernetes accepts and stores a NetworkPolicy no matter what. It is only enforced if your CNI plugin supports it. On a cluster whose plugin does not, the policy sits in the API, kubectl get networkpolicy shows it, and nothing is blocked. The Kubernetes docs say so directly: creating a NetworkPolicy without a controller that implements it has no effect. Always test that a deny actually denies.

The rules of the game

  • No policy means open. A Pod that no policy selects accepts and sends anything.
  • A Pod is isolated once a policy selects it, for the direction (ingress, egress) that policy lists. After that, only what some policy explicitly allows gets through.
  • Policies add up. There is no "deny" rule and no order. Allowed traffic is the union of everything every policy allows.
  • Both ends must agree. For A to reach B, A's egress rules and B's ingress rules must both allow it (if both are restricted).
  • Traffic from a Pod's own node is allowed, so kubelet probes still work.

Step 1: deny everything coming in


apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: dev
spec:
  podSelector: {}
  policyTypes:
    - Ingress


podSelector: {}          an empty selector selects EVERY Pod in this namespace
policyTypes: [Ingress]   this policy is about incoming traffic
(no ingress: rules)      ...and it allows nothing, so all incoming traffic to these Pods is denied

Step 2: allow exactly what you mean


apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-client-to-web
  namespace: dev
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: client
      ports:
        - protocol: TCP
          port: 80


podSelector: app=web         the Pods being protected
ingress:
  - from:
      - podSelector: role=client   who may connect: Pods labelled role=client (same namespace)
    ports: TCP 80                  and only to this port

Together, the two policies say: nothing may reach any Pod, except role=client Pods may reach app=web on port 80. This "deny all, then allow what is needed" is the shape of every sound policy set.

Who can be in a from?


from:
  - podSelector:                  # Pods in the same namespace with this label
      matchLabels: {role: client}
  - namespaceSelector:            # all Pods in namespaces with this label
      matchLabels: {kubernetes.io/metadata.name: monitoring}
  - ipBlock:                      # an address range (for things outside the cluster)
      cidr: 203.0.113.0/24

Namespaces automatically carry the label kubernetes.io/metadata.name with their own name, so namespaceSelector can pick one by name with no extra labelling.

The AND / OR trap

Items in the from list are OR: any match allows the traffic. But selectors inside the same item are AND.


# OR: Pods labelled role=client in this namespace, OR any Pod in monitoring
from:
  - podSelector: {matchLabels: {role: client}}
  - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: monitoring}}

# AND: only Pods labelled role=client that are in the monitoring namespace
from:
  - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: monitoring}}
    podSelector: {matchLabels: {role: client}}

The difference is one dash. It is the most common NetworkPolicy bug, and a very common interview question.

Egress, and the DNS trap


spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}

If you deny egress, you also deny DNS, because looking up web means calling the cluster DNS server on port 53. Everything then fails with "could not resolve host", which looks nothing like a firewall problem. Any egress-restricting policy needs an explicit DNS allowance like the one above.

Linux you already know

  • Everything here is ordinary Linux networking. ip addr, ip route, ss -tlnp and ping work inside a Pod. ip link on a node shows the veth ends of each Pod. The kernel's network namespace from chapter 2 is the Pod's own network stack.
  • A veth pair is a virtual network cable with one end in the Pod and one on the node, plugged into a bridge or routing table, like a patch cable into a switch.
  • An overlay is a tunnel, like a VPN between nodes: packets for another node's range are wrapped and sent across the real network.
  • NetworkPolicy is ufw and iptables, written in labels. In the Linux handbook you opened port 80 with sudo ufw allow 80/tcp. A policy is the same idea, except the source is "Pods labelled role=client", which survives Pods being replaced. The plugin turns your policy into kernel rules (iptables, nftables or eBPF).
  • "Test it from outside" is the lesson from the Nginx chapter: curl on the server worked, the browser did not. A deny policy needs the same check from the Pod that should be blocked.
  • Default-deny is the same advice as least privilege (chapter 16) and as chmod 700: start closed, open what you need.

Common mistakes

Common mistake

"I applied a policy, so I am protected." Only if the CNI enforces it. On some setups, such as a bare Flannel cluster and possibly kind's default plugin, nothing is blocked. Prove it with a test.

Common mistake

Default-deny egress and then "nothing resolves". DNS is blocked. Allow UDP and TCP 53 to the cluster DNS.

Common mistake

Mixing up AND and OR. A separate dash makes an alternative. Two selectors under one dash must both match.

Common mistake

"A second policy will deny what the first allowed." Policies only add. To remove access, remove or edit the policy that grants it.

Common mistake

Forgetting the other namespaces. A podSelector in from matches Pods in the policy's own namespace. To allow another namespace, you need a namespaceSelector.

Common mistake

Using Pod IPs in ipBlock. Pod IPs change. ipBlock is for addresses outside the cluster. Inside, use labels.

Common mistake

"Namespaces already isolate the network." They do not (chapter 8). Only a NetworkPolicy does, and only on a plugin that enforces it.

Common mistake

Assuming Pod traffic is encrypted. It is plain by default. Encryption comes from the CNI (for example WireGuard options) or from a service mesh with mutual TLS.

This can break things

Applying a default-deny policy to a live namespace with no allow rules cuts off every Pod at once, including the Ingress controller's traffic and the metrics scraper. Write the allow policies first, try the whole set in a test namespace, and roll out namespace by namespace.

Try it

Try it

Part A explores the Pod network on any cluster. Part B tests NetworkPolicy. The result of Part B tells you something about your cluster: whether its plugin enforces policies. On kind's default plugin you may find that it does not (I could not confirm this for current kind releases, so the lab tests it). That is a real and useful discovery, not a mistake.

Part A: the Pod network (three-node kind cluster)


kubectl create namespace dev
kubectl create deployment web -n dev --image=nginx:1.27 --replicas=3
kubectl rollout status deployment/web -n dev
kubectl get pods -n dev -o wide                       # Pod IPs and the nodes they are on
kubectl get nodes -o wide                             # node IPs: a different range
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.podCIDR}{"\n"}{end}'

# ping between Pods on different nodes (use real IPs from the first command)
kubectl run pinger -n dev --image=busybox:1.37 --restart=Never -- sleep 3600
kubectl wait -n dev --for=condition=Ready pod/pinger --timeout=60s
kubectl exec -n dev pinger -- ip addr
kubectl exec -n dev pinger -- ip route
kubectl exec -n dev pinger -- ping -c 2 <a-web-pod-ip>

Part B: does NetworkPolicy actually block?


# a Service for web, and two clients: one labelled, one not
kubectl expose deployment web -n dev --port=80
kubectl run client -n dev --image=curlimages/curl --labels=role=client -- sleep 3600
kubectl run stranger -n dev --image=curlimages/curl -- sleep 3600
kubectl wait -n dev --for=condition=Ready pod/client pod/stranger --timeout=60s

# 1. before any policy: both can reach web
kubectl exec -n dev client   -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web
kubectl exec -n dev stranger -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web

# 2. deny all ingress (save the policy from this chapter as default-deny.yaml)
kubectl apply -f default-deny.yaml
kubectl exec -n dev client -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web
#    200 again?  Then your CNI does NOT enforce NetworkPolicy.
#    000 (timeout)? It does. Carry on.

# 3. allow only role=client (save the second policy as allow-client-to-web.yaml)
kubectl apply -f allow-client-to-web.yaml
kubectl exec -n dev client   -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web   # 200
kubectl exec -n dev stranger -- curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://web   # 000

kubectl get networkpolicy -n dev
kubectl delete namespace dev

What to look for:

  • Part A: Pod IPs in one range, node IPs in another. Pods on different nodes ping each other with no NAT. The ip route output shows a default route out through eth0.
  • Part B, step 2: the result is the point. 000 means the policy was enforced. 200 means the policy was stored but ignored, so your plugin does not enforce it.
  • If it is not enforced and you want to practise, recreate kind with the default plugin turned off and install one that enforces policy (Calico or Cilium both do; follow the project's own kind instructions). In the kind config, add networking: with disableDefaultCNI: true, then install the plugin before anything else.
  • Part B, step 3, on an enforcing cluster: client gets 200, stranger gets 000.

Interview questions

Interview

Click a question, answer out loud first, then check.

What is the Kubernetes network model?

Three rules. Every Pod gets its own IP address. Any Pod can reach any other Pod, on any node, without NAT, so the destination sees the real source IP. And agents on a node, like the kubelet, can reach every Pod on that node. Kubernetes doesn't implement this itself. The container runtime calls a CNI plugin to wire up each Pod, and the plugin makes the model true.

What is CNI, and what does a plugin do when a Pod starts?

The Container Network Interface is a standard that lets the runtime ask a plugin to set up networking. When a Pod starts, the runtime creates its network namespace and calls the plugin, which assigns an IP from that node's range, creates a virtual cable from the Pod to the node, and sets up routes. It also arranges how traffic gets to other nodes, through an overlay tunnel like VXLAN, through routing, or with eBPF. When the Pod is deleted it cleans up. Cilium, Calico and Flannel are common plugins.

How does a Pod on one node reach a Pod on another?

Each node owns a slice of the Pod address space. The packet leaves the Pod through its virtual cable to the node, and the node's routes show that the destination is in another node's slice. With an overlay, the plugin wraps the packet inside another packet addressed to that node and unwraps it on arrival. With routed setups, plain routes or BGP deliver it. Either way there's no NAT, so the receiver sees the original Pod IP.

What's the default network behaviour, and how does NetworkPolicy change it?

By default every Pod can talk to every other Pod, across namespaces, in both directions. A NetworkPolicy selects Pods by label. Once a Pod is selected for ingress or egress, it's isolated in that direction, and only what policies explicitly allow gets through. Policies are additive and have no deny rules. The catch is that a policy is only enforced if the CNI supports it. Otherwise it's stored and does nothing, so I always test.

What's the difference between two selectors in one from item and two separate items?

Separate items are OR: traffic matching any of them is allowed. Two selectors in the same item are AND: a namespaceSelector and a podSelector together mean Pods with that label in namespaces with that label. It's a single dash of difference and a common bug, because the AND form is narrower than people expect, and the OR form is wider.

You add a default-deny egress policy and everything breaks. What did you forget?

DNS. With egress denied, Pods can't reach the cluster DNS server, so name lookups fail and it looks like a general outage. I need an egress rule allowing UDP and TCP port 53 to the DNS Pods, usually in kube-system. I'd also check I haven't blocked other things they need, like the API server or metrics endpoints. And I'd have tested it in a non-production namespace first.

Habits worth keeping

Habits

Know which CNI your cluster runs and whether it enforces policy. Test a deny, never assume it. Start closed with default-deny, then allow what is needed. Allow DNS when you restrict egress. Check your dashes: AND versus OR. Use labels, not Pod IPs. And roll out policy one namespace at a time.
