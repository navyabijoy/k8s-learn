Getting a cluster on your machine

kind on macOS, MicroK8s on Ubuntu

Section 04

You learn Kubernetes by breaking a cluster, and you cannot break a production one. So you need a cluster of your own that you can destroy and rebuild in a minute. This chapter sets one up on your Mac with kind, or on Ubuntu with MicroK8s, and checks that it works.

The problem

A real cluster is many machines. You have a laptop. The Linux handbook gave you three ways to get a Linux box: a rented VPS, VirtualBox, or WSL. Kubernetes has the same choice, with one difference: the cluster itself can run inside your laptop, as containers or as one snap.

Key idea

A local cluster is a real, conformant Kubernetes with a small footprint. The commands are the same ones you use on a cloud cluster. What differs is size, speed and the missing cloud pieces (no cloud load balancers, no cloud disks).

What this handbook uses

Labs are written for kind, and the context name is kind-handbook. If you are on Ubuntu, MicroK8s works for nearly every lab: replace kubectl with microk8s kubectl, or alias it.

Install kubectl first


brew install kubectl
kubectl version --client

On Ubuntu, sudo snap install kubectl --classic does the same. --client asks only about the local program, so it works with no cluster.

Key idea

Version skew: Kubernetes supports a kubectl that is within one minor version of the cluster's API server, newer or older. kubectl 1.36 against a 1.35 cluster is fine. A kubectl two or more versions away may misbehave. Check both with kubectl version once you have a cluster.

Option A: kind on macOS

kind means "Kubernetes IN Docker". It starts a Docker container for each node, and inside each container it runs a full node: the kubelet, a container runtime, and the control-plane programs on the control-plane node. Docker (or Podman, or nerdctl, which kind can detect) must be running first.


brew install kind
kind create cluster --name handbook
kubectl cluster-info --context kind-handbook
kubectl get nodes
  • kind create cluster --name handbook builds a one-node cluster and writes a context to your kubeconfig.
  • The context is named kind- plus the cluster name: kind-handbook. kind also switches kubectl to it.
  • cluster-info prints the API server address. get nodes should show one node Ready after a short wait.

A three-node cluster, like a real one

Most chapters that follow behave more interestingly with more than one node (scheduling, taints, DaemonSets). Describe the shape in a file:


kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker


kind delete cluster --name handbook
kind create cluster --name handbook --config kind-3node.yaml
kubectl get nodes
  • The file is a kind config, not a Kubernetes manifest. Its apiVersion belongs to kind.
  • You should see three nodes: one with the control-plane role, two with none. Workers show <none> in ROLES because that is what a plain worker looks like.

Everyday kind commands


kind get clusters
kind load docker-image my-app:1.0 --name handbook
kind delete cluster --name handbook
  • get clusters lists what you have.
  • load docker-image copies an image you built locally into the cluster nodes. Without it, the nodes cannot see your laptop's Docker images. Use a tag other than latest, or set imagePullPolicy: IfNotPresent, or the kubelet will try to pull from a registry and fail.
  • delete cluster removes the nodes and the kubeconfig entry. Recreating takes about a minute. That is the point: if you make a mess, delete and start again.

Option B: MicroK8s on Ubuntu


sudo snap install microk8s --classic
microk8s status --wait-ready
microk8s kubectl get nodes
alias kubectl='microk8s kubectl'
  • The install is a standard snap install. --classic means it is not sandboxed. Chapter 22 explains snaps.
  • status --wait-ready blocks until the cluster is up.
  • The alias makes every kubectl command in this handbook work unchanged in that shell.

On macOS, Canonical documents brew install ubuntu/microk8s/microk8s followed by microk8s install. Chapter 22 covers MicroK8s clusters, add-ons and joining nodes.

Linux you already know

  • Why do we use a Linux machine at all? Because every Kubernetes node is a Linux machine. kind nodes are Linux containers. MicroK8s is a Linux snap. On a Mac, Docker Desktop quietly runs a small Linux VM underneath, just like VirtualBox in the Linux handbook, so there is still a Linux kernel doing the work.
  • A kind node is a container, but you can go in like it is a server: docker exec -it handbook-control-plane bash, then ps aux, systemctl status kubelet, ls /etc/kubernetes/manifests. Same tools as the Linux handbook.
  • docker ps shows your nodes as containers named handbook-control-plane and handbook-worker. A cluster inside containers, and your Pods run in containers inside those. Containers all the way down, because it is all Linux processes.
  • Resource limits are the same story: a three-node kind cluster is three containers sharing your laptop's RAM. Give Docker Desktop enough memory in its settings.

Common mistakes

Common mistake

"kubectl says connection refused." The cluster is not running, or kubectl points somewhere else. Check Docker is running, then kubectl config current-context.

Common mistake

"My local image will not start: ErrImagePull." The cluster cannot see your laptop's images. Run kind load docker-image, and avoid the latest tag.

Common mistake

"My LoadBalancer Service stays <pending>." A laptop cluster has no cloud to hand out addresses. Use kubectl port-forward, or, with kind, the cloud-provider-kind project from the kind maintainers. Nothing is broken.

Common mistake

Installing MicroK8s or the k8s snap on a machine that already runs Docker. Canonical's docs warn about conflicts. Use a clean machine or VM.

Common mistake

"This laptop cluster is how production works." It is a good model of the API. It is not a model of production: no real load balancer, usually one control-plane node, local storage only, and nothing is highly available.

This can break things

A machine can hold several contexts at once: your kind cluster, a staging cluster, production. Before any kubectl delete, run kubectl config current-context. A cluster you built an hour ago is safe to destroy. The other ones are not.

Try it

Try it

Build the three-node cluster, prove it works, look inside a node, and tear it down. Save the config from this chapter as kind-3node.yaml.


# 1. is Docker running?
docker ps

# 2. create the cluster
kind create cluster --name handbook --config kind-3node.yaml

# 3. check it
kubectl config current-context
kubectl version
kubectl get nodes -o wide
kubectl get pods -A

# 4. run something
kubectl run web --image=nginx:1.27
kubectl wait --for=condition=Ready pod/web --timeout=90s
kubectl get pod web -o wide
kubectl port-forward pod/web 8080:80
# second terminal: curl -I localhost:8080

# 5. nodes are containers
docker ps --format '{{.Names}}'
docker exec -it handbook-control-plane bash
ls /etc/kubernetes/manifests
exit

# 6. clean up the Pod, or start over completely
kubectl delete pod web
kind delete cluster --name handbook

What to look for:

  • Step 3: three nodes, all Ready; the client and server versions printed by kubectl version are within one minor version of each other; the kube-system Pods are the ones from chapter 3.
  • Step 4: get pod -o wide shows which worker node the Pod landed on, and that it was not the control-plane node.
  • Step 5: the nodes are containers. The manifests folder holds the static Pod YAML for the control-plane programs.

Interview questions

Interview

Click a question, answer out loud first, then check.

How does kind work?

kind starts one Docker container per node, and each container is a full Kubernetes node image: kubelet, container runtime, and for the control-plane node the API server, etcd, scheduler and controller manager. It writes a kubeconfig context called kind-NAME. So I get a real multi-node cluster on a laptop, which I can delete and recreate in about a minute. It's good for local development and for CI.

What local Kubernetes options have you used, and when would you pick each?

I use kind for throwaway multi-node clusters, especially on a Mac and in CI. On Ubuntu I'd use MicroK8s, which is one snap and can run as a small real HA cluster, or Canonical Kubernetes if I want Canonical's newer distribution. Docker Desktop's built-in Kubernetes is the quickest single-node option if Docker Desktop is already installed. The choice is mostly about nodes: kind and MicroK8s give me several, Docker Desktop one.

How much can your kubectl version differ from the cluster's?

One minor version in either direction is supported. So kubectl 1.36 works against a 1.35, 1.36 or 1.37 API server. More than that and some commands may fail or behave oddly. I check both with kubectl version.

My locally built image won't run in kind. Why?

The kind nodes are containers with their own image store. They can't see images in my laptop's Docker. I need kind load docker-image to copy it in. Then I make sure the tag isn't latest, or set imagePullPolicy: IfNotPresent, because latest defaults to always pulling, and the pull would fail because the image isn't in a registry.

Why is a laptop cluster not a good model of production?

The API behaves the same, but the surroundings don't. There's no real load balancer, so LoadBalancer Services stay pending. Storage is local disk. There's usually one control-plane node, so no high availability. There's no real network separation or node failure. So I trust it for learning the objects and testing manifests, not for judging reliability or performance.

Habits worth keeping

Habits

Rebuild instead of repairing a lab cluster. Name your clusters and check the context before you run anything destructive. Keep the kind config in a file. Match kubectl to the cluster within one minor version. Load local images with kind load docker-image. And treat a laptop cluster as a place to learn the objects, not to judge production behaviour.
