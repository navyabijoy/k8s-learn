Services and cluster DNS

A stable address in front of changing Pods

Section 09

Pods come and go, and every new Pod gets a new IP. So how does one app find another? A Service is the answer: a stable name and address in front of a changing set of Pods. This chapter shows how it works, how to look inside it, and how to find out why it is empty.

The problem

You have a Deployment with three web Pods. Each has its own IP. A new app, frontend, needs to call them.

You cannot hardcode a Pod IP. Chapter 7 showed that Pods are replaced all the time, and a replacement has a different IP. You also do not want frontend to keep a list of three addresses and pick one. That list would change every few minutes.

You want one name that always works, and something behind it that knows who is alive right now.

Key idea

A Service gives a set of Pods one stable virtual IP and one DNS name. It finds its Pods by label, and it only sends traffic to Pods that are ready.

Think of it as

A company's main phone number. Callers dial one number. Whoever is on shift picks up. People change shifts, the number stays.

Stable

The Service IP and name do not change for the life of the Service, however many Pods come and go behind it.

Label based

The Service does not list Pods by name. It says "any Pod with app: web", and the cluster keeps the list up to date.

Not a process

There is no program listening on a Service IP. It is a rule on each node that rewrites the address to a real Pod.

Your first Service

This Service goes in front of the web Deployment from chapter 7:


apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80


spec:
  selector:
    app: web         which Pods: any with this label (same label as the Deployment's Pods)
  ports:
    - port: 80       the port the SERVICE listens on
      targetPort: 80 the port on the POD it forwards to

port and targetPort are the two people mix up. Think of a hotel: port is the number guests dial at reception, targetPort is the room the call is put through to. They can differ. A Service on port 80 can forward to a Pod listening on 8080:


ports:
  - port: 80
    targetPort: 8080


kubectl apply -f web-svc.yaml
kubectl get service web
kubectl describe service web
kubectl get endpointslices -l kubernetes.io/service-name=web
  • get service shows the CLUSTER-IP (the virtual address) and ports.
  • describe service has an Endpoints: line listing the Pod IPs currently behind it. If that line is empty, nothing works. More on that below.
  • get endpointslices shows the same list from the object that actually stores it. (The older Endpoints object is deprecated since Kubernetes 1.33. kubectl get endpoints still works, but EndpointSlices are the real thing.)

How it works

Two pieces, both automatic:

  1. The list. A controller watches Pods. For each Service it keeps an EndpointSlice: the IPs of Pods that match the selector and are ready. A Pod that fails its readiness probe is removed from the list. When it recovers, it comes back.
  2. The rules. On every node, kube-proxy (or the network plugin, if it replaces kube-proxy) turns that list into kernel rules: "traffic to 10.96.x.x:80 goes to one of these Pod IPs". On Linux those are iptables, IPVS or nftables rules.
Pod calls web:80→node rule matches the Service IP→rewritten to one ready Pod IP→Pod answers
Key idea

The balancing happens per connection, on the client's node. It is not a proxy sitting in the middle. That has a famous side effect: a client that opens one long-lived connection (gRPC, HTTP/2, a database pool) sticks to a single Pod, and the other Pods get nothing.

The types build on each other: a LoadBalancer also gets a NodePort, and a NodePort also gets a ClusterIP.


spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080

Skip nodePort and the cluster picks one for you. Pinning it is only useful for demos.

Key idea

A LoadBalancer Service only gets an address if something provides load balancers: a cloud, MetalLB on bare metal, or cloud-provider-kind on kind. Without one, EXTERNAL-IP stays <pending> forever. Nothing is broken. Nothing is answering the request.

Cluster DNS

You do not type the Service IP. You type the name. The cluster runs a DNS server (CoreDNS) and every Pod is pointed at it. A Service named web in namespace dev gets this name:


web . dev . svc . cluster.local
│     │     │     │
│     │     │     └─ the cluster's domain (default)
│     │     └─────── "this is a Service"
│     └───────────── namespace
└─────────────────── Service name

Three ways to call the same Service, from a Pod:


curl http://web
curl http://web.dev
curl http://web.dev.svc.cluster.local
  • Plain web works only from the same namespace.
  • web.dev works from any namespace.
  • The full name always works. Use it in config that crosses namespaces.

Why does the short name work? Look at the resolver file inside any Pod. This is the file from the Linux handbook's filesystem chapter:


kubectl exec -n dev deploy/web -- cat /etc/resolv.conf

It lists the cluster DNS server as nameserver, plus a search line with dev.svc.cluster.local svc.cluster.local cluster.local and options ndots:5. The search line is a list of suffixes the resolver tries in turn. You typed web, so it tries web.dev.svc.cluster.local first, and that matches. It is the same trick as PATH: you type the short name, the system tries a list of places.

Linux you already know

  • A Service is a small version of what nginx as a reverse proxy did in the Linux handbook: one address, many backends. The difference is that the "config" is rebuilt automatically from labels, and it is kernel rules, not a program.
  • kube-proxy writes iptables (or IPVS or nftables) rules. On a node you can see them: sudo iptables -t nat -L KUBE-SERVICES on a cluster that uses iptables mode. Kubernetes is configuring the Linux kernel's own packet rewriting.
  • /etc/resolv.conf and its search line are plain Linux DNS. Tools you know, nslookup and dig, work inside Pods that have them.
  • Cluster DNS names behave like entries in /etc/hosts that you never edit.

When a Service does not work

Nine times in ten, the Service has no endpoints. Check in this order:

  1. kubectl get endpointslices -l kubernetes.io/service-name=web. Empty ENDPOINTS means no Pod is selected and ready.
  2. kubectl get pods --show-labels. Do the Pods carry exactly the labels in the Service selector? A typo (app: wbe) is the usual cause.
  3. kubectl get pods. Are the Pods READY 1/1? A Pod failing its readiness probe is removed from the list on purpose.
  4. Is targetPort the port the app really listens on? kubectl exec in and check.
  5. Is the call from the right namespace, or using the full name?

Common mistakes

Common mistake

Selector does not match the Pod labels. The Service creates fine and silently selects nothing. This is the number one Service bug. Compare the Service selector against the labels on the Pods, not the labels on the Deployment.

Common mistake

Mixing up port and targetPort. port is what clients use on the Service. targetPort is where the Pod listens. If they differ and you set only port, the traffic goes to the wrong place.

Common mistake

"I'll ping the Service IP." It will not answer. The IP is virtual, and only the ports you listed are forwarded. Test with curl or nc to the port, not ping.

Common mistake

Calling the short name across namespaces. curl http://web from namespace prod looks for web.prod. Use web.dev or the full name.

Common mistake

"A Service balances requests evenly." It balances connections, and without any guarantee of fairness. Long-lived connections pin to one Pod. For gRPC you need client-side balancing, a headless Service, or a proxy that understands the protocol.

Common mistake

Using NodePort as your production entry point. It exposes a high port on every node and has no names, no TLS, no routing. Put an Ingress or Gateway in front (next chapter), or a LoadBalancer.

This can break things

A type: LoadBalancer Service on a real cloud creates a billable load balancer with a public address. Deleting the Service deletes it. Forgetting one costs money, and exposing an internal app by accident is a security incident.

Try it

Try it

On the kind cluster from chapter 4. This lab uses the Deployment from chapter 7 and the Service from this chapter, in a scratch namespace.


# 1. set up
kubectl create namespace dev
kubectl apply -n dev -f web-deploy.yaml
kubectl apply -n dev -f web-svc.yaml
kubectl rollout status deployment/web -n dev

# 2. look at the Service and what is behind it
kubectl get service web -n dev
kubectl describe service web -n dev
kubectl get endpointslices -n dev -l kubernetes.io/service-name=web
kubectl get pods -n dev -o wide

# 3. call it by name from inside the cluster
kubectl run tmp -n dev --rm -it --restart=Never --image=curlimages/curl -- curl -s http://web
kubectl run tmp -n dev --rm -it --restart=Never --image=curlimages/curl -- curl -s http://web.dev.svc.cluster.local

# 4. call it from your laptop
kubectl port-forward -n dev service/web 8080:80
# second terminal: curl -I localhost:8080

# 5. watch the list follow the Pods
kubectl get endpointslices -n dev -l kubernetes.io/service-name=web --watch
# second terminal:
kubectl scale deployment web -n dev --replicas=5
kubectl scale deployment web -n dev --replicas=1

# 6. break the selector on purpose
kubectl patch service web -n dev -p '{"spec":{"selector":{"app":"wbe"}}}'
kubectl describe service web -n dev
kubectl run tmp -n dev --rm -it --restart=Never --image=curlimages/curl -- curl -s -m 3 http://web
# fix it again
kubectl patch service web -n dev -p '{"spec":{"selector":{"app":"web"}}}'

# 7. clean up
kubectl delete namespace dev

What to look for:

  • Step 2: the Pod IPs in get pods -o wide are the same ones in the EndpointSlice and in the Endpoints: line of describe.
  • Step 3: the nginx welcome page, from a name, not an IP.
  • Step 5: addresses appear and disappear as the replica count changes. The Service IP never changes.
  • Step 6: Endpoints: becomes <none> and the curl times out. Same Service, same Pods, one typo. That is the failure you will see most in real life.

Interview questions

Interview

Click a question, answer out loud first, then check.

Why do we need Services when Pods have IPs?

Because Pod IPs aren't stable. Pods are replaced all the time, and each replacement gets a new IP. A Service gives a set of Pods one virtual IP and one DNS name that don't change. It selects Pods by label and only sends traffic to ready ones, so clients don't need to know which Pods exist right now.

How does a Service actually route traffic?

A controller keeps EndpointSlices, which are the IPs of ready Pods matching the selector. On every node, kube-proxy, or the CNI if it replaces kube-proxy, turns that into kernel rules: iptables, IPVS or nftables. When a Pod connects to the Service IP, the rule on its own node rewrites the destination to one of the Pod IPs. There's no process in the middle. It also means balancing is per connection.

What's the difference between ClusterIP, NodePort and LoadBalancer?

ClusterIP is the default: a virtual IP reachable only inside the cluster. NodePort adds a port, 30000 to 32767 by default, opened on every node, so you can reach it from outside by node IP. LoadBalancer builds on NodePort and asks the cloud to create an external load balancer pointing at the nodes. Each includes the one before it. For HTTP traffic I'd normally put an Ingress or Gateway in front of ClusterIP Services instead of one LoadBalancer per app.

A Service has no endpoints. How do you debug it?

I check the EndpointSlice first. If it's empty, I compare the Service selector with the labels on the Pods, because a typo there is the most common cause. Then I check the Pods are actually Ready, since a failing readiness probe removes them on purpose. Then I check targetPort matches the port the app listens on, and that I'm calling from the right namespace.

How does DNS work for Services?

CoreDNS runs in the cluster and every Pod's resolv.conf points at it. A Service gets the name name.namespace.svc.cluster.local. Inside the same namespace the short name works because of the search line in resolv.conf. From another namespace I use name.namespace or the full name. A headless Service returns the Pod IPs directly instead of one virtual IP.

Habits worth keeping

Habits

Talk to Services by name, never by Pod IP. Check the EndpointSlice first when a Service misbehaves. Match the selector to the Pod labels exactly. Use curl, not ping, to test. Keep NodePort for demos, and put real traffic through Ingress or Gateway. And remember that a Service balances connections, not requests.
