StatefulSets, DaemonSets, Jobs, CronJobs

The other ways to run Pods

Section 14

A Deployment treats every Pod as interchangeable. That is exactly wrong for a database, a node agent, a nightly backup. Kubernetes has a controller for each of those jobs. This chapter is a guided tour of four: StatefulSets, DaemonSets, Jobs and CronJobs, and a rule for picking between them.

The problem

The Deployment from chapter 7 assumes three things that are not always true.

  • Pods are identical and replaceable. A database replica is not. db-0 is the primary and db-1 is a follower, and each has its own disk.
  • Pods go anywhere. A log collector must run on every node, exactly once.
  • Pods run forever. A backup runs, finishes, and should not be restarted.

One controller cannot do all four, so there are four.

Key idea

Choose the controller by asking: Is each Pod special? Must there be one per node? Does it finish? Does it repeat on a schedule?

StatefulSet

Stable names

Pods are web-0, web-1, web-2, not random hashes. If web-1 is replaced, the new one is called web-1 again.

Stable storage

Each Pod gets its own PVC, created from a template. web-1 always reattaches to its disk.

Stable DNS

Each Pod gets its own DNS name through a headless Service: web-0.web.

Ordered

Starts web-0 first, waits until it is ready, then web-1. Stops in reverse order.


apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - port: 80
      name: http
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
              name: http
          volumeMounts:
            - name: www
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: www
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi


Service web, clusterIP: None   a HEADLESS Service: no virtual IP, DNS returns the Pod IPs
StatefulSet web
  serviceName: web             the headless Service that gives the Pods their DNS names
  replicas: 2                  creates web-0 then web-1
  volumeClaimTemplates:        a PVC is made PER Pod from this template:
    - name: www                  www-web-0, www-web-1

Compare with the Deployment: the Pod template is the same. What is new is serviceName and volumeClaimTemplates.

The DNS name


web-0 . web . dev . svc . cluster.local
│       │     │
│       │     └─ namespace
│       └─────── the headless Service (serviceName)
└─────────────── the Pod name

An ordinary Service gives you one name for the group. A headless Service plus a StatefulSet also gives you one name per Pod. That is how a database follower can say "connect to db-0", whichever node it is on today.

What a StatefulSet does not do

Key idea

A StatefulSet gives each Pod an identity and a disk. It does not know how to set up replication, elect a primary, or take backups. Running a PostgreSQL cluster still needs that logic. That is what operators (chapter 19) add on top of a StatefulSet.

Scaling and deleting

  • Scaling up adds web-2 after web-1 is ready. Scaling down removes the highest number first.
  • The PVCs stay. By default, scaling down or deleting a StatefulSet does not delete its PVCs. Newer versions have a persistentVolumeClaimRetentionPolicy field if you want that. The default is the safe one: data is not lost by accident.
  • Updates are rolling, one Pod at a time, from the highest number down. A partition setting lets you update only some Pods first, as a canary.

DaemonSet

A DaemonSet runs one Pod on every node (or every node matching a selector). Add a node and it gets one. Remove a node and that Pod is cleaned up. You do not set a replica count.


apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
      containers:
        - name: agent
          image: busybox:1.37
          command: ["sh", "-c", "while true; do echo \"agent on $NODE_NAME\"; sleep 30; done"]
          env:
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
  • There is no replicas. The number of Pods is the number of matching nodes.
  • The tolerations block lets it run on control-plane nodes, which are tainted by default (chapter 15). Without it, the agent would skip them.
  • The fieldRef hands the Pod its own node's name as an environment variable. This is the "downward API": a Pod reading facts about itself.

Real DaemonSets you already have: the network plugin (chapter 17), kube-proxy on many clusters, and log and metrics collectors (chapter 21). Run kubectl get daemonset -A on any cluster to see them.

Job

A Job runs Pods until they succeed, then stops. A Deployment would restart a finished container forever. A Job treats "exit 0" as the goal.


apiVersion: batch/v1
kind: Job
metadata:
  name: backup
spec:
  backoffLimit: 3
  ttlSecondsAfterFinished: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: backup
          image: busybox:1.37
          command: ["sh", "-c", "echo backing up; sleep 5; echo done"]


backoffLimit: 3             retry a failing Pod up to 3 times before giving up (default is 6)
ttlSecondsAfterFinished: 300 delete the Job and its Pods 5 minutes after it finishes
restartPolicy: Never        REQUIRED to be Never or OnFailure. Always is not allowed in a Job.
(completions: 1)            how many successful Pods are needed (default 1)
(parallelism: 1)            how many to run at once (default 1)
(activeDeadlineSeconds:)    kill the whole Job if it runs longer than this


kubectl apply -f backup-job.yaml
kubectl get job backup
kubectl logs job/backup
kubectl get pods -l job-name=backup
  • COMPLETIONS 1/1 in get job means done.
  • logs job/backup reads the Job's Pod. Add -f to follow.
  • Finished Pods stay as Completed so you can read their logs, until the TTL deletes them. Without a TTL, they stay forever.

Set completions: 5 and parallelism: 2 and the Job runs five tasks, two at a time. That is how you fan out a batch of work.

CronJob

A CronJob creates a Job on a schedule. The schedule is the same five fields as the Linux crontab: minute, hour, day of month, month, day of week.


apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "*/1 * * * *"
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 2
      ttlSecondsAfterFinished: 300
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: hello
              image: busybox:1.37
              command: ["sh", "-c", "date; echo hello from the cluster"]


schedule: "*/1 * * * *"       every minute. Same fields as crontab: min hour dom month dow
timeZone: "Etc/UTC"           which time zone the schedule uses (leave out for the controller's default)
concurrencyPolicy: Forbid     if the last run is still going, skip this one
successfulJobsHistoryLimit: 3 keep the last 3 successful Jobs (the default)
failedJobsHistoryLimit: 1     keep the last 1 failed Job (the default)
jobTemplate:                  a normal Job spec: the thing to run each time
concurrencyPolicyIf the previous run is still going when the next is due
Allow (default)start the new one anyway. Runs overlap.
Forbidskip the new run.
Replacestop the old run and start the new one.

One honest caveat from the Kubernetes docs: a CronJob can occasionally create a Job twice, or miss one. Write jobs so running twice is harmless (idempotent).


kubectl get cronjob
kubectl get jobs --watch
kubectl create job manual-run --from=cronjob/hello
kubectl patch cronjob hello -p '{"spec":{"suspend":true}}'
  • get jobs --watch shows a new Job each minute.
  • create job --from=cronjob/hello runs the CronJob's job once, right now. Good for testing a schedule you cannot wait for.
  • suspend: true pauses it without deleting it.

Linux you already know

  • StatefulSet pods are named servers. In the Linux handbook, harry and alice each had their own /home directory that stayed theirs. web-0 and web-1 each have their own volume that stays theirs. A Deployment's Pods are more like anonymous workers sharing a pool.
  • A DaemonSet is "install this on every server". Think of adding a monitoring package with apt install to each machine, except new machines get it automatically.
  • A Job is a script you run to completion and check the exit code of: 0 is success, anything else is a failure to retry. backoffLimit is a retry loop.
  • A CronJob is cron. The five fields are the ones from the Linux handbook: */5 * * * * is every five minutes, 0 2 * * * is 02:00 daily, 0 3 * * 0 is Sunday at 3 a.m. The handbook's warnings carry over: use absolute things, redirect or collect output, and do not assume the job ran because you added it.
  • The time zone question is the same one the handbook raised: cron uses the server's zone. A CronJob without timeZone uses the controller's zone, so set it.

Common mistakes

Common mistake

Running a database as a Deployment. Its Pods have random names, share a claim, and can start in parallel. A StatefulSet, or better an operator built on one, is the right tool.

Common mistake

"A StatefulSet makes my database highly available." It gives identity and storage. Replication, failover and backups still need software that does it: the database's own clustering, or an operator.

Common mistake

No headless Service for a StatefulSet. serviceName must name a Service that exists, with clusterIP: None, or the per-Pod DNS names do not work.

Common mistake

"I deleted the StatefulSet, so the data is gone." The PVCs are still there, on purpose. Delete them yourself when you are sure.

Common mistake

restartPolicy: Always in a Job. It is rejected. A Job's Pods must use Never or OnFailure, because a finished container must stay finished.

Common mistake

Jobs piling up. Without ttlSecondsAfterFinished, finished Jobs and their Pods stay. A CronJob every minute leaves hundreds. Set the TTL, and the history limits on a CronJob.

Common mistake

Overlapping CronJob runs. A backup that takes longer than its interval starts a second copy by default (Allow). Use Forbid unless overlap is safe.

Common mistake

A heavy DaemonSet. Whatever it requests, you pay on every node. Ten nodes means ten copies of that CPU and memory request.

This can break things

kubectl delete job NAME deletes its Pods and their logs, even a running backup in the middle of its work. And --force --grace-period=0 on a StatefulSet Pod can leave two copies of the same Pod alive, both writing to one disk.

Try it

Try it

Best on the three-node kind cluster from chapter 4, so the DaemonSet has several nodes to spread over. Use a scratch namespace.


kubectl create namespace dev

# ---- StatefulSet ----
kubectl apply -n dev -f web-sts.yaml
kubectl get pods -n dev --watch                  # web-0 first, then web-1 (Ctrl+C when both are Running)
kubectl get pvc -n dev                           # www-web-0 and www-web-1
kubectl exec -n dev web-0 -- sh -c 'echo "I am web-0" > /usr/share/nginx/html/index.html'
kubectl delete pod web-0 -n dev
kubectl wait -n dev --for=condition=Ready pod/web-0 --timeout=90s
kubectl exec -n dev web-0 -- cat /usr/share/nginx/html/index.html     # same name, same data
kubectl run tmp -n dev --rm -it --restart=Never --image=curlimages/curl -- curl -s http://web-0.web
kubectl scale statefulset web -n dev --replicas=0
kubectl get pvc -n dev                           # still there

# ---- DaemonSet ----
kubectl apply -n dev -f node-agent.yaml
kubectl get daemonset -n dev
kubectl get pods -n dev -l app=node-agent -o wide    # one per node

# ---- Job ----
kubectl apply -n dev -f backup-job.yaml
kubectl get job backup -n dev --watch
kubectl logs -n dev job/backup

# ---- CronJob ----
kubectl apply -n dev -f hello-cron.yaml
kubectl get jobs -n dev --watch                  # wait for two runs, then Ctrl+C
kubectl patch cronjob hello -n dev -p '{"spec":{"suspend":true}}'
kubectl create job -n dev manual-run --from=cronjob/hello

# clean up (this also deletes the PVCs)
kubectl delete namespace dev

What to look for:

  • StatefulSet: the order (web-0 ready before web-1 starts), the per-Pod PVCs, and the same name and same data after deleting web-0. The curl to web-0.web returns the text you wrote.
  • After scaling to 0, the PVCs remain. That is the "data is not lost by accident" default.
  • DaemonSet: the number of Pods equals the number of nodes, including the control-plane node because of the toleration.
  • Job: 1/1 completions, and the log shows done.
  • CronJob: a new Job about every minute, and no overlapping ones.

Interview questions

Interview

Click a question, answer out loud first, then check.

When would you use a StatefulSet instead of a Deployment?

When each replica needs a stable identity and its own storage: databases, message brokers, anything where Pod 0 is different from Pod 1. A StatefulSet gives stable names like db-0, a PVC per Pod from volumeClaimTemplates that reattaches to the same Pod, per-Pod DNS through a headless Service, and ordered startup and shutdown. A Deployment's Pods are interchangeable and share one template, which suits stateless apps. And a StatefulSet doesn't do replication or failover by itself. That needs the application's own clustering, or an operator.

What's a DaemonSet, and what's it used for?

It runs exactly one Pod on every node, or every node matching a selector, and adds or removes Pods as nodes come and go. I use it for things that must run per node: log and metrics collectors, the CNI network plugin, kube-proxy, storage drivers, security agents. Control-plane nodes are tainted, so a DaemonSet needs a toleration if it should run there too.

What's the difference between a Job and a CronJob?

A Job runs Pods to completion: it retries failures up to a backoff limit, and finishes when enough Pods succeed. A CronJob is a schedule that creates a Job at the right times, using the same five-field cron syntax as Linux. So I use a Job for one-off work like a migration, and a CronJob for repeating work like a nightly backup. Both need restartPolicy Never or OnFailure.

How do you stop CronJob runs from overlapping, and what else can go wrong?

Set concurrencyPolicy: Forbid so a new run is skipped if the last is still going, or Replace to stop the old one. Other things to watch: set timeZone so the schedule is what I expect, set ttlSecondsAfterFinished and the history limits so finished Jobs don't pile up, and remember the docs say a run can occasionally happen twice or be missed, so jobs should be idempotent.

How does DNS work for StatefulSet Pods?

The StatefulSet's serviceName points at a headless Service, one with clusterIP: None. Because it has no virtual IP, DNS returns the Pod IPs, and each Pod also gets its own record, pod-name.service.namespace.svc.cluster.local, for example web-0.web.dev.svc.cluster.local. The Pod name is stable across restarts, so other members can always find web-0 even though its IP changes.

Habits worth keeping

Habits

Ask the four questions before picking a controller. Never run a database as a plain Deployment. Remember a StatefulSet gives identity, not clustering. Set a TTL on Jobs and a concurrencyPolicy and timeZone on CronJobs. Make scheduled work idempotent. And budget a DaemonSet's cost times the number of nodes.
