When it's broken

A fixed path: describe, logs, events

Section 20

Sooner or later a Pod is Pending, or ImagePullBackOff, or CrashLoopBackOff, and someone is waiting. The Linux handbook ended its troubleshooting advice with a path, not a list of commands: status, logs, process list, top. Kubernetes has the same kind of path. This chapter gives you the one to use every time.

The problem

The cluster has dozens of moving parts and the status words look alarming. The beginner mistake is to try random things: delete the Pod, restart the Deployment, change a value, hope. That hides evidence and teaches nothing.

The cluster already writes down what went wrong. You just need to look in the right places, in the right order.

Key idea

Always go get, describe, logs. get says what state the Pod is in. describe says why (read the Events at the bottom). logs says what the app itself said.

kubectl get pods→kubectl describe pod→kubectl logs (--previous)→kubectl get events→kubectl exec / debug

The fixed path


kubectl get pods
kubectl describe pod web-6d4cf56db6-abcde
kubectl logs web-6d4cf56db6-abcde
kubectl logs web-6d4cf56db6-abcde --previous
kubectl get events --sort-by=.lastTimestamp
  • 1. get pods: read READY, STATUS, RESTARTS. The STATUS word decides which section of this chapter you need.
  • 2. describe pod: scroll to Events: at the bottom. Almost every infrastructure problem (can't schedule, can't pull, can't mount) is written there in plain words. Also read State and Last State under each container.
  • 3. logs: what the application printed. If the container restarted, add --previous to read the last crashed run, which is usually the one you want.
  • 4. get events: events for the whole namespace, newest last. Use it when the Pod is gone but you want to know what happened to it.

Who wrote that line?

In Events, the From column names the component that wrote it. It tells you whose problem it is:

FromMeansTypical problem
default-schedulerplacementno node fits (FailedScheduling)
kubeletthe node tried to run itimage pull, mounts, probes, crashes
deployment-controller / replicaset-controllerobject managementquota exceeded, can't create Pods
node-controllernode healthnode unreachable, evictions
Key idea

Events are only kept for about one hour by default. If the trouble was yesterday, describe will show nothing. That is when you need logs from your logging system (chapter 21).

Reading the status word

Pending: no node yet, or not started

The Pod exists, but the scheduler has not placed it, or the node has not finished setting it up. Run describe and read the events. Look for FailedScheduling:

Event saysCauseFix
Insufficient cpu / Insufficient memoryrequests are bigger than any node has freelower the requests, or add capacity
node(s) had untolerated taintnodes are tainted and the Pod does not tolerate it (chapter 15)add a toleration, or use other nodes
didn't match Pod's node affinity/selectornodeSelector or affinity matches no nodefix the labels or the selector
unbound immediate PersistentVolumeClaimsthe PVC has no volume (chapter 12)fix the claim or the StorageClass

ImagePullBackOff / ErrImagePull: can't get the image

The kubelet tried to download the image and failed. ErrImagePull is the failure. ImagePullBackOff is the waiting between retries, which grow longer each time. The Events line gives the real error. The usual causes:

  • A typo in the image name or tag. (manifest unknown or not found)
  • A private registry with no credentials. (unauthorized: you need an imagePullSecret)
  • The registry is unreachable from the node, or you hit a rate limit.

CrashLoopBackOff: it starts, then dies, again and again

The container exits, the kubelet restarts it, it exits again. The kubelet waits longer between each try. CrashLoopBackOff is that waiting. The Pod is fine. The app keeps exiting.

  1. kubectl logs POD --previous. This is the last run's output, and it usually names the error: missing environment variable, cannot connect to database, bad config file.
  2. kubectl describe pod POD. Under Last State: Terminated, read Reason and Exit Code.
  3. If there are no logs at all, the process died before printing. Check the command and args and the image's entrypoint.

The exit code is a clue, just like in a shell script:

Exit codeUsually means
0exited cleanly. For a long-running app that is itself a bug: it finished and stopped.
1the app hit an error and quit. Read the logs.
126 / 127command found but not executable / command not found
137killed with SIGKILL (128 + 9). Most often OOMKilled: it hit the memory limit.
139segmentation fault (128 + 11)
143stopped by SIGTERM (128 + 15). Normal when the Pod is being deleted.

The rule is the Linux one: anything above 128 means "killed by signal (code minus 128)".

When logs are not enough


kubectl logs -f web-6d4cf56db6-abcde
kubectl logs -l app=web --tail=50 --all-containers
kubectl exec -it web-6d4cf56db6-abcde -- sh
kubectl debug -it web-6d4cf56db6-abcde --image=busybox:1.37 --target=nginx
  • logs -f follows the log live. -l app=web reads from every Pod with that label. --tail=50 limits the amount. --all-containers includes sidecars.
  • exec -it ... -- sh opens a shell, if the image has one. Many modern slim images have none.
  • kubectl debug solves that. It attaches a temporary ephemeral container with the tools you choose (here busybox) to the running Pod. --target=nginx makes it share the process namespace of the nginx container, so you can see its processes.

Two more kubectl debug forms:


kubectl debug web-6d4cf56db6-abcde -it --copy-to=web-debug --container=nginx -- sh
kubectl debug node/worker-1 -it --image=ubuntu
  • --copy-to makes a copy of the Pod to experiment on, so the original keeps serving.
  • debug node/NAME starts a Pod on that node with the node's filesystem mounted under /host. It is the way to read a node's files and logs without SSH.

The node itself


kubectl get nodes
kubectl describe node worker-1

describe node lists Conditions: Ready, MemoryPressure, DiskPressure, PIDPressure. Any of them True (except Ready) explains evictions. If the node is NotReady, go to the node and treat it like any Linux machine: systemctl status kubelet and journalctl -u kubelet -n 50.

When the app is unreachable

The request path from chapters 9 and 10 gives you the order to check. Start at the app and work outwards, or at the user and work in. Either way, one layer at a time.

Pod running and ready?→Service has endpoints?→right port and name?→Ingress / Gateway rule?→DNS and firewall?
  1. kubectl get pods: is it Running and READY 1/1?
  2. kubectl get endpointslices -l kubernetes.io/service-name=web: any addresses? If empty, the selector or readiness is wrong.
  3. kubectl port-forward service/web 8080:80 then curl localhost:8080: does the Service work on its own?
  4. kubectl describe ingress web (or the HTTPRoute): right host, path and backend? Does the Ingress controller log an error?
  5. Only then look outside the cluster: DNS records, firewalls, load balancer.

Linux you already know

  • The Linux handbook's website checklist was systemctl status → journalctl -u → ps aux → top. This chapter's path is the same shape: get (status) → describe (what the system says about it) → logs (journalctl for a Pod) → exec (go in and look).
  • kubectl logs -f is tail -f or journalctl -u … -f. --previous is the log from before the restart.
  • Exit codes above 128 are 128 + signal number, the same rule you saw with kill -9.
  • Events are like the last lines of systemctl status: a short, recent history, not a full log.
  • A Terminating Pod that will not die is a process ignoring SIGTERM. After the grace period, SIGKILL ends it, the same kill/kill -9 pair.

Common mistakes

Common mistake

Reading logs without --previous on a crash-looping Pod. You see the brand new container's first second, which may be empty. The error is in the run that just died.

Common mistake

Skipping describe. Many problems never reach the app, so there are no logs to read. The answer is in the Events.

Common mistake

Deleting the Pod "to see if it fixes itself". You lose the Events and the Last State, and a Deployment will bring back the same broken Pod. Gather the evidence first.

Common mistake

"kubectl logs shows nothing, so the app is broken." A Pending Pod has no container yet, so it has no logs. And an app that writes to a file instead of stdout shows nothing too. Containers should log to stdout and stderr.

Common mistake

Fixing things inside a running container. Editing a file after exec is lost the next time the container restarts. Fix the image, the ConfigMap or the manifest.

This can break things

kubectl delete pod NAME --force --grace-period=0 removes the Pod object without waiting for the node to confirm the containers stopped. For a StatefulSet (chapter 14) that can mean two copies of the same Pod running at once, both writing to the same data. Only use it when you know the node is gone.

Try it

Try it

Three broken Deployments. For each, find the cause using only the path from this chapter, then fix it. Do not peek at the answers until you have tried. Use a scratch namespace.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: broken-image
spec:
  replicas: 1
  selector:
    matchLabels: {app: broken-image}
  template:
    metadata:

    spec:
      containers:
        - name: web
          image: nginx:1.27-typo

apiVersion: apps/v1
kind: Deployment

  name: broken-crash
spec:
  replicas: 1
  selector:
    matchLabels: {app: broken-crash}
  template:
    metadata:
      labels: {app: broken-crash}
    spec:
      containers:
        - name: app
          image: busybox:1.37
          command: ["sh", "-c", "echo 'cannot connect to database at db:5432' >&2; exit 1"]
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: broken-pending
spec:
  replicas: 1
  selector:
    matchLabels: {app: broken-pending}
  template:
    metadata:
      labels: {app: broken-pending}
    spec:
      containers:
        - name: web
          image: nginx:1.27
          resources:
            requests:
              cpu: "100"
              memory: 500Gi


kubectl create namespace dev
kubectl apply -n dev -f broken.yaml
kubectl get pods -n dev

# for each broken Pod:
kubectl describe pod -n dev <pod-name>
kubectl logs -n dev <pod-name> --previous

# the whole story in one stream
kubectl get events -n dev --sort-by=.lastTimestamp

# after you have found each cause, fix it by editing the Deployment
kubectl set image deployment/broken-image web=nginx:1.27 -n dev
kubectl get pods -n dev

# clean up
kubectl delete namespace dev

What each one should teach you:

  • broken-image: get shows ErrImagePull then ImagePullBackOff. describe has an event saying the image manifest was not found. There are no logs, because the container never started.
  • broken-crash: get shows Error then CrashLoopBackOff. logs --previous prints the message. describe shows Exit Code: 1. The cause is in the app, not the cluster.
  • broken-pending: get shows Pending with no node. describe has a FailedScheduling event from the scheduler: no node has that much CPU or memory. There are no logs, because nothing was ever started.

Interview questions

Interview

Click a question, answer out loud first, then check.

A Pod is stuck in Pending. How do you debug it?

Pending means it hasn't been placed, or the node hasn't finished starting it. I run kubectl describe pod and read the Events. A FailedScheduling event from the scheduler tells me why: not enough CPU or memory for the requests, an untolerated taint, a node selector or affinity that matches nothing, or a PersistentVolumeClaim that isn't bound. Then I fix the cause, either the Pod's requirements or the cluster's capacity.

A Pod is in CrashLoopBackOff. What do you do?

The container keeps exiting and the kubelet keeps restarting it, with longer delays. First I read kubectl logs --previous, because that's the run that just died. Then describe for Last State, the reason and the exit code. Exit 1 usually means an app error. 137 usually means OOMKilled, so I look at the memory limit. If there are no logs, I check the command and entrypoint. A liveness probe that kills a slow app can also cause it.

What does exit code 137 mean?

128 plus 9, so the process was killed by SIGKILL. In Kubernetes the most common reason is that it hit its memory limit and the kernel's OOM killer ended it, and describe shows OOMKilled. It can also be a forced kill after the termination grace period. I'd check Last State, then memory usage and the limit.

Your service isn't reachable. Walk me through your checks.

I go layer by layer. Is the Pod running and ready? Does the Service have endpoints? If not, it's the selector or readiness. Does the Service work alone, using port-forward to the Service? Then the Ingress or Gateway: host, path, backend, and the controller's logs. Only after that do I look outside the cluster at DNS, firewalls and load balancers. Working in order stops me guessing.

The image has no shell. How do you debug inside it?

I use kubectl debug to attach an ephemeral container with the tools I need, such as busybox, to the running Pod. With --target it shares the process namespace of the app container, so I can see its processes. If I don't want to touch the running Pod, --copy-to makes a copy to experiment on. For node-level problems, kubectl debug node/NAME gives a Pod with the node's filesystem mounted.

Habits worth keeping

Habits

Go get, describe, logs, every time. Read the Events and notice who wrote them. Use --previous for crashes. Collect evidence before you delete anything. Check layers in order, from the Pod outwards. Remember that events fade after about an hour, so get your logs somewhere that lasts. Say it out loud: "status, why, what the app said."
