Operators, CRDs and the reconcile loop

Teaching Kubernetes new nouns

Section 19

Chapter 3 said that controllers compare desired state with actual state, forever. Chapter 14 said a StatefulSet cannot run your database cluster for you. This chapter closes the loop: Kubernetes lets you add your own kinds of object and write your own controller. That combination has a name, the operator, and it is why cert-manager, Prometheus and most databases on Kubernetes work the way they do.

The problem

Kubernetes knows nouns like Pod, Deployment and Service. It does not know "a PostgreSQL cluster". Yet running one takes real knowledge:

  • start the primary first, then the replicas, and wire up replication,
  • if the primary dies, promote a replica and repoint clients,
  • take backups on a schedule and test restores,
  • upgrade versions in a safe order.

A person who knows those steps writes them in a runbook, and someone is paged to follow it. You would rather the cluster did it. For that, Kubernetes needs a new noun, PostgresCluster, and a program that knows what that noun means.

Key idea

A CustomResourceDefinition (CRD) adds a new kind to the Kubernetes API. A controller watches objects of that kind and makes reality match them. An operator is a custom controller that carries a human operator's knowledge of one application.

CRD

The definition of a new kind: its name, its fields, its validation. Like adding a new table to a database.

Custom resource (CR)

An instance of that kind: your PostgresCluster called orders-db. Like a row in that table.

Controller

A program that watches those objects and acts on them. Without it, a CR is just stored data.

Operator

A CRD plus a controller that encodes how to run something: install, scale, back up, fail over, upgrade.

You write a CR (spec: what you want)→Controller sees it→Creates Deployments, StatefulSets, Services→Writes status back→Watches, and repeats

The reconcile loop

You have already seen this loop. The ReplicaSet controller runs it for Pods. Every controller in Kubernetes, built in or custom, is the same shape:

  1. Observe desired state: read the object's spec.
  2. Observe actual state: look at what exists, in the cluster and sometimes outside it.
  3. Compare. Same? Do nothing.
  4. Act to close the gap: create, update or delete things.
  5. Write status so people can see what is going on.
  6. Wait for the next change, or the next timer, and go again.

Why it is built this way

  • It reacts to state, not events. A controller does not say "a Pod was deleted, so make one". It says "I want three and I see two, so make one". If the controller was down when the Pod died, it still fixes things when it comes back. Programmers call this level-triggered, as opposed to edge-triggered.
  • It must be idempotent. Running the loop twice must give the same result as once. Nothing breaks if it fires a hundred times.
  • It is safe to crash. The truth lives in the API, not in the controller's memory.

Three pieces every real controller uses

  • Owner references. When a controller creates a Deployment for your CR, it marks the CR as its owner. Delete the CR and Kubernetes's garbage collector deletes everything it owns. That is the ownerReferences you meet when you ask kubectl get pod -o yaml and see a ReplicaSet as the owner.
  • Finalizers. A name in metadata.finalizers says "do not delete me until I have cleaned up". The controller removes it when its cleanup (say, deleting a cloud disk) is done. A Pod stuck in Terminating is often waiting on a finalizer.
  • Status and conditions. The controller writes progress into status: "Ready", "Degraded", the current primary. This is how you ask an operator "are you okay?" with kubectl describe.

A CRD, by hand

Here is a tiny new kind called Website. It has two fields: an image and a replica count.


apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: websites.example.com
spec:
  group: example.com
  scope: Namespaced
  names:
    plural: websites
    singular: website
    kind: Website
    shortNames: ["ws"]
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: ["image"]
              properties:
                image:
                  type: string
                replicas:
                  type: integer
                  minimum: 1
                  default: 1
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true


metadata.name: websites.example.com   must be PLURAL.GROUP
spec:
  group: example.com                  the API group: example.com/v1 will be the apiVersion
  scope: Namespaced                   Website objects live in a namespace (or Cluster for cluster-wide)
  names:
    kind: Website                     what you write in kind:
    plural: websites                  what you type in kubectl get websites
    shortNames: [ws]                  kubectl get ws
  versions:
    - name: v1, served, storage       one version, accepted by the API and used for storage
      schema: openAPIV3Schema         the VALIDATION: image is required, replicas is an integer >= 1
      subresources: status: {}        gives the object a separate /status the controller writes to

Once the CRD is applied, you can create objects of the new kind:


apiVersion: example.com/v1
kind: Website
metadata:
  name: blog
spec:
  image: nginx:1.27
  replicas: 2

It works like any other object. kubectl get websites, kubectl describe website blog and kubectl explain website.spec all work, and the schema rejects replicas: 0 or a missing image.

Key idea

Applying a CR does nothing by itself. No Pods appear. A CRD teaches the API server to store a new kind. It does not teach anything to act on it. Only a controller does that. It is exactly the Ingress lesson from chapter 10: the object is a request, the controller is the worker.

A controller, in twelve lines of shell

A controller is not mysterious. Here is a toy one, in bash, that gives every Website a Deployment. It is the reconcile loop with the safety removed.


#!/usr/bin/env bash
NS=dev
while true; do
  for name in $(kubectl get websites -n "$NS" -o jsonpath='{.items[*].metadata.name}'); do
    image=$(kubectl get website "$name" -n "$NS" -o jsonpath='{.spec.image}')
    replicas=$(kubectl get website "$name" -n "$NS" -o jsonpath='{.spec.replicas}')
    kubectl create deployment "site-$name" -n "$NS" --image="$image" --replicas="$replicas" \
      --dry-run=client -o yaml | kubectl apply -n "$NS" -f - >/dev/null
  done
  sleep 5
done


for each Website                    OBSERVE desired state: what Websites exist, and what do they ask for?
  read image and replicas           (the spec)
  build the Deployment YAML         the state we want in the world
  kubectl apply -n dev              ACT: apply is idempotent, so "already right" changes nothing
sleep 5, repeat                     level-triggered: we look at state, not at events

It lacks everything a real controller has: no status, no owner references (delete a Website and its Deployment stays), no error handling, and it polls instead of watching. Real controllers use the API's watch feature, keep a local cache, and process a work queue. The idea is identical.

What an operator adds

The toy controller turns one object into one Deployment. A real operator turns a CR into the whole system and then operates it:

OperatorNew kinds it addsWhat it does for you
cert-managerCertificate, Issuerrequests and renews TLS certificates, then writes the Secret an Ingress needs (chapters 10, 11)
Prometheus OperatorPrometheus, ServiceMonitorruns Prometheus and generates its scrape config from your objects (chapter 21)
CloudNativePG, Zalando and othersa PostgreSQL Clustercreates a primary and replicas, handles failover, backups, upgrades
StrimziKafka, KafkaTopicruns Kafka, and manages topics as objects
Argo CDApplicationkeeps the cluster in step with a git repository
Gateway API implementationsGateway, HTTPRoutethe Gateway API from chapter 10 is itself a set of CRDs

Operators are usually installed with Helm (chapter 18). The Helm chart installs the CRDs and the controller Deployment. After that you create CRs and the operator does the day-to-day work. That is the division of labour: Helm installs software. An operator runs it.

Writing one

You rarely need to write an operator. If you do, you do not write the watch logic from scratch. Frameworks do that: Kubebuilder and controller-runtime (Go), the Operator SDK, and smaller ones for Python and other languages. You write the reconcile function. Before you start, ask whether a Helm chart, a Job or a CronJob would do. Operators are for software with real operational logic.

Linux and Canonical, again

  • The reconcile loop is a while true script with a conscience. You have written "check, fix if wrong, sleep, repeat". The difference is that it reads one source of truth and is safe to run twice.
  • An operator is a sysadmin's runbook turned into code. Imagine the Linux handbook's troubleshooting path (status, logs, process list) run automatically, plus the fix.
  • systemd is a small controller. A unit file says "this should be running", and systemd restarts it when it is not. A Deployment controller is that, for many machines. An operator is that, with knowledge of one application.
  • A CRD is like adding a new kind of file to /etc that the system will not act on until you also install the daemon that reads it. The daemon is the controller.
  • Juju charms are the same idea in another system. Canonical describes Juju as an engine for "software operators", and a charm is that operator for one application: install, configure, integrate, scale, upgrade. The nouns differ (charm, application, unit, integration) but the job is the same. Chapter 22 returns to this. It is a good thing to say in the interview: "a charm is Juju's operator".

Common mistakes

Common mistake

"I created the custom resource but nothing happened." There is no controller running, or it is not healthy. Check kubectl get pods -A for the operator's Pods and read their logs. A CR is only data until something acts on it.

Common mistake

"A StatefulSet already runs my database." It runs the Pods and the disks. It does not run replication, failover or backups. That is the operator's job.

Common mistake

"Operators are just Helm charts." A chart installs and stops. An operator keeps running, watching, and reacting, long after install: day-two operations.

Common mistake

Writing an operator for something simple. You take on a program to maintain, test and secure. Use one when the operational knowledge justifies it.

Common mistake

Treating status as something you can edit. It belongs to the controller. Your changes are overwritten on the next reconcile. Change spec.

Common mistake

Hand-editing objects an operator owns. The operator will put them back, just as Helm and Deployments do. Change the CR.

This can break things

Deleting a CRD deletes every custom resource of that kind, and through their owner references, everything those resources created. Deleting the Cluster CRD of a database operator can mean deleting every database. Never remove a CRD you do not fully understand. And remember an operator often runs with broad RBAC (chapter 16). Treat installing one as giving it admin-like power over its own area.

Try it

Try it

On the kind cluster. We install the Website CRD, create a CR and see that nothing happens, then run the toy controller in a second terminal and watch the loop. Save the files from this chapter as website-crd.yaml, blog.yaml and toy-controller.sh.


kubectl create namespace dev

# ---- 1. teach the API a new kind ----
kubectl apply -f website-crd.yaml
kubectl get crd websites.example.com
kubectl api-resources | grep -i website
kubectl explain website.spec

# ---- 2. a custom resource, and nothing happens ----
kubectl apply -n dev -f blog.yaml
kubectl get websites -n dev
kubectl get deployments,pods -n dev            # empty: no controller yet

# ---- 3. validation comes from the schema ----
kubectl apply -n dev -f - <<'EOF'
apiVersion: example.com/v1
kind: Website
metadata:
  name: bad
spec:
  replicas: 0
EOF
# rejected: image is required, and replicas must be at least 1

# ---- 4. start the controller (second terminal) ----
#   chmod +x toy-controller.sh && ./toy-controller.sh
kubectl get deployments -n dev                 # site-blog appears within seconds

# ---- 5. watch the loop do its job ----
kubectl delete deployment site-blog -n dev     # it comes back within seconds
kubectl patch website blog -n dev --type merge -p '{"spec":{"replicas":4}}'
kubectl get pods -n dev                        # four Pods

# ---- 6. clean up: stop the controller with Ctrl+C in the other terminal ----
kubectl delete website blog -n dev
kubectl get deployments -n dev                 # site-blog is STILL there: no owner reference
kubectl delete deployment site-blog -n dev
kubectl delete crd websites.example.com        # also deletes any Website still around
kubectl delete namespace dev

What to look for:

  • Step 2: the Website exists and you can describe it, but there are no Pods. A CRD only stores.
  • Step 3: the API server itself rejects the bad object, using the schema in the CRD. No controller was involved.
  • Step 5: delete the Deployment and it returns, because the loop saw "want one, have none". Change replicas in the CR and the Deployment follows. Desired state, actual state, the gap closed.
  • Step 6: deleting the Website leaves its Deployment behind. That is what owner references and finalizers are for in a real operator.

Interview questions

Interview

Click a question, answer out loud first, then check.

What is a CRD, and what is a custom resource?

A CustomResourceDefinition tells the API server about a new kind of object: its group, name, fields and validation schema. A custom resource is an instance of that kind. After I apply a CRD, I can kubectl get and apply the new kind like any built-in one. But a CRD only stores data. Something has to watch those objects and act, and that's a controller.

What is an operator?

A CRD plus a controller that encodes the operational knowledge of running a particular application, the kind that lives in a human operator's runbook. For a database, that's creating the primary and replicas, failover, backups, and upgrades. I declare a cluster object, and the operator reconciles reality toward it and keeps doing so. Helm installs software, an operator runs it day to day.

Explain the reconcile loop.

The controller reads the desired state from the object's spec, observes the actual state of the world, compares them, and takes the actions that close the gap, then writes progress into status and waits for the next change. It's level-triggered: it reacts to the current state, not to individual events, so it recovers if it missed something. And it must be idempotent, because it may run many times. The Deployment and ReplicaSet controllers work the same way as a custom operator.

What are owner references and finalizers for?

Owner references link a created object to its owner, such as a Deployment owned by my custom resource, so that deleting the owner makes garbage collection delete everything it created. A finalizer is a marker saying "don't delete this object until I've cleaned up". The controller does its cleanup, for example removing an external cloud resource, then removes the finalizer. A resource stuck in Terminating is usually waiting on one.

When would you write your own operator, and when not?

When the application has real operational logic worth automating, such as failover, backups or coordinated upgrades, and there's no good existing operator. I'd use Kubebuilder or controller-runtime so I only write the reconcile logic. I wouldn't write one for something a Helm chart, a Job or a CronJob handles, because an operator is a program I'd have to build, test, secure and maintain for the life of the system.

Habits worth keeping

Habits

Say "a CRD stores, a controller acts". Check the operator's Pods and logs when a CR does nothing. Change spec, never status or owned objects. Protect your CRDs, since deleting one deletes its data. Reach for an existing operator before writing your own. And describe the reconcile loop in one breath: look at what you want, look at what you have, close the gap, repeat.
