Ingress

Getting traffic from outside the cluster to a Service

Section 10

A Service gives your app a stable address inside the cluster. The outside world needs something smarter: one entry point that reads the hostname and URL and sends each request to the right Service. That is what Ingress was made for, and what Gateway API is now replacing. You need to understand both, because the interviewer's cluster may well have either.

The problem

You have three apps: a website, an API, and an admin page. Each has a Service. How do users reach them?

  • A LoadBalancer Service per app works, but on a cloud that is three load balancers, three public IPs and three bills.
  • A NodePort per app gives you ports like 31842. Nobody types that.
  • Neither knows about shop.example.com, about /api, or about HTTPS certificates.

You want one public entry point that understands HTTP: "requests for shop.example.com/api go to the API Service, everything else goes to the website", with TLS handled once at the door.

Key idea

An Ingress is a set of routing rules. An Ingress controller is the program that reads them and does the routing. Kubernetes ships the rules object, not a controller. Without a controller, an Ingress does nothing at all.

Check this first: the state of Ingress today

Two facts you must be able to say in an interview. First, the Ingress API is frozen: stable since Kubernetes 1.19, with no plans to remove it, but no further development. The Kubernetes project now recommends the Gateway API for new work. Second, ingress-nginx, the most widely used controller, was retired in March 2026: no more releases, bug fixes or security patches. Existing installs keep running, but the project says to migrate, and notes that no alternative is a drop-in replacement. Ingress is still everywhere in existing clusters, so you need to read it. New designs should use Gateway API.

Your first Ingress


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: example
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80


spec:
  ingressClassName: example     which controller should handle this Ingress
  rules:
    - host: shop.example.com    only for this hostname (leave out to match any)
      http:
        paths:
          - path: /api          if the URL path starts with /api ...
            pathType: Prefix    ... how to match (see below)
            backend:
              service:
                name: api       ... send to the Service named api
                port:
                  number: 80    ... on this Service port

Both the host and the path must match before the controller sends the request to that Service. The backend is a Service, not a Pod: this is why chapter 9 comes first.

Path types

pathTypeMatches
Exactonly that exact path. /api matches /api, not /api/users.
Prefixthat path and everything under it, split on /. /api matches /api and /api/users, but not /apiary.
ImplementationSpecificwhatever your controller decides. Avoid it if you want the Ingress to be portable.

When more than one rule matches, the longest path wins. That is why /api wins over / for /api/users.

Which controller? The class

A cluster can run several controllers. ingressClassName picks one by naming an IngressClass. If you leave it out, a default class must exist, marked with the annotation ingressclass.kubernetes.io/is-default-class: "true".


kubectl get ingressclass
kubectl get ingress
kubectl describe ingress shop
  • get ingressclass shows which controllers are installed. An empty list means nothing will act on your Ingress.
  • get ingress shows the host and, once a controller has picked it up, an address.
  • describe ingress shows each rule and the backend it resolved to, with events from the controller.

HTTPS


spec:
  ingressClassName: example
  tls:
    - hosts:
        - shop.example.com
      secretName: shop-tls
  rules:
    - host: shop.example.com
      # ...

The controller ends TLS at the door: it uses the certificate in the Secret shop-tls (a Secret of type kubernetes.io/tls, with tls.crt and tls.key), decrypts, then sends plain HTTP to the Service. You rarely create that Secret by hand. A tool called cert-manager can request and renew certificates and write the Secret for you.

The portability trap

Ingress only standardises host and path. Everything else (redirects, rewrites, rate limits, timeouts, CORS) is configured with annotations that each controller invents for itself. An Ingress full of nginx.ingress.kubernetes.io/... annotations works on one controller and is ignored by another. That is one of the main reasons Gateway API exists.

Gateway API

The Gateway API is the newer design. Instead of one overloaded object it has separate objects for separate people, and it puts the things annotations used to do (redirects, header changes, traffic splitting) into real fields.

ObjectRoleWho owns it
GatewayClassa type of gateway, backed by one controller (like an IngressClass)the infrastructure provider
Gatewayan actual entry point: which ports and protocols it listens onthe cluster operator
HTTPRoutethe routing rules: host, path, headers to Servicesthe application developer
GatewayClass (who implements)→Gateway (the listener)→HTTPRoute (the rules)→Service

This split is the point. The platform team owns the Gateway: the ports, the certificates, which namespaces may attach routes. Each app team owns its own HTTPRoute in its own namespace. In the Ingress world they all edited one object.


apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: example
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
spec:
  parentRefs:
    - name: shop-gateway
  hostnames:
    - "shop.example.com"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: api
          port: 80
    - backendRefs:
        - name: web
          port: 80


Gateway
  gatewayClassName: example     which controller implements it
  listeners:
    - port: 80, protocol: HTTP  what it listens on
      allowedRoutes: from: Same only routes in this namespace may attach

HTTPRoute
  parentRefs: shop-gateway      which Gateway to attach to
  hostnames: shop.example.com   which Host header
  rules:
    - matches: path /api        if the path starts with /api
      backendRefs: api:80       send it to Service api
    - backendRefs: web:80       no match given = everything else goes to web

The three apiVersions all read gateway.networking.k8s.io/v1. As of the Kubernetes documentation I read, the stable kinds are GatewayClass, Gateway, HTTPRoute and GRPCRoute.

Things Gateway API does in fields, not annotations


rules:
  - backendRefs:
      - name: web-v1
        port: 80
        weight: 90
      - name: web-v2
        port: 80
        weight: 10

That is a 90/10 traffic split for a canary release, written in a standard field that any compliant controller understands. Other standard pieces: matching on headers, redirects, URL rewrites and header edits (as route filters), and routes that refer to Services in other namespaces (which need explicit permission through a ReferenceGrant).

Key idea

Both need a controller to do anything. The API objects are just requests. Gateway API is an add-on: the CRDs (chapter 19) must be installed, and a controller must implement them. Many implementations exist, including Envoy Gateway, NGINX Gateway Fabric, Cilium, Traefik and the big cloud providers. Canonical Kubernetes lists ingress and gateway among its optional features, so on that distribution you switch one on instead of installing it (chapter 22).

Moving off ingress-nginx

If you meet a cluster still running ingress-nginx, the honest advice is the project's own: plan a migration. The Kubernetes maintainers' statement says there is no drop-in replacement, so budget real work. The usual path:

  1. Inventory your Ingresses and, above all, the annotations they use. Those are what will not carry over.
  2. Pick a Gateway API controller (or another Ingress controller) and install it beside the old one.
  3. Translate Ingress rules to Gateway and HTTPRoute objects. A conversion tool called ingress2gateway exists to help, but review its output. Do not trust it blindly.
  4. Test with a separate hostname. Then move DNS across and watch error rates.
  5. Remove ingress-nginx once nothing needs it.

Linux you already know

  • An Ingress controller is nginx as a reverse proxy, the exact thing in the Linux handbook's Nginx chapter. There you edited /etc/nginx/sites-available/, ran nginx -t and reloaded. Here the controller generates that configuration from Ingress objects and reloads itself.
  • server_name and location blocks in nginx are the same idea as host and path in an Ingress rule.
  • Ports 80 and 443, and curl -I with a Host header, are the same debugging tools you used for Nginx on the VPS.
  • TLS certificates are files with keys. chmod 600 logic applies: a TLS Secret is a private key, so treat it like /etc/ssl/private.

Common mistakes

Common mistake

Creating an Ingress with no controller installed. It is accepted by the API and nothing happens. kubectl get ingressclass being empty is the clue.

Common mistake

Wrong or missing ingressClassName. With several controllers, or none marked default, nobody claims it. Name the class.

Common mistake

Pointing a backend at a Service that does not exist, or in another namespace. An Ingress can only reach Services in its own namespace. Gateway API routes can cross namespaces, but only with a ReferenceGrant.

Common mistake

"Ingress is a type of Service." It is not. An Ingress sends traffic to Services. And the controller itself usually sits behind a LoadBalancer or NodePort Service.

Common mistake

Annotations that only one controller understands. They silently do nothing on another. Treat each as a dependency on that controller.

Common mistake

Choosing ingress-nginx for a new cluster. It is retired and gets no security fixes. Choose a maintained controller, and prefer Gateway API.

This can break things

The Ingress controller is your public front door. A broken rule can send everyone's traffic to the wrong app, and a missing TLS setting can expose private services over plain HTTP. Change routes one at a time, and test on a spare hostname first.

Try it

Try it

Part A needs only your kind cluster. Part B installs Envoy Gateway (a Gateway API controller) using the project's own quickstart. The install command carries a version number that moves, so open the Envoy Gateway quickstart and use the version shown there. It was v1.9.2 when I read it.

Part A: write and validate an Ingress, with no controller


# 1. is there an ingress class on this cluster?
kubectl get ingressclass

# 2. ask the API server to validate your Ingress without storing it
kubectl apply --dry-run=server -f shop-ingress.yaml

# 3. learn the fields from the cluster itself
kubectl explain ingress.spec.rules.http.paths
kubectl explain ingress.spec.tls

Save the Ingress from this chapter as shop-ingress.yaml. Step 2 prints ingress.networking.k8s.io/shop created (server dry run)-style output on success, and an error if a field is wrong. Try breaking it: change pathType: Prefix to pathType: Fuzzy.

Part B: a real route with Envoy Gateway


# 1. install the controller (use the version from the quickstart page)
helm install eg oci://docker.io/envoyproxy/gateway-helm --version v1.9.2 -n envoy-gateway-system --create-namespace
kubectl wait --timeout=5m -n envoy-gateway-system deployment/envoy-gateway --for=condition=Available

# 2. the project's own demo: a GatewayClass, a Gateway named eg, and an HTTPRoute
kubectl apply -f https://github.com/envoyproxy/gateway/releases/download/v1.9.2/quickstart.yaml -n default
kubectl get gatewayclass,gateway,httproute

# 3. kind has no cloud load balancer, so reach it with a port-forward
export ENVOY_SERVICE=$(kubectl get svc -n envoy-gateway-system --selector=gateway.envoyproxy.io/owning-gateway-namespace=default,gateway.envoyproxy.io/owning-gateway-name=eg -o jsonpath='{.items[0].metadata.name}')
kubectl -n envoy-gateway-system port-forward service/${ENVOY_SERVICE} 8888:80 &
curl --verbose --header "Host: www.example.com" http://localhost:8888/get

Now point it at your own app. This uses the Gateway eg from the demo:


apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
spec:
  parentRefs:
    - name: eg
  hostnames:
    - "web.example.com"
  rules:
    - backendRefs:
        - name: web
          port: 80


# 4. your own app, and a route to it
kubectl create deployment web --image=nginx:1.27
kubectl expose deployment web --port=80
kubectl apply -f web-route.yaml
kubectl get httproute web
kubectl describe httproute web
curl --header "Host: web.example.com" http://localhost:8888/

# 5. clean up
kill %1
kubectl delete -f web-route.yaml
kubectl delete service,deployment web
kubectl delete -f https://github.com/envoyproxy/gateway/releases/download/v1.9.2/quickstart.yaml --ignore-not-found=true
helm uninstall eg -n envoy-gateway-system

What to look for:

  • Part A, step 2: the server accepts or rejects the YAML without any controller being present. Validation is the API server's job. Routing is the controller's.
  • Part B, step 2: get gatewayclass,gateway,httproute shows the three layers. Check the Gateway reports it is programmed.
  • Part B, step 4: describe httproute has a status section saying whether the Gateway accepted the route. curl with the Host header reaches nginx. Without the Host header it should not match your route. That is host routing at work.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between a Service of type LoadBalancer and an Ingress?

A LoadBalancer Service exposes one Service on its own external IP, at layer 4, with no idea of hostnames or paths. On a cloud that's one load balancer per Service. An Ingress is a set of HTTP routing rules, host and path to Service, handled by one controller behind a single entry point. So I can serve many apps through one IP and terminate TLS in one place. The controller itself usually sits behind a LoadBalancer Service.

What is an Ingress controller, and does Kubernetes include one?

It's the program that reads Ingress objects and does the routing, typically a reverse proxy like nginx, Traefik, HAProxy or Envoy, or a cloud load balancer integration. Kubernetes doesn't include one. If I create an Ingress with no controller installed, the API accepts it and nothing happens. I select the controller with an IngressClass.

Why is the project moving from Ingress to Gateway API?

Ingress only standardised host and path, so everything else, like redirects, rewrites and rate limits, lived in controller-specific annotations that weren't portable. It also puts everyone in one object. Gateway API splits the roles: a GatewayClass for the implementation, a Gateway owned by the platform team, and HTTPRoutes owned by app teams. It makes things like traffic splitting and header matching real, portable fields. The Ingress API is frozen: it stays, but gets no new features.

ingress-nginx has been retired. What would you do about a cluster that uses it?

It gets no more releases or security fixes since March 2026, so I'd plan a migration rather than wait. First inventory the Ingresses and especially the annotations, since those are what won't translate. Pick a maintained controller, preferably a Gateway API one, and install it alongside. Convert the rules, maybe with the ingress2gateway tool but reviewing the output, test on a spare hostname, then move DNS and watch. The Kubernetes maintainers said there's no drop-in replacement, so I'd expect real work.

How does TLS work with an Ingress?

The Ingress has a tls section with the hostnames and the name of a Secret of type kubernetes.io/tls holding the certificate and private key. The controller terminates TLS at the edge using that certificate, then forwards plain HTTP to the Service inside the cluster. In practice I'd use cert-manager to request and renew the certificate and keep the Secret up to date, rather than managing it by hand.

Habits worth keeping

Habits

Check kubectl get ingressclass before you write rules. Name the class. Route to Services, never to Pods. Avoid controller-specific annotations when you can, and note each one you use. Prefer Gateway API for anything new. Test with curl --header "Host: ...". And say plainly in the interview: "Ingress is frozen, ingress-nginx is retired, new work goes on Gateway API."
