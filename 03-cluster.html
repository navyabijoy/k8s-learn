What a cluster is

Control plane, nodes, and who does what

Section 03

You have run a Pod. Now the questions start. Who picked the node? Who pulled the image? Who restarts it? This chapter names every part of a cluster and says what each one does, in the order they act when you run kubectl apply.

The problem

Imagine you have ten Linux servers. You want to run an app three times, spread over them, and keep three copies running even when a server dies.

By hand, that means: pick servers, start the app on each, watch them, notice a dead one, start a replacement somewhere else. You would write scripts for it. Then scripts to run the scripts.

A cluster is that job, done by software. You say "I want three copies". The cluster works out where, starts them, and keeps checking.

Key idea

A cluster is a control plane that decides and nodes that do. You never talk to a node to run something. You write what you want to the control plane, and it makes the nodes match.

Control plane

The decision makers. They keep the list of what should exist and notice when reality differs. They do not run your app (in most real clusters).

Node

A machine (physical or virtual) that runs Pods. Each node is an ordinary Linux machine with a few Kubernetes programs on it.

Desired state

What you asked for: "3 copies of web". It lives in the cluster's database.

Actual state

What exists right now: two copies running, one missing. Kubernetes keeps comparing the two and closing the gap.

The parts, in plain words

Think of a restaurant. Orders come in at the front desk. They are written in one order book. A manager checks the book against the kitchens. Each kitchen has a chef who cooks what the book says.

Key idea

The parts do not call each other. They all talk to the API server, and they watch it for changes. The scheduler does not tell the kubelet to start a Pod. It writes "this Pod goes to node 2" into the API, and the kubelet on node 2 sees that and acts.

What happens when you run kubectl apply

You write a Deployment that asks for three copies of web. Follow it through:

  1. kubectl sends it to the API server. The API server checks who you are, whether you may create Deployments, and whether the YAML makes sense.
  2. The API server stores it in etcd. Now the cluster "knows" you want three copies. Nothing is running yet.
  3. The Deployment controller (inside the controller manager) sees the new Deployment. It creates a ReplicaSet. The ReplicaSet controller sees that, and creates three Pod objects. Still nothing is running. These are records.
  4. The scheduler sees three Pods with no node. For each, it picks a node and writes that into the Pod.
  5. The kubelet on each chosen node sees a Pod assigned to it. It asks the container runtime to pull the image and start the containers.
  6. The kubelet reports back. Status goes to the API server, then into etcd. Now kubectl get pods shows Running.
kubectl→API server→etcd→controllers create Pods→scheduler picks a node→kubelet starts containers

Nothing in that list is magic. It is a chain of programs, each doing one small job, each reading and writing the same API.

Desired state, actual state, and the loop

Every controller runs the same loop, forever:

Look at desired state→Look at actual state→Different?→Act to close the gap→Repeat

That is called reconciling. It is why a deleted Pod owned by a Deployment comes back: the ReplicaSet controller sees two copies where it wants three and makes one more. Chapter 19 shows you how to write your own.

Look at a real cluster


kubectl get nodes
kubectl get nodes -o wide
kubectl get pods -n kube-system
  • get nodes lists the machines and whether they are Ready. The ROLES column marks the control-plane node.
  • -o wide adds the OS image, kernel version and container runtime of each node. This is where you find out which runtime you have.
  • get pods -n kube-system shows the cluster's own Pods. -n picks a namespace (chapter 8). Look for kube-apiserver-…, etcd-…, kube-scheduler-…, kube-controller-manager-…, coredns-….

To ask the API server whether it is healthy:


kubectl cluster-info
kubectl get --raw='/readyz?verbose'
kubectl get --raw='/livez'
  • cluster-info prints the API server address and the DNS service.
  • /readyz?verbose lists every internal check with ok or failed. Use it when the API feels slow or wrong.
  • /livez is the shorter "is the process alive" answer.

Linux you already know

None of these parts is a new kind of thing. They are Linux programs.

  • The kubelet is a systemd service on each node. On a node you can run systemctl status kubelet and journalctl -u kubelet, exactly like nginx in the Linux handbook. If the kubelet stops, that node stops reporting.
  • On clusters built with kubeadm, the API server, scheduler, controller manager and etcd run as static Pods. The kubelet starts them from YAML files in /etc/kubernetes/manifests. Drop a file there and a Pod appears. Delete it and the Pod goes. The kubelet is the thing watching that folder.
  • etcd keeps its data on disk, by default under /var/lib/etcd. It is a database, so you back it up like one.
  • A node is a Linux machine. ps aux | grep kube works on it. top shows what is eating its CPU.
  • The container runtime uses the kernel's namespaces and cgroups from the last chapter. Kubernetes does not run containers itself.
Key idea

If you can troubleshoot a Linux service, you can troubleshoot a cluster. "Is the process running? What do its logs say? What is it waiting for?" is the same path.

How big is a real cluster?

  • A laptop cluster often has one node doing both jobs. Fine for learning.
  • A real cluster runs three control-plane nodes (sometimes five) and any number of worker nodes. Three, because etcd needs a majority (a quorum) to accept writes. With three members, one can fail. With five, two can. An even number buys you nothing: four members still tolerate only one failure, because a majority of four is three.
  • On a normal cluster the control-plane nodes are tainted so your Pods do not land on them (chapter 15).

Common mistakes

Common mistake

"The API server stores my data." It does not. It is stateless. It reads and writes etcd. You can run several API servers behind a load balancer for exactly that reason.

Common mistake

"etcd stores my app's data." It stores the cluster's data: objects like Pods, Deployments and Secrets. Your database's rows live on your own volumes (chapter 12).

Common mistake

"If the control plane goes down, my apps go down." Not straight away. Running Pods keep running, because the kubelets already have their instructions and the node networking is already set up. What stops is change: no new Pods, no rescheduling, no scaling, no self-healing of anything that fails after that.

Common mistake

"The scheduler starts Pods." It only chooses a node. The kubelet starts the Pod.

Common mistake

"Use kubectl get componentstatuses to check health." It has been deprecated for years and is unreliable. Use /readyz?verbose instead.

Common mistake

"The 'master' node." Old name. Say control plane (or control-plane node). Interviewers notice.

This can break things

etcd holds every Secret and the entire desired state of the cluster. Lose it with no backup and the cluster forgets everything it was running. Back it up, and treat the backup like a password file.

Try it

Try it

You need a cluster. If you do not have one yet, do chapter 4 first and come back. With a kind cluster named handbook, the node container is called handbook-control-plane, and you can look inside it like a Linux machine.


# 1. which machines are in the cluster, and what runtime do they use?
kubectl get nodes -o wide

# 2. the cluster's own Pods
kubectl get pods -n kube-system -o wide

# 3. ask the API server about its health
kubectl get --raw='/readyz?verbose'

# 4. look at the node as a Linux machine (kind runs each node as a Docker container)
docker exec -it handbook-control-plane bash
ps aux | grep -E "kube|etcd|containerd" | head
systemctl status kubelet --no-pager
ls /etc/kubernetes/manifests
exit

# 5. watch the chain from the section above in action, in a second terminal
kubectl get events --watch
# back in the first terminal:
kubectl create deployment hello --image=nginx:1.27 --replicas=2
# when you are done:
kubectl delete deployment hello

What to look for:

  • In step 4, the four control-plane programs run as processes on the node, and the manifests folder holds their YAML.
  • In step 5, events appear in the order from this chapter: the Deployment scales a ReplicaSet, the ReplicaSet creates Pods, the scheduler assigns them, the kubelet pulls and starts. Note the From column. It tells you which component wrote each line.

Interview questions

Interview

Click a question, answer out loud first, then check.

Walk me through what happens when I run kubectl apply on a Deployment.

kubectl sends the YAML to the API server. The API server authenticates me, checks I'm allowed, validates the object, and writes it into etcd. The Deployment controller notices a new Deployment and creates a ReplicaSet, and the ReplicaSet controller creates the Pod objects. At that point they're just records with no node. The scheduler sees Pods with no node and assigns each one. The kubelet on each chosen node sees a Pod bound to it, tells the container runtime to pull the image and start the containers, and reports status back through the API server. Every step goes through the API server. Components watch it; they don't call each other.

What's in the control plane and what's on a worker node?

The control plane has the API server, etcd, the scheduler and the controller manager, plus the cloud controller manager if you're on a cloud. Worker nodes have the kubelet, a container runtime like containerd, and usually kube-proxy for Service networking. The control plane decides. The nodes run Pods.

Why does only the API server talk to etcd?

It gives one place to enforce authentication, authorization, validation and admission, and one place that understands the data format. If every component wrote to etcd directly, none of that would be consistent, and you couldn't change the storage later without touching everything. It also means the API server itself is stateless, so I can run several behind a load balancer.

The control plane goes down. What happens to my running apps?

They keep running. The kubelets already have their Pods, and the network rules on the nodes are already in place, so traffic keeps flowing. What I lose is change. No new Pods get scheduled, nothing scales, a Pod that crashes after the outage won't be replaced by a controller, and kubectl stops working. The kubelet will still restart a crashed container on its own node, since that's local. So it's degraded, not dead.

Why run three etcd members and not four?

etcd needs a majority to accept writes. With three members the majority is two, so I can lose one. With four the majority is three, so I can still only lose one. The fourth member adds cost and one more thing that can fail, without adding tolerance. Five tolerates two failures. So odd numbers: three for most clusters, five for bigger or more critical ones.

Habits worth keeping

Habits

Say "control plane", not "master". Ask "who wrote this?" when you read events: the scheduler, a controller and the kubelet each point to a different problem. Remember that everything goes through the API server. Back up etcd. And when something feels mysterious, treat the node like any Linux machine: process, logs, what is it waiting for.
