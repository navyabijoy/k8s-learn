Why Kubernetes exists

The problem that came before the tool

Section 01

Kubernetes is not a clever idea that someone invented for fun. It is a pile of solutions to problems you will hit the moment you run more than a few containers on more than one machine. This chapter lists those problems, one at a time, so that when you say "Kubernetes does X" you can also say why X was needed.

The problem, told as a story

Imagine you run a small website on one Linux server. You installed nginx and your app, as in the Linux handbook. systemctl keeps them running. Life is fine.

Stage 1: traffic grows

One server is not enough. You rent a second, then a third. Now you have questions that one server never raised:

  • Which server runs which program?
  • How do the servers find each other?
  • How do you send traffic across all three?

You start writing scripts. A script to copy the app to every server. A script to restart it. A spreadsheet of which program lives where.

Stage 2: servers die

One night a server fails. Your app was on it. systemd on that machine cannot help: the machine is gone. Someone gets paged, starts the app on another server, and edits the load balancer by hand. Total downtime: however long that takes.

Stage 3: containers

You package the app and its dependencies into a container image (chapter 2). That is a big step forward: the app runs the same everywhere. But containers answer the question "how do I package it?". They do not answer "where does it run, and who restarts it?". docker run starts one container on one machine, and that is all it knows.

Stage 4: many containers, many machines

Now you have fifty containers over ten servers. Updates, scaling, failures, secrets, config, storage, networking. Every one of those is a script you would have to write and keep correct.

Key idea

Kubernetes is software that treats a group of machines as one pool. You tell it what you want running. It decides where, starts it, watches it, and fixes it when reality drifts away from what you asked for.

one server + systemd→many servers + scripts→containers→many containers: you need an orchestrator

The jobs it does

Each of these is something you would otherwise do by hand, or script.

Scheduling

Picks which machine runs each container, based on what it needs and what each machine has free.

Self-healing

Restarts containers that die. Replaces Pods when a node dies. Stops sending traffic to something that is not ready.

Scaling

Runs more or fewer copies when you ask, or when load changes if you set up autoscaling.

Rolling updates

Changes versions a few copies at a time, and can go back if the new version is bad.

Service discovery

Gives groups of Pods a stable name and address, and spreads traffic across them.

Config and secrets

Keeps settings and passwords outside the image, and hands them to the right Pods.

Storage

Attaches disks to Pods and keeps data when a Pod moves.

One API

Everything above is controlled through the same HTTP API and the same YAML, on any cloud or laptop.

You will meet each of those as its own chapter. Here are the ones you have already seen: scheduling and self-healing (chapters 3 and 13), rolling updates (chapter 7) and service discovery (chapter 9).

The one big idea: declare, do not instruct

You already know two ways to make a change on Linux.

Imperative: "do this"Declarative: "make it look like this"
Linuxsudo apt install nginx, then systemctl start nginxa config file that says "nginx should be installed and running"
Kuberneteskubectl run, kubectl scalea YAML file that says "3 replicas of web", given to kubectl apply
If something driftsnothing happens until you noticethe system notices and puts it back

Kubernetes is built around the second kind. You write down desired state. Programs called controllers keep comparing it to actual state and closing the gap, forever. That one loop is the whole design. If you remember only one sentence from this chapter, remember that one.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27

That file does not say "start three containers". It says "there should be three". If one dies, there are two, and the cluster makes a third. You will write this exact file in chapter 7.

What Kubernetes is not

  • Not a container runtime. It does not start containers itself. It asks a runtime (like containerd) to.
  • Not Docker. Docker builds and runs containers. Kubernetes organises many of them across machines. They work together but are different tools.
  • Not a platform in a box. It does not build your code, run your CI, or give you a database. People add those.
  • Not magic scaling. It can scale Pods. It does not make a badly written app fast or fix a database that cannot take the load.
  • Not free to run. You pay in complexity: more things to learn, secure and upgrade.

When you do not need it

An honest answer to "should we use Kubernetes?" is sometimes no. One small app on one server, with a few users, does not need an orchestrator. A systemd service, or docker compose on a single machine, is simpler, cheaper and easier to debug.

Reach for Kubernetes when…Skip it when…
you run many services on several machinesyou have one app on one server
you need zero-downtime updates and self-healinga few minutes of downtime during an update is fine
teams deploy independently and oftenone person deploys once a month
you want the same workflow on any cloud or on premisesyou are happy on one provider's simple hosting

Where it came from

Google ran huge numbers of containers for years on an internal system called Borg. In 2014 Google began Kubernetes as an open-source project built on what they had learned. It was donated to the Cloud Native Computing Foundation (CNCF), which now looks after it, and it has been the standard way to run containers at scale for most of a decade since.

The name is Greek for "helmsman", the person steering a ship. You will see it written K8s: a K, eight letters, and an s.

Linux you already know

  • systemd keeps services running on one machine, and restarts them when they fail. Kubernetes does the same job for containers across many machines. When you read "Deployment" you can think "systemd, but for a fleet".
  • cron runs jobs on a schedule on one machine. Kubernetes has CronJobs for the same job across a cluster (chapter 14).
  • The process and service ideas from the Linux handbook carry over exactly: a container is a process, a Pod is a group of them, and a Service is a stable name for a group of them.
  • The Linux kernel is still doing the real work. Kubernetes is a manager sitting on top of it.

Common mistakes

Common mistake

"Kubernetes is a replacement for Docker." They solve different problems. Docker (or any tool that builds OCI images) makes the container image. Kubernetes runs lots of them across machines, using a runtime such as containerd.

Common mistake

"Kubernetes makes my app highly available." It gives you the tools: copies, health checks, rescheduling. An app with one replica, no probes, and one database is still a single point of failure.

Common mistake

"We should use Kubernetes because everyone does." Choose it for a reason you can say in one sentence. In an interview, being able to say when not to use it shows more understanding than reciting features.

Common mistake

"Kubernetes starts my containers." It decides. The kubelet and the container runtime on each node start them. The next chapters show who does what.

Interview questions

Interview

Click a question, answer out loud first, then check.

What problem does Kubernetes solve?

Containers solve packaging, but not running many of them across many machines. Kubernetes takes a pool of machines and runs containers on them for me. I describe what I want, like three copies of this app, and it picks the machines, starts them, restarts them when they fail, replaces them when a node dies, updates them gradually, and gives them a stable network address. It replaces a lot of scripting and manual work.

What does "declarative" mean in Kubernetes?

I write down the state I want, not the steps to get there. For example, replicas: 3. Controllers then compare that desired state against what actually exists and keep fixing the difference. If a Pod dies, I don't do anything. The controller sees two where there should be three and creates one. The opposite, imperative, is running commands one by one and hoping nothing drifts afterwards.

Why not just use Docker Compose?

Compose is great on one machine. It describes a set of containers on a single host. It doesn't spread them across several machines, replace them when a machine fails, do rolling updates with health checks, or give me a cluster-wide network and API. If I have one small app on one server, Compose, or even systemd, is simpler and I'd use that. Kubernetes pays off when I have many services, several machines, and a need for resilience and gradual rollouts.

Is Kubernetes the same as Docker?

No. Docker builds container images and can run containers on one host. Kubernetes manages containers across many hosts. Kubernetes doesn't run containers itself. It asks a container runtime, usually containerd, to. They work together: I might build an image with Docker and run it on Kubernetes.

When would you not recommend Kubernetes?

When the problem is small. One app on one server, a small team, and downtime during deploys is acceptable. The cost of Kubernetes is complexity: more to learn, secure and upgrade. In that case a systemd service or Compose on a VM is easier to run and debug. I'd recommend Kubernetes once there are enough services, machines or teams that the automation pays for the complexity.

Habits worth keeping

Habits

Start from the problem, then name the tool. Say "desired state and actual state" when you explain how it works. Compare to Linux things you know: systemd, cron, processes. Be honest about when it is too much. And remember: Kubernetes decides, the nodes do.
