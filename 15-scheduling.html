Scheduling: taints, tolerations, affinity

Choosing which node a Pod lands on

Section 15

By default the scheduler puts a Pod wherever it fits. Most of the time that is exactly right. Sometimes it is not: the database must be on the fast disks, the batch jobs must stay off the web nodes, and three replicas must not all land on one machine. This chapter is the small set of controls for that, and the one rule that keeps them straight: taints push away, affinity pulls toward.

The problem

Picture a cluster with five nodes: two with SSDs, one with a GPU, one reserved for a team, and one control-plane node. Four situations:

  • The database needs SSD nodes.
  • The machine-learning job needs the GPU node, and nothing else should waste it.
  • Your three web replicas all landed on the same node. When it dies, the site goes down.
  • You need to reboot a node for a kernel update without dropping anyone's traffic.

The scheduler cannot know any of this. You have to tell it.

Key idea

The scheduler works in two steps. It filters out nodes that cannot run the Pod, then scores the rest and picks the best. Every control in this chapter changes the filter or the score.

all nodes→Filter: drop nodes that cannot run it (requests, taints, selectors)→Score: rank the rest (spread, preferences)→Bind to the winner
nodeSelector

The Pod says "only nodes with this label". The simplest pull.

Affinity

A richer pull. Required or just preferred. Toward certain nodes, or toward or away from other Pods.

Taint (on a node)

A "staff only" sign on a door. Keeps Pods out unless they have the right badge.

Toleration (on a Pod)

The badge. It allows a Pod through the door. It does not make it go there.

nodeSelector: the simple pull


kubectl get nodes --show-labels
kubectl label node handbook-worker disktype=ssd
kubectl get nodes -L disktype

Nodes already carry labels like kubernetes.io/hostname and, on clouds, topology.kubernetes.io/zone. You add your own with kubectl label, as in chapter 8.


spec:
  nodeSelector:
    disktype: ssd
  containers:
    - name: db
      image: postgres:17

The Pod can only go to nodes labelled disktype=ssd. If there are none, it stays Pending.

Node affinity: richer pulls


spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values: [ssd, nvme]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: [zone-a]


requiredDuringScheduling...     HARD rule: if no node matches, the Pod stays Pending
  matchExpressions: disktype In [ssd, nvme]
preferredDuringScheduling...    SOFT rule: add points to matching nodes, but go elsewhere if needed
  weight: 80                    how much it matters, 1 to 100
...IgnoredDuringExecution       if the node's labels change AFTER the Pod is running, leave the Pod alone

The operators are In, NotIn, Exists, DoesNotExist, Gt and Lt. The long names look like a mouthful, but they only say how hard the rule is and when it is checked.

nodeSelectornode affinity
Simple equalityyesyes
In, NotIn, Exists…noyes
"Prefer, but do not insist"noyes

Use nodeSelector when one label is enough. Use affinity when you want "either of these", or "this if possible".

Pod anti-affinity and spreading

Now the third problem: three replicas on one node. You want them apart.

Anti-affinity: "not with my own kind"


spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: web
            topologyKey: kubernetes.io/hostname

Read it as: "prefer not to share a hostname (a node) with another Pod labelled app: web". topologyKey says what "together" means: the same node (kubernetes.io/hostname), the same zone (topology.kubernetes.io/zone), and so on.

With required... instead, it becomes a hard rule. Careful: if you ask for five replicas on three nodes, two Pods can never be placed and stay Pending.

Topology spread constraints: the modern way to spread


spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway
      labelSelector:
        matchLabels:
          app: web


maxSkew: 1                           the difference between the fullest and emptiest node may be at most 1 Pod
topologyKey: ...hostname             spread across nodes (use ...zone to spread across zones)
whenUnsatisfiable: ScheduleAnyway    DoNotSchedule = hard rule, ScheduleAnyway = best effort
labelSelector: app=web               which Pods to count

With three nodes and six replicas this gives two per node. Unlike anti-affinity it handles "more replicas than nodes" gracefully, and it works at larger scale. Prefer it for spreading across nodes and zones.

Taints and tolerations: the push

Affinity lives on the Pod and pulls it toward nodes. A taint lives on the node and pushes Pods away, unless they tolerate it.


kubectl taint nodes handbook-worker dedicated=gpu:NoSchedule
kubectl describe node handbook-worker | grep -i taint
kubectl taint nodes handbook-worker dedicated=gpu:NoSchedule-


kubectl taint nodes handbook-worker dedicated=gpu:NoSchedule

                    │               └─────────────── key

A Pod that is allowed on that node carries a matching toleration:


spec:
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule

operator: Exists matches the key with any value. A toleration with only operator: Exists and nothing else tolerates every taint. System Pods sometimes do that.

Key idea

A toleration only lifts a ban. It does not create a pull. A Pod that tolerates dedicated=gpu may still land on any other node. To make a Pod land only on the GPU node and keep everyone else off it, you need both halves: a taint on the node (keeps others out) and a nodeSelector or affinity on the Pod (pulls it there), plus the toleration (lets it in).


apiVersion: v1
kind: Pod
metadata:
  name: gpu-job
spec:
  nodeSelector:
    dedicated: gpu
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
  containers:
    - name: job
      image: busybox:1.37
      command: ["sleep", "3600"]

Label and taint the node with the same words (kubectl label node X dedicated=gpu and kubectl taint nodes X dedicated=gpu:NoSchedule), and this is the "dedicated node" pattern: others are kept out, this Pod is drawn in.

Maintenance: cordon, drain, and Pod disruption budgets

This is the fourth problem, and it is the one you will do in real life.


kubectl cordon handbook-worker
kubectl drain handbook-worker --ignore-daemonsets --delete-emptydir-data
kubectl uncordon handbook-worker
  • cordon marks the node unschedulable. New Pods stay away. Existing ones keep running.
  • drain does a cordon, then evicts the Pods so their controllers recreate them elsewhere. --ignore-daemonsets is needed because a DaemonSet Pod would just come back. --delete-emptydir-data acknowledges that emptyDir data on that node will be lost.
  • uncordon opens the node again after maintenance.

On Linux you would stop services, reboot, start them. Draining is the cluster-aware version: it moves the work away first.

Don't drain everyone at once


apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web

A PodDisruptionBudget (PDB) says "during voluntary disruptions like a drain, keep at least 2 of these Pods running". kubectl drain respects it: it evicts one Pod, waits for the replacement to be ready, then continues. You can also write maxUnavailable: 1. A PDB does not protect against a node crashing. It only governs evictions that Kubernetes itself carries out.

Priority

When the cluster is full, not all Pods are equal. A PriorityClass gives a Pod a number. A higher-priority Pod that cannot be scheduled can preempt: evict lower-priority Pods to make room. System components use the built-in classes system-cluster-critical and system-node-critical. For your own, use a few classes (for example high, default, batch), not dozens.

Linux you already know

  • Pinning to a node is like taskset pinning a process to a CPU core, or deciding which server in your fleet hosts a service. nodeSelector says which.
  • Draining a node is stopping services cleanly before a reboot, the same care as the Linux handbook's advice to have a plan before apt upgrade on production. cordon is "stop taking new work", drain is "finish and move your work", uncordon is "back in service".
  • Priority and preemption are the cluster's version of nice values: who gets the CPU, and who is killed first when resources run out. QoS classes (chapter 13) and PriorityClasses work together.
  • Labels on nodes are the same sticky notes as chapter 8, on machines. A node's kubernetes.io/hostname is the output of the hostname command from the Linux handbook.
  • A taint is a file permission for a machine. A directory with chmod 700 keeps everyone out except its owner. A taint keeps every Pod out except those with the matching toleration.

Common mistakes

Common mistake

"I added a toleration, so my Pod will run on the tainted node." It may. Nothing pulls it there. Add a nodeSelector or affinity too.

Common mistake

A selector or affinity that matches no node. The Pod stays Pending, and the scheduler's event says no node matched the Pod's node affinity or selector. Compare the Pod's wording with kubectl get nodes --show-labels.

Common mistake

Required anti-affinity with more replicas than nodes. Replicas beyond the node count can never be placed. Use preferred anti-affinity or a topology spread constraint instead.

Common mistake

"cordon and drain are the same." cordon only stops new Pods. Running Pods stay. drain also evicts them.

Common mistake

Drain is stuck. The usual causes: a PodDisruptionBudget that cannot be satisfied (for example minAvailable equals the replica count), a DaemonSet Pod (add --ignore-daemonsets), or a Pod with local emptyDir data.

Common mistake

Forgetting that NoExecute evicts. Adding it to a node with running Pods removes any Pod that does not tolerate it. NoSchedule does not.

Common mistake

Using nodeName to skip the scheduler. It bypasses every check, including taints and resource requests. Fine for debugging, wrong for real workloads.

This can break things

Draining the only node that runs a single-replica app, with no PodDisruptionBudget, is an outage. Check kubectl get pods -A -o wide for what is on the node, and make sure important apps have two or more replicas and a PDB before you drain.

Try it

Try it

This needs the three-node kind cluster from chapter 4. Its nodes are handbook-control-plane, handbook-worker and handbook-worker2. Check yours with kubectl get nodes and adjust the names.


kubectl create namespace dev
kubectl get nodes --show-labels

# ---- 1. nodeSelector ----
kubectl label node handbook-worker disktype=ssd
kubectl run on-ssd -n dev --image=busybox:1.37 --overrides='{"spec":{"nodeSelector":{"disktype":"ssd"},"containers":[{"name":"on-ssd","image":"busybox:1.37","command":["sleep","3600"]}]}}'
kubectl get pod on-ssd -n dev -o wide                 # NODE is handbook-worker
kubectl run nowhere -n dev --image=busybox:1.37 --overrides='{"spec":{"nodeSelector":{"disktype":"floppy"},"containers":[{"name":"nowhere","image":"busybox:1.37","command":["sleep","3600"]}]}}'
kubectl get pod nowhere -n dev                        # Pending
kubectl describe pod nowhere -n dev | tail -4         # the scheduler says why

# ---- 2. taint and toleration ----
kubectl taint nodes handbook-worker2 dedicated=gpu:NoSchedule
kubectl create deployment spread -n dev --image=nginx:1.27 --replicas=6
kubectl get pods -n dev -l app=spread -o wide         # none on handbook-worker2
kubectl label node handbook-worker2 dedicated=gpu
kubectl apply -n dev -f gpu-job-pod.yaml
kubectl get pod gpu-job -n dev -o wide                # on handbook-worker2, the only node that allows and attracts it

# ---- 3. cordon and drain ----
kubectl taint nodes handbook-worker2 dedicated=gpu:NoSchedule-
kubectl cordon handbook-worker
kubectl get nodes                                     # SchedulingDisabled
kubectl drain handbook-worker --ignore-daemonsets --delete-emptydir-data
kubectl get pods -n dev -o wide                       # nothing left on handbook-worker
kubectl uncordon handbook-worker

# ---- clean up ----
kubectl delete namespace dev
kubectl label node handbook-worker disktype-
kubectl label node handbook-worker2 dedicated-

What to look for:

  • Part 1: on-ssd lands on handbook-worker. nowhere stays Pending, and its event says the node(s) did not match the Pod's node selector.
  • Part 2: none of the six spread Pods go to the tainted node. gpu-job does, because it tolerates the taint and selects the label.
  • Part 3: after cordon, the node shows SchedulingDisabled. After drain, the Deployment has recreated its Pods on the other nodes. Pods that were created by a bare kubectl run (like on-ssd) would be deleted and not recreated, because nothing owns them. In real life, own your Pods with a controller.

Interview questions

Interview

Click a question, answer out loud first, then check.

What's the difference between taints and affinity?

Direction. Affinity and nodeSelector are on the Pod and attract it toward certain nodes. Taints are on the node and repel Pods, unless a Pod has a matching toleration. A toleration only permits, it doesn't attract. So to reserve nodes for one workload I combine a taint to keep others out, a toleration so the workload may enter, and a nodeSelector or affinity so it actually goes there.

Explain the taint effects.

NoSchedule means new Pods without a toleration won't be placed there, and running Pods are left alone. PreferNoSchedule is a soft version: avoided if possible. NoExecute also stops scheduling and additionally evicts running Pods that don't tolerate it, optionally after tolerationSeconds. The node controller uses NoExecute for not-ready and unreachable nodes, which is why Pods get moved off dead nodes after about five minutes by default.

How do you make sure replicas don't all land on one node, or in one zone?

I'd use topology spread constraints, with the topology key for the node or the zone, a maxSkew of one, and whenUnsatisfiable set to DoNotSchedule for a hard rule or ScheduleAnyway for best effort. Pod anti-affinity can do it too, but a required anti-affinity leaves replicas Pending if there are more replicas than nodes, and it's heavier at scale. Topology spread handles that case better.

How do you safely take a node out for maintenance?

I cordon it so nothing new lands there, then drain it, which evicts the Pods so their controllers recreate them on other nodes. I use --ignore-daemonsets and, if needed, --delete-emptydir-data. Before that I make sure important apps have more than one replica and a PodDisruptionBudget, so the drain evicts them gradually and never drops below the minimum. After maintenance I uncordon the node.

What is a PodDisruptionBudget, and what doesn't it protect against?

It says how many Pods of an app must stay available, or how many may be unavailable, during voluntary disruptions, such as a drain or a cluster upgrade. The eviction API respects it, so a drain waits until the minimum would still be met. It doesn't protect against involuntary failures like a node crashing or an out-of-memory kill. For those I rely on replicas, spread across nodes and zones.

Habits worth keeping

Habits

Remember "taints push, affinity pulls". Use a toleration plus a selector together. Prefer topology spread to anti-affinity for spreading. Give important apps two or more replicas and a PodDisruptionBudget. Cordon, then drain, then uncordon. And when a Pod is Pending, read the scheduler's event first: it names the filter that rejected every node.
