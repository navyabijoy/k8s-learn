Helm

Packaging YAML so you can install it twice

Section 18

By now one app takes a Deployment, a Service, a ConfigMap, maybe an Ingress, and a few more files. Now you want it in dev, staging and production, with different numbers in each. Copying and editing YAML does not scale. Helm is the package manager that fixes that, and if you understood apt in the Linux handbook, you already understand most of it.

The problem

You have five YAML files for web. In dev you want 1 replica and image tag 1.27. In production you want 5 replicas and a different tag, and a bigger memory limit. You copy the folder, edit three numbers, and now you have two folders to keep in step. Add staging. Add a second app. Soon nobody knows which copy is correct.

You also want to install other people's software: a monitoring stack, an Ingress controller, a database. Those come as thirty YAML files. You would rather type one command.

Key idea

A Helm chart is a package of templated Kubernetes YAML plus default values. You install it with your own values, and Helm renders the templates, applies them, and remembers the result as a release you can upgrade or roll back.

And the mistake from the Linux handbook comes back unchanged: helm repo update does not update your software. It only refreshes the catalogue. Your releases stay as they are until you run helm upgrade.

  • -n monitoring --create-namespace installs into that namespace and creates it if missing. Releases belong to a namespace, so helm list shows only the current one. -A shows all.
  • helm install monitoring ...: monitoring is your name for this install. Install the same chart again as monitoring-2 and you get a second, separate release.

What is inside a chart


web/
├── Chart.yaml          name, chart version, appVersion, description
├── values.yaml         the defaults for every setting
├── charts/             sub-charts this chart depends on
└── templates/
    ├── deployment.yaml     Kubernetes YAML, with {{ ... }} holes in it
    ├── service.yaml
    ├── _helpers.tpl        reusable snippets (names, labels)
    └── NOTES.txt           text printed after install

Two files hold the idea. values.yaml holds the choices:


replicaCount: 2
image:
  repository: nginx
  tag: "1.27"
service:
  port: 80
resources:
  requests:
    memory: 64Mi

And a template uses them. Everything in {{ }} is filled in when Helm renders:


apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-web
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}-web
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-web
    spec:
      containers:
        - name: nginx
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: 80
          resources:
            {{- toYaml .Values.resources | nindent 12 }}


{{ .Release.Name }}              the name you gave: helm install THIS-NAME ...
{{ .Values.replicaCount }}       a value from values.yaml (or one you override)
{{ .Chart.Name }}                the chart's name, from Chart.yaml
{{- toYaml ... | nindent 12 }}   print a whole block of values as YAML, indented 12 spaces
{{ if .Values.x }} ... {{ end }} include this part only when a value is set
{{ range .Values.list }}         repeat for each item

Those few pieces cover most templates you will read. Templates are Go's template language with extras. You do not need to master it. You need to read it.

Values: three layers


helm install demo ./web -n dev
helm install demo ./web -n dev -f prod-values.yaml
helm install demo ./web -n dev -f prod-values.yaml --set replicaCount=10
chart's values.yaml←-f file(s), later files win←--set on the command line wins
  • The first uses the chart's defaults.
  • The second overlays your file. Keep one file per environment (dev-values.yaml, prod-values.yaml) in git. That replaces the folder-copying problem.
  • The third overrides one value from the command line. Good for quick tests, bad as the only record of what you did.

Look before you install


helm lint ./web
helm template demo ./web -f prod-values.yaml
helm install demo ./web -n dev --dry-run
helm get values demo -n dev
helm get manifest demo -n dev
  • lint checks the chart for mistakes.
  • template renders the YAML on your machine and prints it. It needs no cluster. This is the most useful debugging command in Helm: you see exactly what would be sent.
  • --dry-run goes further and asks the cluster to validate, without installing.
  • get values shows the values you gave an installed release. get manifest shows the YAML it applied.

Upgrades, history and rollback


helm upgrade demo ./web -n dev --set replicaCount=3
helm history demo -n dev
helm rollback demo 1 -n dev
helm upgrade --install demo ./web -n dev -f prod-values.yaml
  • upgrade re-renders with new inputs and applies the difference. It creates a new revision.
  • history lists revisions, with status and a description.
  • rollback demo 1 re-applies revision 1 as a new revision. (It does not delete the later ones.)
  • upgrade --install installs if it is missing, upgrades if present. The one command to put in a pipeline.

Behind the scenes Helm saves each revision as a Secret in the release's namespace, which is how it remembers history with no database of its own. kubectl get secrets -n dev shows them, with names starting sh.helm.release.v1.

Key idea

A Helm rollback re-applies the old Kubernetes objects. It does not undo what the application did: a database migration that already ran, or data written to a volume, stays. Rollback rolls back YAML, not state.

Helm or Kustomize?

Helm is not the only way. Kustomize is built into kubectl (kubectl apply -k). Instead of templates with holes, it takes plain YAML and applies patches on top, per environment.

HelmKustomize
Approachtemplates and valuesplain YAML plus patches (overlays)
Install other people's softwareyes: the usual wayawkward
Versioned packages and releasesyes, with history and rollbackno: it just renders YAML
Readabilitytemplates can get hard to readalways valid YAML
Best forthird-party software, shared packagesyour own app across environments

They are often combined. GitOps tools such as Argo CD and Flux can render a Helm chart and apply it, so the cluster follows what is in git. Charts can also be stored in OCI registries, the same place as container images: helm install demo oci://registry.example.com/charts/web --version 1.2.0.

Linux you already know

  • The whole chapter is the package management chapter. Repository, update, install, upgrade, remove, search, show. If someone asks you to explain Helm, start with apt.
  • values.yaml is a config file in /etc, and -f prod-values.yaml is "use this config file instead".
  • The upgrade warning from the Linux handbook applies: apt upgrade can break a service, so have a rollback plan on production. helm upgrade can change a database version, so read helm diff or helm template first. Helm gives you rollback, but only for the YAML.
  • helm template is a dry run in the spirit of nginx -t: check the config before you apply it.
  • "Test, then reload": lint, template, dry-run, then install.

Common mistakes

Common mistake

"helm repo update upgrades my apps." It only refreshes the chart list. Releases change only on helm upgrade.

Common mistake

Not pinning the chart version. Without --version, helm upgrade may pull a newer chart with different defaults. Pin it, and change it on purpose.

Common mistake

Upgrading without your values. If you run helm upgrade and forget -f prod-values.yaml, Helm uses the chart defaults and throws away your earlier --set choices. Keep values in files and pass them every time, or use --reuse-values knowingly.

Common mistake

Editing resources by hand. kubectl edit on something Helm owns creates drift. The next helm upgrade may overwrite it or behave strangely. Change values, not live objects.

Common mistake

A typo in a value name. If you write replicaCout: 3 Helm accepts it and ignores it silently, unless the chart ships a values schema. Check with helm get values and helm template.

Common mistake

Forgetting the namespace. helm list shows only one namespace. A release you cannot see is usually in another. Use helm list -A.

Common mistake

CRDs and Helm. Custom resource definitions (chapter 19) in a chart's crds/ folder are installed once and not upgraded or deleted by Helm. When a chart's CRDs change, you must apply them yourself.

Common mistake

Putting passwords in a values file in git. Same rule as Secrets (chapter 11): use an external store, SOPS, or Sealed Secrets.

This can break things

helm uninstall removes everything the release created: Deployments, Services, ConfigMaps. PersistentVolumeClaims made by a StatefulSet's templates stay, but anything else, including data in emptyDir, goes. And helm upgrade on a database chart can move the database to a new major version. Read the chart's notes and run helm template first.

Try it

Try it

You need Helm installed (brew install helm on macOS) and the kind cluster for the second half. The first half needs no cluster at all. Flags change between Helm major versions, so if one is rejected, run helm <command> --help.


# ---- no cluster needed ----
helm version
helm create web                       # a starter chart, with sensible files
ls -R web | head -30
helm lint ./web
helm template demo ./web --set image.tag=1.27 | head -60

# ---- with a cluster ----
helm install demo ./web -n dev --create-namespace --set image.tag=1.27
helm list -n dev
kubectl get all -n dev
kubectl get secrets -n dev                           # the release is stored here

helm upgrade demo ./web -n dev --set image.tag=1.27 --set replicaCount=3
kubectl get pods -n dev
helm history demo -n dev
helm get values demo -n dev

helm rollback demo 1 -n dev
helm history demo -n dev                             # revision 3 is a copy of revision 1
kubectl get pods -n dev

helm uninstall demo -n dev
kubectl delete namespace dev

What to look for:

  • helm create shows the folder layout from this chapter. Open values.yaml and templates/deployment.yaml and find the {{ }} pieces.
  • helm template prints plain Kubernetes YAML with the holes filled in. Change a --set value and watch the output change.
  • After the upgrade, the Deployment has three replicas, and history shows two revisions.
  • After rollback, history shows a third revision whose description says it is a rollback to 1. Replicas go back to one.
  • The sh.helm.release.v1... Secrets are Helm's memory.

Interview questions

Interview

Click a question, answer out loud first, then check.

What is Helm, and what problem does it solve?

Helm is the package manager for Kubernetes. A chart bundles templated manifests with default values, and a release is one installed instance of a chart. It solves two things: parameterising the same manifests for different environments without copying folders, and installing third-party software like monitoring stacks with one command. It also records revisions, so I can upgrade and roll back a release as a unit.

How do values get merged when you install a chart?

In layers. The chart's own values.yaml is the base. Files passed with -f override it, and with several files the later ones win. --set on the command line overrides everything. I keep one values file per environment in git, and pass it on every install and upgrade so nothing silently falls back to chart defaults.

What does helm template do, and why is it useful?

It renders the chart's templates with the given values and prints the resulting Kubernetes YAML, without needing a cluster or installing anything. It's how I see exactly what Helm would apply, so I use it to debug templates and in CI to validate the output, for example with a linter or a policy check. GitOps tools do something similar when they render a chart before applying it.

How does a Helm rollback work, and what doesn't it undo?

Helm stores every revision of a release as a Secret in the namespace. helm rollback RELEASE N re-applies the manifests from revision N, recorded as a new revision. It rolls back Kubernetes objects only. A database migration that already ran, or data already written to a volume, isn't undone. So for stateful apps I treat an upgrade as potentially one-way, and take backups first.

Helm or Kustomize?

They solve overlapping problems differently. Helm uses templates and values, gives me packaged, versioned releases with history, and is the normal way to install third-party software. Kustomize takes plain YAML and layers patches per environment, built into kubectl, and the result is always valid YAML. I'd use Helm for shared or third-party packages and Kustomize for my own manifests across environments, and they combine fine, for instance Argo CD rendering a chart and then patching it.

Habits worth keeping

Habits

Remember that repo update is apt update, not apt upgrade. Pin chart versions. Keep one values file per environment in git and pass it every time. Run helm template and lint before you install. Never edit Helm-owned objects by hand. Use upgrade --install in pipelines. And treat rollback as YAML-only.
